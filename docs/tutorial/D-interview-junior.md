Этот раздел — тренажёр. Здесь собраны вопросы, которые реально задают на
собеседованиях уровня Junior по Objective-C: про синтаксис, объекты,

главами тут нет — это проверка того, уложилось ли уже пройденное.

Формат у каждой задачи один. Сначала — условие. Если это вопрос «что
выведет программа», не беги сразу к ответу: закрой нижнюю часть рукой,
проговори ответ вслух или запиши, и только потом читай разбор. Так
проверка работает, а простое чтение — нет.

Многие задачи сопровождаются компилируемым файлом в `code/`. Собрать и
запустить любой можно одной командой:

```text
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/junior-01-nil.m -o /tmp/t && /tmp/t
```

Весь показанный вывод — настоящий, снят с этой команды. Дата, время и
числа в скобках у тебя будут свои — их добавляет `NSLog` (см. главу 1).
Часть задач намеренно про падения программы (выход за границу массива,
`addObject:nil`). Такой код мы разбираем словами, но в `code/` не кладём —
чтобы проверка примеров оставалась зелёной.

## Задача 1. Что выведет `[nil length]`

Дан код:

```objc
NSString *s = nil;
NSUInteger len = [s length];
NSString  *up  = [s uppercaseString];
BOOL       has = [s hasPrefix:@"a"];
NSLog(@"%lu / %@ / %d", (unsigned long)len, up, has);
```

Программа упадёт? Если нет — что напечатает?

**Разбор.** Программистов из Си здесь подлавливают чаще всего. В Си проход
по нулевому указателю — как правило, мгновенный крах (segmentation
fault). Кажется, что
и тут `[nil length]` обязано уронить программу. Не уронит.

В Objective-C **отправка сообщения `nil` — безопасная пустая операция**.
Runtime видит, что получатель `nil`, и просто ничего не делает. А в ответ
отдаёт «нулевой» результат — какой именно, зависит от типа возврата
метода:

- метод возвращает число (`NSUInteger`, `NSInteger`, `int`…) → получишь `0`;
- метод возвращает объект (`NSString *`, `id`…) → получишь `nil`;
- метод возвращает `BOOL` → получишь `NO`.

Поэтому вывод (файл `code/junior-01-nil.m`):

```text
[nil length]           = 0
[nil uppercaseString]  = (null)
[nil hasPrefix:@"a"]   = 0
```

`(null)` — это так `NSLog` печатает `nil`-объект. `0` в конце — это `NO`.

Это удобно (не нужно обвешивать каждый объект проверкой `if (x != nil)`),
но и опасно: если объект случайно оказался `nil`, ошибка не выстрелит на
месте, а тихо даст `0`/`nil`/`NO`, и баг всплывёт позже и не там. Где
результат важен — проверяй `if (x == nil)` явно.

> **Отличие от Си.** `*p` при `p == NULL` в Си роняет программу.
> `[nil message]` в Objective-C — узаконенная пустая операция с нулевым
> результатом. Это сознательное решение языка, а не случайность.

## Задача 2. `==` или `isEqualToString:`

Что напечатает каждая строка?

```objc
NSString *a = @"hello";
NSString *b = [NSString stringWithFormat:@"%@%@", @"hel", @"lo"];
NSLog(@"%d", (a == b));
NSLog(@"%d", [a isEqualToString:b]);
```

**Разбор.** Текст у `a` и `b` одинаковый — `hello`. Но вопрос не в тексте.

- `a == b` сравнивает **указатели**: «это один и тот же объект в памяти?».
- `[a isEqualToString:b]` сравнивает **содержимое**: «одинаковый ли текст,
  буква за буквой?».

`a` — это строковый литерал, он живёт в неизменяемой области программы.
`b` собран в рантайме методом `stringWithFormat:` — это **другой** объект.
Значит, указатели разные, а текст одинаковый:

```text
a == b               : 0
[a isEqualToString:b]: 1
адрес a = 0x10e7b1038
адрес b = 0xd146d585ee0ba9ab
```

(Адреса у тебя будут свои, важно одно — они разные.) Вывод файла
`code/junior-02-string-equal.m`. Странный «адрес» `b` — не опечатка:
короткую строку runtime упаковал прямо в указатель (tagged pointer,
подробнее в задаче 3), в куче такой строки нет вовсе.

Правило на всю жизнь: **строки сравнивай по содержимому через
`isEqualToString:`, никогда через `==`.** Две внешне одинаковые строки
`==` легко сочтёт разными. `==` для объектов уместно, только когда нужна
именно **идентичность** — «тот же самый объект?»: проверить, не `nil` ли
это, или сравнить с объектом-одиночкой вроде `[NSNull null]` (задача 9).

> **Отличие от Си.** В Си строки тоже не сравнивали через `==` (это
> сравнило бы адреса `char *`) — для содержимого был `strcmp`. Здесь та же
> логика, только вместо `strcmp` — сообщение `isEqualToString:`.

## Задача 3. Два `NSNumber` и `==`

```objc
NSNumber *a = @42;
NSNumber *b = @42;
NSNumber *x = [NSNumber numberWithDouble:12345.6789];
NSNumber *y = [NSNumber numberWithDouble:12345.6789];
NSLog(@"%d %d", (a == b), [a isEqualToNumber:b]);
NSLog(@"%d %d", (x == y), [x isEqualToNumber:y]);
```

Что выведет?

**Разбор.** Логика та же, что у строк: содержимое чисел сравнивает
`isEqualToNumber:`, а `==` сравнивает указатели. Но с числами есть
ловушка хитрее. Реальный вывод (`code/junior-03-number-equal.m`):

```text
@42 == @42                : 1
[@42 isEqualToNumber:@42] : 1
x == y                    : 0
[x isEqualToNumber:y]     : 1
```

Смотри: `@42 == @42` дало `1` (правда!), а `x == y` для двух одинаковых
дробных — `0` (ложь!). Как так?

Маленькие целые `NSNumber` рантайм на 64-битных системах хранит **прямо
внутри указателя** (это называется tagged pointer — «помеченный
указатель»): само число 42 закодировано в биты «адреса», отдельный объект
в памяти не создаётся. Поэтому два `@42` получают одинаковый «адрес», и
`==` случайно оказывается прав. А `12345.6789` так не упаковывается —
создаются два разных объекта, и `==` честно возвращает `0`.

Вывод: `==` для чисел **иногда случайно прав, иногда врёт** — на него
нельзя полагаться вообще. Сравнивай значения через `isEqualToNumber:`
(а `isEqualToNumber:` верен в обоих случаях — обе строки с ним дали `1`).

## Задача 4. Что делают `alloc` и `init` и что будет, если забыть `init`

```objc
@interface Box : NSObject
@property (nonatomic) NSInteger value;
@end
@implementation Box
- (instancetype)init {
    self = [super init];
    if (self) { _value = 100; }
    return self;
}
@end
// ...
Box *raw = [Box alloc];
Box *ok  = [[Box alloc] init];
```

Чему равны `raw.value` и `ok.value`?

**Разбор.** Объект в Objective-C рождается в два шага, и у каждого своя
работа:

- `alloc` (allocate, выделить) — просит у системы память под новый объект
  и **обнуляет** все его поля. Объект уже существует, но «сырой»: настройка
  ещё не выполнена.
- `init` (initialize, инициализировать) — приводит объект в рабочее
  состояние. Здесь `init` задаёт `_value = 100` (значение по умолчанию).

Если `init` забыть, останется сырой объект с нулевыми полями. Вывод
(`code/junior-04-alloc-init.m`):

```text
после alloc:        value = 0
после alloc + init: value = 100
```

`raw` прошёл только `alloc` → `value` нулевой. `ok` прошёл `alloc` и
`init` → `value` равен 100, как задумано в инициализаторе. Поэтому почти
всегда их пишут слитной парой: `[[Box alloc] init]`.

Разбери и сам инициализатор — это шаблон, который встречается постоянно:

- `self = [super init];` — сначала даём родителю настроить свою часть
  объекта и **присваиваем результат `self`** (родитель имеет право вернуть
  другой объект или `nil`);
- `if (self) { ... }` — настраиваем свои поля, только если родитель не
  отдал `nil`;
- `return self;` — обязательно возвращаем готовый объект.

Частый баг новичка — забыть `return self;` или `self = [super init]`.
Без `return self;` инициализатор вернёт мусор (компилятор предупредит:
`non-void function does not return a value`). Без `self =` у `NSObject`
всё случайно сработает, но если родитель вернёт другой объект, ты будешь
настраивать не тот (подробнее — задача 20).

> **Отличие от Си.** В Си это было `malloc(sizeof(...))` плюс ручное
> заполнение полей. Здесь `alloc` выделяет память, а `init` заполняет —
> но заполняет сам объект, по своему чертежу. Освобождать руками не надо:
> память объектов считает ARC (глава 13).

## Задача 5. `strong` против `copy` у свойства `NSString`

Дан класс с двумя свойствами-строками:

```objc
@property (nonatomic, strong) NSString *strongName;
@property (nonatomic, copy)   NSString *copiedName;
```

И код:

```objc
NSMutableString *m = [NSMutableString stringWithString:@"Анна"];
p.strongName = m;
p.copiedName = m;
[m appendString:@" Каренина"];
NSLog(@"%@ / %@", p.strongName, p.copiedName);
```

Что напечатает?

**Разбор.** Подвох в том, что `NSString *` может в действительности указывать
на `NSMutableString` — изменяемую строку (`NSMutableString` — потомок
`NSString`). Мы кладём в оба свойства **одну и ту же** изменяемую строку
`m`, а потом меняем `m`.

- `strong` хранит **ту же ссылку**, что ему дали. Свойство и переменная
  `m` указывают на один объект. Изменили `m` — изменилось и то, что видит
  `strongName`.
- `copy` при присваивании делает **снимок** — неизменяемую копию. Свойство
  получает свой отдельный объект `@"Анна"`, на который последующие правки
  `m` уже не влияют.

Вывод (`code/junior-05-copy-property.m`):

```text
strong: Анна Каренина
copy:   Анна
```

`strongName` «поехал» вслед за `m`, а `copiedName` остался снимком. Вот
почему **строковые свойства почти всегда объявляют с `copy`**: ты хочешь
своё неизменное значение, а не чужую строку, которую кто-то снаружи
поменяет у тебя за спиной. То же правило — для `NSArray`,
`NSDictionary`, `NSSet`: их свойства тоже делают `copy`.

## Задача 6. `BOOL`, `YES`, `NO` и ловушка с числом

Что выведет?

```objc
NSLog(@"%d %d", YES, NO);
int weird = 256;
BOOL fromInt = (BOOL)weird;
NSLog(@"%d", fromInt);
```

**Разбор.** `BOOL` — это objc-шный «да/нет» с двумя именованными
значениями: `YES` (под капотом 1) и `NO` (под капотом 0). Печатаем их
через `%d`, потому что это маленькие целые. Первая строка очевидна:
`1 0`.

А вот вторая — классическая ловушка, и ответ в ней **зависит от
платформы**. На Intel-маке (x86_64) `BOOL` — это `signed char`, обычное
однобайтовое целое. Число `256` в один байт не влезает: его младший байт
равен нулю (256 = `0x100`). При укладке в `BOOL` старшие биты
отбрасываются, остаётся `0`, то есть `NO`. Вывод, снятый на Intel-маке
(`code/junior-06-bool.m`):

```text
YES = 1, NO = 0
sizeof(BOOL) = 1 байт
есть элементы: 1
BOOL из числа 256 = 0
```

Число было ненулевым (256, «истина по смыслу»), а `BOOL` получился `0`,
«ложь».

На Apple Silicon (arm64) и на iPhone `BOOL` — это настоящий `bool` из Си.
Там любое ненулевое число при приведении превращается в `1`, и последняя
строка покажет `BOOL из числа 256 = 1`. Хороший ответ на собеседовании
называет обе платформы: «на x86_64 — `0` из-за обрезки байта, на arm64 —
`1`». Код, который работает только на одной из них, — баг. Отсюда два
правила:

1. **Не заталкивай произвольное число прямо в `BOOL`.** Если хочешь
   «не ноль ли это», пиши явное сравнение: `BOOL ok = (count > 0);`.
2. **Не сравнивай `BOOL` с `YES` напрямую** (`if (x == YES)`). Там, где
   `BOOL` — `signed char`, в `x` может попасть, скажем, `2` (например,
   `BOOL x = flags & 2;`). Тогда `x` — истина в условии `if (x)`, но
   `x == YES` (то есть `2 == 1`) даст ложь. Пиши просто `if (x)` — это
   проверяет «истинность», а не точное равенство единице.

Привычка «не пихать числа в `BOOL` и не сравнивать с `YES`» спасает на
любой платформе.

## Задача 7. `addObject:nil` — что произойдёт

```objc
NSMutableArray *a = [NSMutableArray array];
NSString *name = nil;
[a addObject:name];
```

Программа продолжит работать?

**Разбор.** Нет — она **упадёт** прямо на `addObject:`. И это надо чётко
отделять от задачи 1.

Сообщение `nil` (получатель — `nil`) безопасно. Но здесь получатель — это
живой массив `a`, а `nil` идёт **аргументом**. `NSMutableArray` не умеет
хранить «ничего»: коллекции Foundation хранят только настоящие объекты.
Получив `nil` аргументом, метод выбрасывает исключение вроде:

```text
*** -[__NSArrayM insertObject:atIndex:]: object cannot be nil
```

и программа аварийно завершается. Тот же эффект даст литерал с `nil`
внутри: `@[a, nil, b]` — крах на месте сборки массива.

Поэтому перед добавлением проверяй, что объект есть:

```objc
if (name != nil) {
    [a addObject:name];
}
```

А если нужно осмысленное «здесь значения нет» — кладут не `nil`, а
объект-заглушку `NSNull` (см. задачу 9).

Запоминай разницу: **`nil`-получатель — тихо и безопасно; `nil`-аргумент
у коллекции — краш.**

## Задача 8. `objectAtIndex:` против `firstObject` на пустом массиве

```objc
NSArray *empty = @[];
id a = [empty firstObject];
id b = [empty objectAtIndex:0];
```

Что вернёт каждая строка?

**Разбор.** Они ведут себя **по-разному**, и в этом вся соль.

- `firstObject` (и `lastObject`) на пустом массиве **возвращает `nil`** —
  безопасно, без падения.
- `objectAtIndex:0` на пустом массиве **роняет программу**: индекс 0 за
  границей пустого массива, runtime выбрасывает исключение
  `NSRangeException` — `index 0 beyond bounds for empty array`.

Поэтому вторую строку в файл мы не кладём. Безопасную часть проверяем в
`code/junior-07-firstobject.m`:

```text
firstObject пустого: (null)
lastObject  пустого: (null)
firstObject:     10
objectAtIndex:0: 10
lastObject:      30
```

На непустом массиве `firstObject` и `objectAtIndex:0` дают одно и то же.
Разница только на пустом: один отдаёт `nil`, другой падает.

Практический вывод: когда не уверен, что в массиве есть элементы, бери
крайние через `firstObject`/`lastObject` — они прощают пустоту.
`objectAtIndex:` используй, только когда индекс точно в пределах
`0 ... count-1`.

## Задача 9. `nil`-значение в словаре и `NSNull`

```objc
NSMutableDictionary *d = [NSMutableDictionary dictionary];
d[@"name"]   = @"Анна";
d[@"middle"] = [NSNull null];
d[@"city"]   = nil;
NSLog(@"%@ / %@ / %@ / %@",
      d[@"name"], d[@"middle"], d[@"city"], d[@"absent"]);
```

Что выведет — и не упадёт ли строка с `d[@"city"] = nil`?

**Разбор.** Сразу про `d[@"city"] = nil` — это **не** краш и **не**
вставка пустого значения. Для изменяемого словаря присваивание `nil`
по ключу через скобки означает **удаление ключа**. После этой строки
ключа `city` в словаре просто нет.

Хранить `nil` как значение словарь не может (та же причина, что у массива
в задаче 7). Когда надо явно сказать «значение здесь отсутствует, и это
осмысленно», кладут объект-заглушку **`NSNull`** — это настоящий объект,
синглтон, который получают сообщением `[NSNull null]`.

Вывод (`code/junior-08-nsnull.m`, без строки `city`, чтобы показать
работающий результат):

```text
name:   Анна
middle: <null>
absent: (null)
middle — это NSNull, а не настоящее значение
```

Тонкость: `<null>` (в угловых скобках) — это как печатается объект
`NSNull`. А `(null)` (в круглых) — это `nil`, то есть «ключа нет вообще»
(`absent` мы не клали). Отличать их важно: за отсутствующим ключом словарь
возвращает `nil`, а `NSNull` — это лежащее по ключу реальное значение,
которое надо проверять сравнением `== [NSNull null]`.

Зачем вообще `NSNull`? Чаще всего он прилетает из разобранного JSON: поле
с `null` в ответе сервера превращается именно в `NSNull`, и забыть про
это — типичный источник багов («думал, там строка, а там `NSNull`»).

## Задача 10. Почему нельзя `[array addObject:5]`

```objc
NSMutableArray *a = [NSMutableArray array];
[a addObject:5];        // ???
[a addObject:@5];       // ???
```

Какая строка скомпилируется, какая нет, и почему?

**Разбор.** Первая строка **не компилируется**. `addObject:` ждёт объект
(`id`), а `5` — это голый `int`, примитив языка Си, не объект. Объекту
коллекции дать примитив нельзя.

Чтобы число попало в коллекцию, его сначала **упаковывают** (boxing) в
объект `NSNumber`. Делают это литералом:

- `@5` — упаковать целое 5;
- `@3.14` — упаковать дробное;
- `@(10 + 5)` — упаковать значение **выражения** (скобки обязательны, если
  внутри не одна константа, а вычисление или переменная: `@(x)`).

Вторая строка (`@5`) поэтому в порядке. Достать число обратно
(unboxing) — сообщением вроде `intValue` / `doubleValue`. Вывод
`code/junior-09-nsnumber.m`:

```text
храним объект:   42
распаковали int: 42
второй элемент:  15
double обратно:  3.14
```

> **Отличие от Си.** В Си массив `int a[]` хранит числа напрямую — это
> ведь просто кусок памяти. `NSMutableArray` хранит **только объекты**,
> поэтому число приходится заворачивать в `NSNumber`. Зато один массив
> может держать вперемешку строки, числа и что угодно — все они объекты.

## Задача 11. Быстрый перебор `for-in` и мутация во время него

```objc
NSMutableArray *nums = [@[@1, @2, @3, @4] mutableCopy];
for (NSNumber *x in nums) {
    if (x.intValue % 2 == 0) {
        [nums removeObject:x];   // удаляем прямо в цикле
    }
}
```

Что случится?

**Разбор.** Программа **упадёт**. Цикл `for (x in nums)` — это быстрый
перебор (fast enumeration). Он проходит коллекцию и одновременно следит,
не менялась ли она. Если изменить коллекцию **прямо во время перебора**
(`removeObject:`, `addObject:`), runtime ловит это и выбрасывает
исключение `NSGenericException` (адрес у тебя будет свой):

```text
*** Collection <__NSArrayM: 0x6000010e4270> was mutated while being
enumerated.
```

Менять то, что сейчас перебираешь, нельзя. Правильных приёмов два:

1. **Собрать кандидатов, удалить потом.** Проходим коллекцию только на
   чтение, копим в отдельный массив, что надо убрать, и удаляем уже после
   цикла.
2. Перебирать **копию** (`for (x in [nums copy])`), а менять оригинал.

Первый приём проверяем в `code/junior-10-forin.m`. Там два куска:
сначала обычный перебор массива фруктов (только чтение), потом удаление
чётных из `@[@1, @2, @3, @4, @5]` по первому приёму:

```text
фрукт: яблоко (длина 6)
фрукт: банан (длина 5)
фрукт: вишня (длина 5)
без чётных: (
    1,
    3,
    5
)
```

(`яблоко` — 6 символов: перебор отработал штатно, потому что массив
`fruits` мы только читали.) Чётные удалились корректно, потому что
`removeObjectsInArray:` вызван **после** цикла, а не внутри.

> **Отличие от Си.** Перебор `for (int i=0; i<n; i++) a[i]` в Си про
> мутацию ничего не знает — массив фиксированный, «сломать перебор
> вставкой» там нечем. Foundation-коллекции растут и сжимаются, поэтому
> язык специально защищается от изменения во время обхода.

## Задача 12. Полиморфизм: какой метод вызовется

```objc
@interface Animal : NSObject
- (NSString *)sound;
- (void)describe;
@end
@implementation Animal
- (NSString *)sound { return @"..."; }
- (void)describe {
    NSLog(@"%@ говорит: %@", NSStringFromClass([self class]), [self sound]);
}
@end

@interface Dog : Animal @end
@implementation Dog
- (NSString *)sound { return @"Гав"; }
@end
// аналогично Cat -> @"Мяу"

NSArray *zoo = @[[Animal new], [Dog new], [Cat new]];
for (Animal *a in zoo) { [a describe]; }
```

`describe` написан **один раз** в `Animal`. Что напечатают три вызова?

**Разбор.** Здесь работает полиморфизм. Переменная цикла объявлена как
`Animal *a`, но это лишь обещание компилятору «тут будет животное». А
какой метод реально выполнится, runtime выбирает по **фактическому
классу** объекта в момент выполнения (динамическая диспетчеризация,
глава 5).

`describe` унаследован всеми и сам по себе не переопределён — поэтому
выполняется один и тот же его код. Но внутри он шлёт `[self sound]`, и вот
тут `self` — это конкретный объект: для `Dog` сработает `Dog`-овский
`sound`, для `Cat` — кошачий. Вывод (`code/junior-11-polymorphism.m`):

```text
Animal говорит: ...
Dog говорит: Гав
Cat говорит: Мяу
```

Один метод `describe`, а звук у каждого свой — потому что `sound`
выбирается по реальному классу `self`, а не по типу переменной `a`.
`NSStringFromClass([self class])` подтверждает: класс у каждого свой.

> **Отличие от Си.** В Си `describe(animal)` — обычная функция, она
> вызвала бы один и тот же `sound`, какой указали при компиляции. Здесь
> объект сам решает в рантайме, какой `sound` его — это и есть «отправка
> сообщения», а не «вызов функции».

## Задача 13. `isKindOfClass:` против `isMemberOfClass:`

`Dog` — потомок `Animal`. Что выведет?

```objc
Dog *d = [Dog new];
NSLog(@"%d", [d isKindOfClass:[Animal class]]);
NSLog(@"%d", [d isMemberOfClass:[Animal class]]);
NSLog(@"%d", [d isMemberOfClass:[Dog class]]);
```

**Разбор.** Оба сообщения спрашивают объект о его классе, но по-разному:

- `isKindOfClass:` — «объект относится к этому классу **или любому его
  потомку**?». Учитывает всю цепочку наследования.
- `isMemberOfClass:` — «объект относится **ровно** к этому классу?».
  Точное совпадение, потомки не считаются.

`d` — это `Dog`, а `Dog` — потомок `Animal`. Значит:

- `[d isKindOfClass:[Animal class]]` → `YES` (`Dog` — разновидность
  `Animal`);
- `[d isMemberOfClass:[Animal class]]` → `NO` (`d` не ровно `Animal`, а
  `Dog`);
- `[d isMemberOfClass:[Dog class]]` → `YES` (вот теперь точное совпадение).

Полный вывод `code/junior-12-iskindof.m`:

```text
isKindOfClass:Dog      = 1
isKindOfClass:Animal   = 1
isKindOfClass:NSObject = 1
isMemberOfClass:Dog    = 1
isMemberOfClass:Animal = 0
```

`isKindOfClass:NSObject` тоже `1` — `NSObject` корень всех классов, любой
объект ему «родственник». На практике почти всегда нужен именно
`isKindOfClass:` (он учитывает наследование). `isMemberOfClass:` берут
редко — когда важно поймать строго один класс и отсечь потомков.

## Задача 14. `instancetype` или `id` в фабричном методе

В чём разница между двумя объявлениями и почему первое лучше?

```objc
+ (instancetype)widgetWithTitle:(NSString *)title;   // так
+ (id)widgetWithTitle:(NSString *)title;             // или так?
```

**Разбор.** Оба варианта вернут объект, и программа в обоих случаях
заработает. Разница в том, **что знает компилятор** о типе результата.

- `id` — «какой-то объект, тип неизвестен». Компилятор не проверит, что
  ты потом с ним делаешь.
- `instancetype` — «объект **именно этого** класса» (того, у которого
  вызвали метод). Компилятор знает точный тип и проверит обращения к нему.

Зачем это нужно на практике:

```objc
NSString *s = [Widget widgetWithTitle:@"Кнопка"];      // (1)
NSUInteger n = [Widget widgetWithTitle:@"Кнопка"].title.length; // (2)
```

- (1) Ошибка: в строковую переменную кладём `Widget`. С `instancetype`
  компилятор это ловит: `incompatible pointer types initializing
  'NSString *' with an expression of type 'Widget *'`. С `id` — молчит,
  и программа упадёт уже при запуске, когда `s` получит строковое
  сообщение.
- (2) С `instancetype` результат — `Widget *`, и точка `.title` сразу
  работает. С `id` это ошибка компиляции: `property 'title' not found on
  object of type 'id'`. Особенно это важно при
наследовании: фабричный метод с `instancetype`, написанный в `Widget`,
для подкласса `RoundWidget` вернёт уже `RoundWidget *`, а с `id` — просто
«объект».

Внутри метода для этого пишут `[[self alloc] init]`, а не
`[[Widget alloc] init]`: `self` в методе класса — это сам класс, по
которому метод вызвали, поэтому подкласс получит объект своего класса.
Проверка `code/junior-13-instancetype.m`:

```text
создан Widget с title = Кнопка
```

Тонкость для тех, кто хочет блеснуть: у методов семейств `alloc`,
`init`, `new` компилятор выводит тип результата сам, даже если там
написано `id` (так называемый related result type). У фабрик вроде
`widgetWithTitle:` такого вывода нет — там `instancetype` обязателен.

Правило: для `alloc`/`init` и фабричных методов («конструкторов»)
возвращай **`instancetype`**. `id` оставляй там, где тип результата и
правда заранее не известен.

## Задача 15. Реализуй стек поверх `NSMutableArray`

Напиши класс `Stack` с операциями `push:`, `pop`, `peek`, `isEmpty`,
`count`. Стек — это «стопка тарелок»: кладём сверху и снимаем сверху
(LIFO, last in — first out).

**Разбор.** Стек удобно построить поверх готового `NSMutableArray`,
работая только с **одним** его концом. Берём конец массива за «верх
стопки»: `addObject:` кладёт в конец, `lastObject` смотрит конец,
`removeLastObject` снимает с конца. Все три операции — быстрые.

```objc
@interface Stack : NSObject
- (void)push:(id)object;
- (id)pop;
- (id)peek;
- (BOOL)isEmpty;
- (NSUInteger)count;
@end

@implementation Stack {
    NSMutableArray *_items;          // приватное хранилище
}

- (instancetype)init {
    self = [super init];
    if (self) { _items = [NSMutableArray array]; }
    return self;
}

- (void)push:(id)object { [_items addObject:object]; }

- (id)pop {
    if (_items.count == 0) return nil;   // защита от выхода за границу
    id top = [_items lastObject];
    [_items removeLastObject];
    return top;
}

- (id)peek    { return [_items lastObject]; }   // на пустом вернёт nil
- (BOOL)isEmpty { return _items.count == 0; }
- (NSUInteger)count { return _items.count; }

@end
```

Главное в реализации:

- Хранилище `_items` объявлено в фигурных скобках `@implementation` — это
  приватное поле, снаружи его не видно. Класс отдаёт наружу только
  осмысленные операции, а на чём он построен — его дело (инкапсуляция).
- В `pop` стоит проверка на пустоту. Документация Apple обещает, что
  `removeLastObject` у пустого массива выбросит `NSRangeException`. По
  нашему запуску современный Foundation молча ничего не делает, но
  опираться на недокументированную мягкость нельзя — поэтому сначала
  проверяем и возвращаем `nil`. `peek` через `lastObject`
  проверки не требует — `lastObject` на пустом сам отдаёт `nil`.
- `_items` создаём в `init`, иначе он останется `nil`, и `push:` будет
  тихо слать сообщения в `nil` (см. задачу 1) — элементы «добавлялись» бы
  в никуда.

Вывод `code/junior-14-stack.m`:

```text
пустой в начале: 1
после трёх push, count = 3
peek (не снимая): c
pop: c
pop: b
после двух pop, count = 1
pop: a
pop пустого: (null)
пустой в конце: 1
```

Видно главное свойство LIFO: положили `a, b, c`, а снимаются они в
обратном порядке — `c, b, a`. `pop` пустого стека отдал `nil` и не уронил
программу.

## Задача 16. Найди утечку: сильная ссылка на `delegate`

Что не так с этим кодом и к чему приведёт?

```objc
@interface Downloader : NSObject
@property (nonatomic, strong) id<DownloadDelegate> delegate;  // strong
@end

@interface Controller : NSObject <DownloadDelegate>
@property (nonatomic, strong) Downloader *downloader;
@end
// контроллер создаёт загрузчик и ставит себя его делегатом:
self.downloader = [Downloader new];
self.downloader.delegate = self;
```

**Разбор.** Здесь **цикл удержания** (retain cycle) — обе стороны держат
друг друга сильно, и ни одна не может освободиться:

```text
Controller ──strong──> Downloader
    ▲                       │
    └────────strong─────────┘   (delegate = strong)
```

`Controller` сильно держит `Downloader` (свойство `downloader`).
`Downloader` сильно держит `Controller` обратно (свойство `delegate`).
Когда `Controller` должен бы умереть, его всё ещё держит `Downloader` — а
`Downloader` держит `Controller`. ARC видит, что у обоих ещё есть владелец,
и не освобождает ни того, ни другого. Память утекла, `dealloc` не
вызовется никогда.

**Лечение — сделать `delegate` слабой ссылкой (`weak`):**

```objc
@property (nonatomic, weak) id<DownloadDelegate> delegate;
```

`weak` указывает на объект, но **не удерживает** его. Цикл разрывается:
сильная связь остаётся только одна (`Controller` → `Downloader`), и когда
контроллер уходит, освобождаются оба. Файл `code/junior-15-delegate.m`
доказывает это печатью из `dealloc`:

```text
Controller: загрузка завершена
Controller освобождён
Downloader освобождён
после блока — оба объекта уже мертвы
```

Оба `dealloc` сработали — утечки нет. Будь `delegate` сильным, этих двух
строк про «освобождён» в выводе не было бы вовсе.

Правило, которое спрашивают почти на каждом собеседовании: **свойство
`delegate` всегда `weak`.** Делегат — это «тот, кому я докладываю», а не
«тот, кем я владею»; владеть им я не должен.

> **Отличие от Си.** В Си памятью управляешь сам (`malloc`/`free`), и
> «циклов удержания» нет — есть просто забытый `free` (утечка) или двойной
> `free` (крах). Здесь память считает ARC по числу сильных ссылок, и новый
> класс ошибок — два объекта, держащие друг друга. `weak` — штатное
> средство такие циклы рвать.

## Задача 17. `mutableCopy` и `copy` — что можно менять

```objc
NSArray *a = @[@1, @2, @3];
NSMutableArray *m1 = [a copy];
NSMutableArray *m2 = [a mutableCopy];
[m2 addObject:@4];   // строка A
[m1 addObject:@5];   // строка B
```

Какая строка упадёт?

**Разбор.** Подвох в типе, который реально возвращают эти сообщения, а не
в том, что написано слева.

- `copy` у массива возвращает **неизменяемый** `NSArray` — даже если ты
  присвоил его переменной типа `NSMutableArray *`. Компилятор поверит
  объявлению и пропустит код, но в рантайме объект-то неизменяемый.
- `mutableCopy` возвращает **изменяемый** `NSMutableArray` — настоящую
  редактируемую копию.

Поэтому:

- строка A (`[m2 addObject:@4]`) — в порядке: `m2` действительно
  изменяемый.
- строка B (`[m1 addObject:@5]`) — **краш**: `m1` в действительности
  неизменяемый `NSArray`, и в ответ на `addObject:` прилетит исключение
  `-[__NSArrayI addObject:]: unrecognized selector sent to instance`
  (имя класса в скобках зависит от того, как массив создан).

Бонус: `copy` у **неизменяемого** массива обычно даже не копирует —
возвращает тот же объект. По нашему запуску `m1 == a` здесь истинно.
Копировать то, что и так не меняется, незачем.

Тип переменной (`NSMutableArray *`) — это лишь обещание компилятору, а
изменяемость определяет **реальный объект**, который вернуло сообщение.
`copy` всегда отдаёт неизменяемый вариант, `mutableCopy` — изменяемый,
как бы ты ни назвал переменную. Этот код мы не кладём в `code/`, потому
что строка B роняет программу.

## Задача 18. Объект-значение как ключ словаря

```objc
NSMutableDictionary *d = [NSMutableDictionary dictionary];
NSString *k1 = [NSString stringWithFormat:@"пользователь_%d", 7];
d[k1] = @"Анна";
NSString *k2 = [NSString stringWithFormat:@"пользователь_%d", 7];
NSLog(@"%@", d[k2]);
```

`k1` и `k2` — разные объекты. Найдётся ли значение по `k2`?

**Разбор.** Да, напечатает `Анна`. И это важно понять: словарь ищет ключ
**не по адресу, а по содержимому**.

Когда кладёшь и достаёшь по ключу, `NSDictionary` не сравнивает указатели
через `==`. Он спрашивает у ключа две вещи: его `hash` (число-отпечаток)
и `isEqual:` (равенство по содержимому). У двух строк `user_7` хеш
одинаковый и `isEqual:` вернёт `YES`, хотя это разные объекты в памяти.
Поэтому ключ находится.

Отсюда следствие, о котором спрашивают чуть выше уровнем: если делаешь
**свой** класс ключом словаря, ты обязан правильно реализовать у него
пару `isEqual:` и `hash` (согласованно: равные объекты — одинаковый хеш).
Иначе словарь не найдёт по ключу то, что в него положил. У готовых
`NSString` и `NSNumber` это уже сделано за тебя — потому строки и числа
и используют ключами чаще всего.

(Почему ключ длинный, кириллицей? Короткую ASCII-строку вроде `user_7`
runtime упакует в tagged pointer (задача 3), и `k1 == k2` окажется
истиной — вопрос потеряет смысл.)

Ещё деталь: ключи словарь **копирует** (`copy`), поэтому ключ обязан
поддерживать протокол `NSCopying`. Эта копия и защищает: даже если ключом
дали `NSMutableString`, а потом поменяли её, внутри словаря лежит
замороженный снимок, и значение по старому тексту находится. А вот
`NSSet` свои элементы **не** копирует: положишь в множество изменяемую
строку, поменяешь её — хеш собьётся, и множество не найдёт даже её
саму.

## Задача 19. Свойство `readonly` и приватная изменяемость

Снаружи класс отдаёт неизменяемый список, а внутри хочет его пополнять.
Как так сделать и где тут типичная ошибка новичка?

```objc
@interface Playlist : NSObject
@property (nonatomic, copy, readonly) NSArray *songs;
- (void)addSong:(NSString *)song;
@end
```

**Разбор.** `readonly` означает «снаружи есть только геттер, сеттера нет».
Это правильное оформление: чужой код может прочитать `playlist.songs`, но
не подменит весь список и не полезет добавлять в него напрямую.

Ошибка новичка — отдать наружу **тот самый** внутренний `NSMutableArray`:

```objc
- (NSArray *)songs { return _songs; }   // _songs изменяемый!
```

Тип в объявлении — `NSArray *`, но фактически вернётся изменяемый объект.
Любой снаружи сможет привести его обратно к `NSMutableArray` и менять
твой внутренний список за спиной — инкапсуляция сломана. Правильно — внутри
держать `NSMutableArray`, а наружу отдавать **снимок**:

```objc
@implementation Playlist {
    NSMutableArray *_songs;   // своё поле: свой геттер у readonly-свойства
}                             // отключает автоматическое создание _songs
- (NSArray *)songs { return [_songs copy]; }
// ... init создаёт _songs, addSong: делает [_songs addObject:song]
@end
```

(Атрибут `copy` у `readonly`-свойства на геттер никак не влияет — он
касается только сеттера, а сеттера снаружи нет. Поэтому снимок в геттере
делаем руками.) А пополнять список — только через свой метод `addSong:`, который
работает с приватным `_songs` напрямую. Так класс полностью контролирует,
кто и когда меняет его данные. Это та же мысль, что в задачах 5 и 17:
не отдавай наружу изменяемое нутро, отдавай неизменяемый снимок.

## Задача 20. Что такое `self` в методе и зачем `[super init]`

```objc
- (instancetype)init {
    self = [super init];
    if (self) {
        _value = 100;
    }
    return self;
}
```

Объясни каждую строку: что такое `self`, что такое `super`, почему
результат `[super init]` присваивают обратно `self`.

**Разбор.** Это шаблон назначенного инициализатора, и его просят разобрать
очень часто.

- **`self`** — внутри любого метода это «текущий объект-получатель», тот,
  кому послали сообщение. Через `self` объект обращается к своим полям и
  шлёт сообщения сам себе.
- **`super`** — тот же самый объект `self`, но «глядя на него как на
  родителя»: сообщение через `super` ищет метод не в своём классе, а
  начиная с **родительского**. `[super init]` означает «пусть сначала
  родитель (`NSObject` и выше) настроит свою часть объекта».

Почему `self = [super init];`, а не просто `[super init];`? Потому что
`init` родителя **имеет право вернуть другой объект** или `nil`. Это редко,
но бывает (так устроены некоторые классы Foundation). Если родитель вернул
другой объект, дальше настраивать надо именно его, поэтому результат
кладут обратно в `self`. А `if (self)` страхует от случая, когда родитель
вернул `nil` (инициализация не удалась) — тогда мы не лезем настраивать
поля у несуществующего объекта и сразу вернём `nil`.

Порядок строго такой: **сначала родитель** (`[super init]`), **потом своя
настройка** (`_value = 100`). Наоборот нельзя — пока родитель не привёл
объект в порядок, трогать его рано. И в конце обязательно `return self;` —
без него инициализатор вернёт мусор. Рабочий пример этого шаблона —
`code/junior-04-alloc-init.m` из задачи 4.

> **Отличие от Си.** В Си не было ни `self`, ни `super` — была функция и
> переданные ей аргументы. Здесь объект знает сам себя (`self`) и умеет
> позвать «родительскую версию» метода (`super`) — это часть объектной
> модели, которой в чистом Си попросту нет.

## Что повторить перед собеседованием

Короткий чек-лист по этому разделу. Если на любой пункт отвечаешь
неуверенно — вернись к нужной задаче.

- Сообщение `nil`-получателю безопасно и даёт `0`/`nil`/`NO`; `nil`
  аргументом коллекции — краш (задачи 1, 7).
- Строки и числа сравнивают по содержимому: `isEqualToString:` /
  `isEqualToNumber:`, не `==` (задачи 2, 3).
- Объект рождается связкой `[[Класс alloc] init]`; `init` строится по
  шаблону `self = [super init]` … `return self` (задачи 4, 20).
- Строковые и коллекционные свойства объявляй с `copy`; наружу отдавай
  неизменяемый снимок, не внутренний mutable (задачи 5, 17, 19).
- `BOOL` — это `YES`/`NO`; не пихай в него произвольные числа и не
  сравнивай с `YES` напрямую (задача 6).
- Числа в коллекциях — только упакованные в `NSNumber` (`@5`, `@(x)`);
  отсутствие значения — `NSNull`, не `nil` (задачи 9, 10).
- Коллекцию нельзя менять во время `for-in` (задача 11).
- Метод выбирается по фактическому классу объекта — полиморфизм;
  `isKindOfClass:` учитывает наследование, `isMemberOfClass:` — нет
  (задачи 12, 13).
- Для `alloc`/`init` и фабрик возвращай `instancetype`, не `id`
  (задача 14).
- `delegate` всегда `weak` — иначе цикл удержания (задача 16).
