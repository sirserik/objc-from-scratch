# Глава 20. KVC и KVO

До сих пор мы добирались до данных объекта прямо: `acc.balance`,
`[acc setOwner:@"Серик"]`. Имя свойства было вписано в код, и компилятор
знал его заранее. А что, если имя свойства станет известно только во
время выполнения — придёт из формы, из конфигурации, из сетевого ответа?
В Си такое невозможно в принципе: поле структуры читается только по имени
прямо в исходнике. Objective-C даёт ровно эту возможность из коробки —
через два механизма, выросших из runtime главы 14.

Первый — **KVC** (Key-Value Coding, кодирование «ключ-значение»): доступ
к свойствам по строковому имени. Второй — **KVO** (Key-Value Observing,
наблюдение «ключ-значение»): автоматическое уведомление о том, что
свойство изменилось. KVO стоит на KVC, а под капотом — на той самой
подмене `isa`, которую мы разобрали в главе 14. Построим оба с нуля.

## Что мы сделаем

- Прочитаем и запишем свойство по строковому имени: `valueForKey:` и
  `setValue:forKey:`.
- Поймём, что KVC ищет под капотом (метод доступа -> голый ivar).
- Пройдём по вложенным объектам через `valueForKeyPath:` (`@"address.city"`).
- Применим KVC к массиву: соберём значения и посчитаем операторами
  `@count`, `@sum`, `@avg`, `@max`.
- Увидим, как KVC сам упаковывает примитивы в `NSNumber` (привет главе 16).
- Подпишемся на изменение свойства через `addObserver:forKeyPath:...`.
- Своими глазами увидим isa-swizzling: после подписки `isa` объекта
  меняется на сгенерированный подкласс.
- Докажем, что изменение через сеттер уведомление шлёт, а прямое
  присваивание ivar — нет.
- Разберём ручные уведомления и `+automaticallyNotifiesObserversForKey:`.
- Снимем наблюдателя (`removeObserver:`) и узнаем, что будет, если
  забыть или снять дважды.

## Часть 1. KVC — доступ по строковому имени

### Разбираем задачу руками

Представь форму редактирования профиля. Полей десятки: имя, город,
телефон, баланс. Писать на каждое поле по строчке `obj.name = ...`,
`obj.city = ...` — скучно и негибко: добавили поле — правь код в трёх
местах. Хочется иначе: пробежать по словарю `@{ @"name": @"Серик",
@"balance": @1500.50 }` и присвоить каждое значение свойству с
**таким же именем**. Имя свойства тут — обычная строка, известная только
в момент выполнения.

Вот для этого и есть KVC. Его сердце — два метода, которые `NSObject`
даёт **любому** объекту бесплатно:

- `setValue:forKey:` — «запиши это значение в свойство с этим именем»;
- `valueForKey:` — «верни значение свойства с этим именем».

### Шаг 1. Читаем и пишем свойство по имени

Заведём класс `Account` с владельцем и балансом — самый обычный, без
единой строчки «под KVC». Включать ничего не нужно: способность работать
по ключу встроена в `NSObject`.

```objc
@interface Account : NSObject
@property (nonatomic, copy) NSString *owner;
@property (nonatomic) double balance;      /* примитив double */
@end

@implementation Account
@end
```

Теперь обращаемся к свойствам не через точку, а по строке:

```objc
Account *acc = [[Account alloc] init];

[acc setValue:@"Серик" forKey:@"owner"];
[acc setValue:@1500.50 forKey:@"balance"];   /* @1500.50 — NSNumber */

NSString *owner = [acc valueForKey:@"owner"];
id balance      = [acc valueForKey:@"balance"];

NSLog(@"владелец = %@", owner);
NSLog(@"баланс   = %@  (класс %@)", balance, [balance class]);
NSLog(@"баланс как double = %.2f", [balance doubleValue]);
```

Разберём по частям.

- `setValue:forKey:` принимает **объект-значение** и **строку-ключ**.
  Первый аргумент всегда объект (`id`), поэтому число пришлось завернуть
  в `NSNumber` литералом `@1500.50`. Ключ — обычная `NSString`.
- `valueForKey:` принимает ключ-строку и возвращает `id` — объект. Для
  `owner` это `NSString`, как и было. А вот для `balance` интереснее: само
  свойство — примитив `double`, объектом не является. KVC **сам** обернул
  его в `NSNumber`, чтобы вернуть как `id`. Поэтому переменная `balance`
  у нас типа `id`, а не `double`.
- `[balance doubleValue]` распаковывает `NSNumber` обратно в `double` —
  ровно как в главе 16.

Запускаем (`code/20-kvc.m`):

```text
владелец = Серик
баланс   = 1500.5  (класс __NSCFNumber)
баланс как double = 1500.50
через свойство: owner=Серик balance=1500.50
```

Смотри на вторую строку, в скобках: класс значения — `__NSCFNumber`.
Это внутренняя реализация `NSNumber`. То есть `valueForKey:@"balance"`
действительно вернул объект-обёртку, хотя в классе `balance` объявлен
как голый `double`. Это **автоупаковка KVC** (см. главу 16): примитивы
`int`, `double`, `BOOL`, C-структуры KVC на входе распаковывает, а на
выходе упаковывает в `NSNumber`/`NSValue`. Тебе не нужно делать это
руками — главное помнить, что `valueForKey:` для числового свойства
вернёт именно `NSNumber`, а не `double`.

> **Отличие от Си.** В Си поле структуры читается только по имени,
> вписанному в исходник: `acc.balance`. «Дай мне поле, имя которого лежит
> в переменной-строке» там нельзя — после компиляции от имён полей не
> остаётся ничего, спрашивать некого. Чтобы такое сделать в Си, пришлось
> бы вручную строить свою таблицу «строка -> смещение поля». В Objective-C
> KVC даёт это бесплатно: имена свойств живут в runtime, и `valueForKey:`
> находит нужное во время выполнения.

### Шаг 2. Что KVC делает под капотом

Откуда `valueForKey:@"owner"` знает, как взять значение? Он не лезет
сразу в память — он действует по строгому порядку поиска. Для чтения
ключа `key` (упрощённо; полный порядок — в Key-Value Coding Programming
Guide, раздел Accessor Search Patterns):

```text
[obj valueForKey:@"balance"]
   |
   1. ищет геттер: -getBalance, -balance, -isBalance, -_balance
   |      нашёл -> зовёт его, результат (если примитив) упаковывает
   2. нет геттера? и разрешён прямой доступ к ivar?
   |      ищет поле: _balance, потом _isBalance, balance, isBalance
   |      нашёл -> читает поле напрямую, упаковывает
   3. ничего не нашли -> -valueForUndefinedKey: -> исключение
                          NSUnknownKeyException
```

Для записи `setValue:forKey:` зеркально: сначала ищет сеттер
`-setBalance:` (или `-_setBalance:`), и только если его нет (и разрешён прямой доступ) — пишет
прямо в ivar `_balance`. Разрешение прямого доступа к ivar даёт метод
класса `+accessInstanceVariablesDirectly` — по умолчанию он возвращает
`YES`.

Шаг с ivar легко показать. Заведём класс с **голым полем без свойства** —
ни геттера, ни сеттера у него нет:

```objc
@interface Box : NSObject {
    NSString *_secret;                     /* только ivar */
}
@end

@implementation Box
@end
```

И всё равно достучимся до `_secret` по ключу `"secret"`:

```objc
Box *box = [[Box alloc] init];
[box setValue:@"пароль" forKey:@"secret"];   /* пишет прямо в _secret */
NSLog(@"секрет из ivar = %@", [box valueForKey:@"secret"]);
```

В выводе:

```text
секрет из ivar = пароль
```

Сеттера нет, а запись прошла — KVC сам нашёл ivar `_secret` по ключу
`secret` (отбросив подчёркивание) и записал в него. Это и есть третий шаг
алгоритма. Полезно для отладки, но в обычном коде на это не опираются:
лезть в чужие приватные поля по строке — плохая привычка.

### Шаг 3. Key path — путь сквозь вложенные объекты

Ключ адресует одно свойство. А если нужно свойство **внутри** свойства?
Например, у человека есть адрес (`Address`), а у адреса — город. Для
таких цепочек есть **key path** (путь по ключам): ключи, разделённые
точками, и метод `valueForKeyPath:`.

```objc
@interface Address : NSObject
@property (nonatomic, copy) NSString *city;
@property (nonatomic, copy) NSString *street;
@end

@interface Person : NSObject
@property (nonatomic, copy) NSString *name;
@property (nonatomic, strong) Address *address;   /* вложенный объект */
@end
```

Собираем человека с адресом и читаем сквозь точку:

```objc
Person *p = [[Person alloc] init];
p.name    = @"Серик";
p.address = addr;          /* addr.city = @"Алматы", addr.street = @"Абая" */

NSLog(@"name           = %@", [p valueForKeyPath:@"name"]);
NSLog(@"address.city   = %@", [p valueForKeyPath:@"address.city"]);
NSLog(@"address.street = %@", [p valueForKeyPath:@"address.street"]);
```

```text
name           = Серик
address.city   = Алматы
address.street = Абая
```

Точка в `@"address.city"` читается как «возьми у `p` свойство `address`,
а у него — свойство `city`». KVC раскручивает путь слева направо: сначала
`valueForKey:@"address"`, потом у результата `valueForKey:@"city"`. Цепочка
может быть любой длины. Заметь: `valueForKeyPath:` с обычным ключом без
точки (`@"name"`) работает как `valueForKey:` — путь из одного звена.

> **Отличие от Си.** В Си обращение к вложенному полю — это
> `p.address->city`, и весь путь зашит в исходник на этапе компиляции.
> Строка `@"address.city"`, по которой во время выполнения находят
> вложенное поле, в Си немыслима без собственного парсера и таблиц.
> Здесь это одна строка и один вызов.

### Шаг 4. KVC и коллекции

KVC раскрывается во всю силу на массивах. Два разных приёма.

**Первый: `valueForKey:` на массиве собирает значения.** Если послать
`valueForKey:` не одиночному объекту, а `NSArray`, он применит ключ к
**каждому** элементу и вернёт массив результатов. Возьмём корзину
товаров. `Product` — простой класс со свойствами `NSString *title` и
`double price` и фабричным методом `+title:price:`, который создаёт и
заполняет товар (целиком — в `code/20-keypath.m`):

```objc
NSArray<Product *> *cart = @[
    [Product title:@"Книга"    price:3500.0],
    [Product title:@"Наушники" price:9900.0],
    [Product title:@"Чехол"    price:1200.0],
];

NSArray *titles = [cart valueForKey:@"title"];
NSLog(@"названия = %@", titles);
```

```text
названия = (
    "\U041a\U043d\U0438\U0433\U0430",
    "\U041d\U0430\U0443\U0448\U043d\U0438\U043a\U0438",
    "\U0427\U0435\U0445\U043e\U043b"
)
```

Из массива из трёх `Product` мы одной строкой достали массив их названий.
(Кириллица в выводе показана как `\U....` — так `NSArray` печатает
вложенные строки в своём `description`; сами строки целые, это лишь форма
лога. Если хочется читаемо — склей массив через
`componentsJoinedByString:`, как мы делали в главе 12.) Удобно для
«вытащить из списка объектов список одного поля».

С числовым свойством то же самое, и вот тут видно кое-что интересное:

```objc
NSArray *prices = [cart valueForKeyPath:@"price"];
NSLog(@"цены     = %@", prices);
```

```text
цены     = (
    3500,
    9900,
    1200
)
```

Свойство `price` объявлено как `double` — примитив, не объект. Но в
массив попали объекты: KVC **сам завернул** каждое число в `NSNumber`,
потому что в коллекции примитив положить нельзя. Это общее правило KVC:
на границе он упаковывает примитивы в `NSNumber`, а структуры — в
`NSValue` (обе обёртки мы разбирали в главе 16). Именно поэтому чуть ниже
`@sum.price` вернёт нам `NSNumber`, а не `double`.

**Второй: операторы коллекций.** Это особые ключи, начинающиеся с `@`:
`@count`, `@sum`, `@avg`, `@max`, `@min`, `@distinctUnionOfObjects` и
другие. Они считают агрегат по всему массиву. Синтаксис:
`@оператор.ключ` (кроме `@count`, которому ключ не нужен).

```objc
NSNumber *count = [cart valueForKeyPath:@"@count"];
NSNumber *sum   = [cart valueForKeyPath:@"@sum.price"];
NSNumber *avg   = [cart valueForKeyPath:@"@avg.price"];
NSNumber *max   = [cart valueForKeyPath:@"@max.price"];
NSNumber *min   = [cart valueForKeyPath:@"@min.price"];

NSLog(@"@count      = %@", count);
NSLog(@"@sum.price  = %@", sum);
NSLog(@"@avg.price  = %.2f", [avg doubleValue]);
NSLog(@"@max.price  = %@", max);
NSLog(@"@min.price  = %@", min);
```

```text
@count      = 3
@sum.price  = 14600
@avg.price  = 4866.67
@max.price  = 9900
@min.price  = 1200
```

Разбор операторов:

- `@"@count"` — сколько элементов в массиве. Ключ после точки не нужен:
  считаем сами объекты, а не их поле.
- `@"@sum.price"` — сложить значения свойства `price` всех элементов.
  `3500 + 9900 + 1200 = 14600`.
- `@"@avg.price"` — среднее значение `price`. `14600 / 3 ≈ 4866.67`.
- `@"@max.price"` / `@"@min.price"` — наибольшее и наименьшее значение
  `price`.

Все операторы возвращают **объект**, а не голое число: `@count` — это
`NSNumber`, `@sum` и `@avg` по нашим экспериментам приходят как
`NSDecimalNumber` (подкласс `NSNumber`), а `@max`/`@min` возвращают само
значение свойства — здесь упакованный `NSNumber`. Поэтому среднее мы
печатаем через `[avg doubleValue]`. Это та же
автоупаковка: свойство `price` — `double`, а наружу приходит число-объект.

Запусти `code/20-keypath.m` целиком — увидишь и key path, и оба приёма
с коллекциями.

### Зачем вообще KVC

KVC — не самоцель, это фундамент. На нём стоит многое: обобщённый код
(заполнение форм, сериализация объекта в словарь и обратно, маппинг JSON
на модель — всё это перебор ключей строками); `NSPredicate` и сортировка
(фильтры вида `@"price > 1000"` читают свойства через KVC); Cocoa bindings
на macOS; и главное для нас — **KVO**, наблюдение за изменениями, к
которому мы переходим. Без KVC оно бы не работало.

## Часть 2. KVO — наблюдение за изменением

### Разбираем задачу руками

Баланс счёта меняется — а где-то на экране висит его сумма, которую надо
обновить. Можно после каждого изменения вручную звать «обнови экран», но
изменений много, и легко забыть в одном месте. Хочется наоборот: один раз
сказать «следи за `balance`» — и пусть уведомляют при любом изменении,
кто бы его ни сделал. Это и есть KVO. Три действия:

1. **подписаться**: `addObserver:forKeyPath:options:context:`;
2. **получать уведомления** в методе `observeValueForKeyPath:ofObject:change:context:`;
3. **обязательно отписаться**: `removeObserver:forKeyPath:context:`.

### Шаг 5. Подписываемся и ловим изменение

Наблюдаемый объект — наш `Account`. Добавим ему один «нечестный» метод
(зачем — увидим на шаге 7):

```objc
@interface Account : NSObject
@property (nonatomic) double balance;
- (void)setBalanceSneaky:(double)value;
@end

@implementation Account
- (void)setBalanceSneaky:(double)value {
    _balance = value;          /* прямое присваивание полю, в обход сеттера */
}
@end
```

Наблюдатель — отдельный класс, который переопределяет метод-приёмник
уведомлений. Этот метод объявлен в `NSObject`, так что просто
переопределяем его:

```objc
@interface Watcher : NSObject
@end

@implementation Watcher
- (void)observeValueForKeyPath:(NSString *)keyPath
                      ofObject:(id)object
                        change:(NSDictionary<NSKeyValueChangeKey, id> *)change
                       context:(void *)context {
    if (context == &kBalanceContext) {
        NSLog(@"  [наблюдатель] %@: %@ -> %@",
              keyPath,
              change[NSKeyValueChangeOldKey],
              change[NSKeyValueChangeNewKey]);
    } else {
        [super observeValueForKeyPath:keyPath ofObject:object
                               change:change context:context];
    }
}
@end
```

Разберём параметры этого метода — runtime зовёт его при каждом замеченном
изменении:

- `keyPath` — какой ключ изменился (`@"balance"`).
- `object` — у какого объекта.
- `change` — словарь с подробностями. Ключи в нём — константы:
  `NSKeyValueChangeOldKey` (старое значение) и `NSKeyValueChangeNewKey`
  (новое). Значения там — объекты, поэтому `double` приходит как
  `NSNumber` (снова автоупаковка).
- `context` — тот самый «маркер», который мы передали при подписке.
  Сравнивая его, отличаем нашу подписку от чужих.

Теперь подписка и изменения в `main`:

```objc
Account *acc = [[Account alloc] init];
Watcher *w   = [[Watcher alloc] init];

[acc addObserver:w
      forKeyPath:@"balance"
         options:NSKeyValueObservingOptionNew | NSKeyValueObservingOptionOld
         context:&kBalanceContext];

acc.balance = 100.0;                         /* через сеттер */
[acc setValue:@250.0 forKey:@"balance"];     /* через KVC-сеттер */
[acc setBalanceSneaky:999.0];                /* напрямую в ivar */

[acc removeObserver:w forKeyPath:@"balance" context:&kBalanceContext];
```

Разберём подписку `addObserver:forKeyPath:options:context:`:

- `addObserver:` — кто будет получать уведомления (наш `w`). Важно:
  объект-наблюдатель KVO **не удерживает** — за временем его жизни следишь
  ты сам.
- `forKeyPath:` — за каким ключом следим. Можно и key path (`@"address.city"`).
- `options:` — что положить в словарь `change`. Мы объединили `|` две
  опции из `NSKeyValueObservingOptions`: `...OptionNew` (класть новое
  значение) и `...OptionOld` (класть старое). Есть ещё `...OptionInitial`
  (прислать уведомление сразу при подписке) и `...OptionPrior` (слать
  ещё и перед изменением).
- `context:` — произвольный указатель-маркер. Мы передаём адрес статической
  переменной `kBalanceContext` — он уникален во всей программе. В приёмнике
  сверяем `context == &kBalanceContext` и точно знаем, что это наша
  подписка, а не чья-то ещё.

Где взялся `kBalanceContext` — это просто статическая переменная на
уровне файла, её адрес и служит уникальным маркером:

```objc
static char kBalanceContext;   /* значение неважно — важен его адрес */
```

### Шаг 6. Запускаем и видим isa-swizzling

Перед подпиской и сразу после неё распечатаем две вещи: что отвечает
объект на `-class` и что лежит в его настоящем `isa` (через
`object_getClass` из главы 14):

```objc
NSLog(@"до подписки:  -class=%@  настоящий isa=%s",
      [acc class], class_getName(object_getClass(acc)));
/* ...addObserver... */
NSLog(@"после подписки: -class=%@  настоящий isa=%s",
      [acc class], class_getName(object_getClass(acc)));
```

Запускаем `code/20-kvo.m` целиком:

```text
до подписки:  -class=Account  настоящий isa=Account
после подписки: -class=Account  настоящий isa=NSKVONotifying_Account
--- меняем через сеттер ---
  [наблюдатель] balance: 0 -> 100
  [наблюдатель] balance: 100 -> 250
--- меняем напрямую через ivar ---
итоговый баланс = 999.00
```

Вот он, фокус из главы 14, вживую. До подписки и `-class`, и настоящий
`isa` — это `Account`. **После** `addObserver:` `-class` по-прежнему
отвечает `Account`, а настоящий `isa` стал `NSKVONotifying_Account` —
класса, которого мы не писали.

Что произошло. В момент подписки runtime:

1. на лету создал **динамический подкласс** `Account` с именем
   `NSKVONotifying_Account` (см. главу 14, isa-swizzling);
2. переопределил в нём сеттер `setBalance:` так, что тот вокруг настоящего
   присваивания шлёт уведомления `willChange.../didChange...`;
3. переопределил `-class`, чтобы он **врал** и возвращал прежний `Account`
   — иначе твой код запутался бы, увидев незнакомый класс;
4. **подменил `isa`** объекта `acc` на этот новый подкласс.

Объект снаружи остался «тем же `Account`», но его реальный `isa` теперь
ведёт на сгенерированный подкласс с «говорящими» сеттерами. Именно
поэтому KVO «бесплатно» ловит изменения: каждое присваивание через сеттер
проходит через переопределённый метод подкласса.

> **Отличие от Си.** В Си, чтобы заметить изменение переменной, пришлось
> бы оборачивать каждое присваивание своей функцией-«сеттером» и вручную
> звать всех заинтересованных — везде, во всём коде, не забыв ни одного
> места. KVO делает это само, подменив класс объекта на лету
> (isa-swizzling, глава 14). Переменная как была полем — так и осталась,
> а наблюдение появилось из воздуха. В Си «слежки за переменной» нет и
> взяться ей неоткуда.

### Шаг 7. Сеттер уведомляет, прямой ivar — нет

Теперь главный урок KVO. Посмотри на вывод ещё раз: уведомления
`[наблюдатель]` пришли **дважды** — на `acc.balance = 100.0` и на
`[acc setValue:@250.0 forKey:@"balance"]`. Оба пути идут через сеттер
`setBalance:` (KVC-запись тоже зовёт сеттер), а сеттер у нас теперь —
переопределённый, «говорящий».

А вот на `[acc setBalanceSneaky:999.0]` уведомления **нет**. Хотя баланс
честно стал 999 (последняя строка это подтверждает), наблюдатель промолчал.
Почему: `setBalanceSneaky:` пишет прямо в поле `_balance`, минуя сеттер.
Подменённый класс ничего не оборачивал вокруг прямого доступа к ivar —
ему просто негде вклиниться. KVO видит изменения **только через сеттер**.

Отсюда железное правило: **меняй наблюдаемые свойства через сеттер или
`setValue:forKey:`, никогда не присваивай ivar напрямую** (внутри своих
методов — `self.balance = ...`, а не `_balance = ...`). Иначе наблюдатели
не узнают об изменении, и на экране останется старое значение. Это одна
из самых частых и коварных ошибок с KVO.

### Шаг 8. Ручные уведомления и automaticallyNotifies...

Автоматику KVO мы видели: подменённый сеттер сам шлёт пару
«перед/после». Иногда нужно слать уведомления **вручную** — например,
свойство вычисляемое и сеттера у него нет, или одно изменение должно
уведомить сразу о нескольких ключах. Для этого есть пара методов:

```objc
[self willChangeValueForKey:@"balance"];   /* «сейчас изменю» */
_balance = value;                          /* собственно изменение */
[self didChangeValueForKey:@"balance"];    /* «изменил» */
```

`willChangeValueForKey:` запоминает старое значение, `didChangeValueForKey:`
берёт новое и шлёт уведомление наблюдателям. Сравнивать KVO не станет:
даже если значение не поменялось, наблюдатель получит уведомление
«5 -> 5» (мы проверили — так же ведёт себя и автоматический сеттер, если
присвоить то же число). Хочешь молчать при равных значениях — проверь
это сам до `willChange...`. Между парой — само изменение. Звать методы
надо парой и в этом порядке.

Чтобы автоматика не сработала вдобавок к ручной (двойное уведомление),
для такого ключа её отключают, переопределив метод класса:

```objc
+ (BOOL)automaticallyNotifiesObserversForKey:(NSString *)key {
    if ([key isEqualToString:@"balance"]) {
        return NO;          /* для balance уведомляем вручную */
    }
    return [super automaticallyNotifiesObserversForKey:key];
}
```

Вернул `NO` для ключа — runtime больше не оборачивает его сеттер сам, и
вся ответственность на твоих `willChange.../didChange...`. Для всех
остальных ключей возвращаем решение `super` (по умолчанию `YES`). В
обычной жизни автоматики хватает; ручные уведомления — для зависимых и
вычисляемых свойств.

### Шаг 9. removeObserver — обязательно

Последняя строка примера — не формальность:

```objc
[acc removeObserver:w forKeyPath:@"balance" context:&kBalanceContext];
```

Документация Apple требует снимать наблюдателя, пока оба объекта ещё
живы: KVO не удерживает наблюдателя. Долгие годы нарушение этого правила
кончалось падением: `Watcher` уничтожен, подписка осталась, и при
следующем изменении `balance` уведомление уходило по **мёртвому адресу**.

По нашим экспериментам на свежей macOS (26) падения уже нет: Foundation
сам обнуляет ссылку на умершего наблюдателя, и уведомление просто никуда
не уходит. Но это недокументированное поведение, на старых системах оно
другое, а сама запись о подписке так и висит на объекте. Поэтому правило
не меняется: подписался — отпишись.

Снимай подписку там, где это логично: для долгоживущих объектов — в
`dealloc` наблюдателя; в нашем коротком примере — прямо перед концом,
пока `acc` и `w` оба на месте. Парность простая: на каждый `addObserver:`
ровно один `removeObserver:`. А вот снять несуществующую подписку —
гарантированная ошибка на любой системе, исключение `NSRangeException`:

```text
Cannot remove an observer <Watcher 0x...> for the key path "balance"
from <Account 0x...> because it is not registered as an observer.
```

Так что не отписывайся дважды.

### А как в Swift: NSKeyValueObservation

У классического KVO есть болевые точки: строковый ключ (опечатку поймаешь
только в рантайме), приёмник в отдельном методе вдали от подписки, ручной
`removeObserver:`. В Swift их убрали: метод `observe(_:options:changeHandler:)`
принимает проверяемый компилятором key path (`\.balance`) и замыкание, а
возвращает объект `NSKeyValueObservation` — пока он жив, подписка
действует, а при его уничтожении снимается сама. Механика под ним — тот
же isa-swizzling.

В Objective-C такого блочного API у Foundation **нет** (в заголовках SDK
`NSKeyValueObservation` не встречается): здесь KVO — это только
`addObserver:forKeyPath:options:context:` и `observeValueForKeyPath:...`,
которые мы разобрали. Блочные обёртки над ними в проектах на Objective-C
пишут сами или берут готовые сторонние библиотеки.

## Полная программа

Три самостоятельных файла, каждый собирается и запускается отдельно:

- `code/20-kvc.m` — `valueForKey:`/`setValue:forKey:`, доступ к ivar,
  автоупаковка в `NSNumber`.
- `code/20-keypath.m` — `valueForKeyPath:`, key path сквозь вложенные
  объекты, KVC на коллекциях, операторы `@count`/`@sum`/`@avg`/`@max`.
- `code/20-kvo.m` — подписка, isa-swizzling, разница «сеттер vs ivar»,
  снятие наблюдателя.

## Проверяем

Каждый файл собирается одной командой (подставь имя):

```text
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
      code/20-kvc.m -o t && ./t
```

Все три собираются **без предупреждений** под `-Wall -Wextra`. Ожидаемый
вывод приведён по ходу главы (дата, имя программы и числа в скобках будут
свои). Контрольные точки:

- в `20-kvc.m` класс значения `balance` — `__NSCFNumber` (упаковка);
- в `20-kvo.m` после подписки настоящий `isa` — `NSKVONotifying_Account`,
  а `-class` всё ещё `Account`;
- в `20-kvo.m` ровно **два** уведомления (на оба сеттера) и **ни одного**
  на `setBalanceSneaky:`.

## Частые ошибки

- **Меняешь ivar напрямую — наблюдатель молчит.** `_balance = x` в обход
  сеттера KVO не заметит. Внутри методов пиши `self.balance = x` или
  `setValue:forKey:`.
- **Забыл `removeObserver:`.** Наблюдатель умер, подписка осталась. На
  старых системах следующее изменение слало сообщение мёртвому объекту и
  роняло программу; на свежей macOS, по нашим экспериментам, уже нет, но
  документация по-прежнему требует отписки. Парность строгая: один
  `addObserver:` — один `removeObserver:`.
- **Отписался дважды или без подписки.** Исключение `NSRangeException`.
  Снимай подписку ровно один раз.
- **Не сверяешь `context`.** Если на объект подписан и твой код, и
  суперкласс, без проверки `context` поймаешь чужие уведомления. Всегда
  передавай уникальный `context` и сверяй его, а чужое отдавай `super`.
- **Опечатка в ключе.** `@"balanse"` соберётся, но в рантайме даст
  `setValue:forUndefinedKey:` -> исключение `NSUnknownKeyException`
  («this class is not key value coding-compliant for the key balanse»):
  ключи — строки, компилятор их не проверяет.
- **Ждёшь `double`, а пришёл `NSNumber`.** И из `valueForKey:`, и из
  словаря `change` числа приходят упакованными — распаковывай через
  `doubleValue`/`intValue`.

## Упражнения

1. Добавь в `Account` свойство `NSString *currency` и в `20-kvc.m`
   заполни оба свойства, пробежав словарём
   `@{ @"owner": @"Серик", @"currency": @"KZT" }` в цикле `for...in` по
   его ключам, вызывая `setValue:forKey:`. Это и есть «обобщённое
   заполнение формы».
2. В `20-keypath.m` добавь оператор `@"@distinctUnionOfObjects.title"` и
   посмотри, чем он отличается от `valueForKey:@"title"` (подсказка:
   убирает дубликаты). Добавь в корзину второй товар «Книга» и сравни.
3. Сделай в `Person` свойство-массив `friends` (тоже `Person`) и достань
   `valueForKeyPath:@"friends.name"` — массив имён друзей.
4. В `20-kvo.m` добавь к подписке опцию `NSKeyValueObservingOptionInitial`
   и убедись, что уведомление приходит сразу при `addObserver:`, ещё до
   первого изменения.
5. Сделай класс `Thermostat` с вычисляемой температурой и **ручными**
   уведомлениями (`willChangeValueForKey:`/`didChangeValueForKey:` +
   `+automaticallyNotifiesObserversForKey:` -> `NO`). Подпишись и проверь,
   что уведомление приходит ровно один раз.
6. Намеренно продублируй в `20-kvo.m` строку `removeObserver:` — отпишись
   дважды. Поймай падение и прочитай текст исключения `NSRangeException` —
   потом узнаешь такую ошибку сразу. Затем убери обе отписки, а
   наблюдателя `w` заверни в отдельную область видимости `{ ... }`, чтобы
   он умер раньше `acc`, и поменяй баланс: придёт ли уведомление и упадёт
   ли программа на твоей системе?

## Что мы получили

Мы научили программу работать со свойствами по их строковому имени.
**KVC** дал чтение и запись по ключу (`valueForKey:`/`setValue:forKey:`),
проход сквозь вложенные объекты (`valueForKeyPath:`, `@"address.city"`),
агрегаты по коллекциям (`@count`, `@sum`, `@avg`, `@max`) и бесплатную
упаковку примитивов в `NSNumber`. На нём стоят формы, сериализация,
`NSPredicate` и сортировка — весь обобщённый код, которому имя свойства
известно лишь во время выполнения.

**KVO** добавил автоматическое наблюдение: подписался на ключ — и
получаешь уведомления при каждом изменении через сеттер. Под капотом мы
своими глазами увидели механику главы 14: runtime создаёт динамический
подкласс `NSKVONotifying_Account`, подменяет `isa` объекта и переопределяет
сеттеры. Отсюда два правила KVO: менять только через сеттер (иначе
изменение незаметно) и снимать наблюдателя ровно один раз.

В Си ничего подобного нет: там поле читается лишь по имени из исходника, а
следить за переменной пришлось бы вручную в каждой точке кода. Здесь и
доступ по строке, и наблюдение выросли из одной идеи — живого runtime, где
объект знает свой класс, а класс можно подменить на лету. Дальше поднимемся
к многопоточности и увидим, как несколько потоков делят одни объекты.
