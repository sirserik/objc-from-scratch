# Приложение E. Задачи собеседования: Middle

Junior-раздел проверял, помнишь ли ты механику: сообщения, `nil`,
свойства, простой ARC. Middle-уровень спрашивает иначе — не «что делает
эта строка», а «что произойдёт с памятью», «что выведет этот код и
почему», «как ты спроектируешь вот это». Здесь почти не бывает ответа в
одну строку: за каждым вопросом стоит модель владения, поведение runtime
или контракт класса.

Формат тот же, что в Junior-разделе. Каждая задача — это **условие**,
потом **подумай сам** (остановись и попробуй ответить), потом **разбор**
по правилам Objective-C и, где задача про код, — **компилируемое
решение** в `code/middle-NN-имя.m`. Каждый показанный вывод реальный:
файлы собраны и запущены, `dealloc`-логи настоящие. Дата, имя программы и
число в квадратных скобках, которые `NSLog` печатает в начале строки,
здесь убраны — у тебя они будут свои.

Собрать и запустить любой файл:

```text
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/middle-01-retain-cycle.m -o /tmp/t && /tmp/t
```

Идём от простого к сложному: сперва блоки и память, потом копирование,
протоколы и категории, в конце — KVC/KVO и контракты `NSCopying`,
`isEqual:`/`hash`.

## Задача 1. Что выведет блок: захват по значению и `__block`

**Условие.** Перед тобой три фрагмента. Скажи, что напечатает каждый.

```objc
int x = 10;
void (^plain)(void) = ^{ NSLog(@"%d", x); };
x = 99;
plain();                       // (1) ?

__block int y = 10;
void (^shared)(void) = ^{ NSLog(@"%d", y); };
y = 99;
shared();                      // (2) ?

NSMutableArray *blocks = [NSMutableArray array];
for (int i = 0; i < 3; i++) {
    [blocks addObject:^{ NSLog(@"%d", i); }];
}
for (void (^b)(void) in blocks) { b(); }   // (3) ?
```

**Подумай сам.** Когда блок «снимает» значение переменной — в момент
создания или в момент вызова?

**Разбор.** Обычный захват фиксирует **копию значения в момент создания
блока** (глава 12). Дальнейшие изменения переменной блок не видит.

- (1) `plain` захватил `x` равным `10`. Присваивание `x = 99` идёт уже
  после создания блока — на захваченную копию оно не влияет. Печатает
  **`10`**.
- (2) `__block` меняет природу захвата: `y` становится **общей ячейкой**,
  на которую смотрят и внешний код, и блок. К моменту вызова `shared` в
  ячейке лежит `99`. Печатает **`99`**.
- (3) Каждая итерация создаёт новый блок и захватывает **своё** значение
  `i` на тот момент: `0`, `1`, `2`. Печатает **`0 1 2`**.

Третий пункт — частая ловушка для тех, кто пришёл из языков, где замыкание
в цикле захватывает переменную «по ссылке» и все блоки потом видят
финальное значение. В Objective-C без `__block` каждый блок держит свою
копию. Сделай `i` объявленным как `__block` — и все три блока напечатают
одно и то же финальное значение цикла.

**Решение:** `code/middle-02-block-capture.m`.

```text
plain видит x = 10
shared видит y = 99
блок помнит i = 0
блок помнит i = 1
блок помнит i = 2
```

## Задача 2. `weak` после смерти объекта и ловушка `unsafe_unretained`

**Условие.** Объект создан во вложенном блоке и умирает на выходе из него.
Снаружи на него смотрит `__weak`-ссылка. Что напечатают две последние
строки — и что было бы, объяви мы ссылку `unsafe_unretained`?

```objc
__weak Ticket *weakRef = nil;
@autoreleasepool {
    Ticket *t = [[Ticket alloc] init];
    t.code = @"A-17";
    weakRef = t;
}   // t умирает здесь
NSLog(@"%@", weakRef);                 // ?
NSLog(@"%lu", (unsigned long)weakRef.code.length);  // ?
```

**Подумай сам.** Что лежит в `weakRef` после смерти объекта — мусор, `nil`
или старый адрес?

**Разбор.** `weak` — это ссылка-наблюдатель: она не удерживает объект, а
когда тот умирает, ARC **сам обнуляет** её в `nil` (глава 13). Поэтому
слабая ссылка либо показывает живой объект, либо честный `nil` — но
никогда не висячий указатель.

- `NSLog(@"%@", weakRef)` после смерти `t` печатает **`(null)`**.
- `weakRef.code.length` — это сообщение к `nil`. В Objective-C сообщение к
  `nil` безопасно и возвращает «нулевое» значение, для числа — **`0`**.

Будь ссылка `unsafe_unretained` (или старое свойство `assign`), всё иначе:
она **не обнуляется**. После смерти объекта она осталась бы указывать на
освобождённую память — висячий указатель. Первая же `NSLog(@"%@", ...)`
по нему — обращение к мёртвому объекту, неопределённое поведение: мусор
или падение. Правило простое: нужна необременяющая ссылка «вверх» или на
делегата — бери `weak`, а не `unsafe_unretained`, если только тебе не
важна каждая наносекунда и ты не доказал, что объект переживёт ссылку.

**Решение:** `code/middle-03-weak-nil.m`.

```text
объект жив:  weakRef.code = A-17
dealloc Ticket (A-17)
объект мёртв: weakRef = (null)
сообщение к nil безопасно: длина = 0
```

Строка `dealloc Ticket (A-17)` встала ровно на закрывающей скобке
вложенного блока — объект умер там, и сразу после слабая ссылка стала
`nil`.

## Задача 3. Найди утечку: команда и игроки

**Условие.** Команда владеет игроками (сильно держит их в массиве), а
каждый игрок ссылается на свою команду обратной ссылкой. Найди ошибку,
из-за которой `dealloc` не сработает, и почини её.

```objc
@interface Player : NSObject
@property (nonatomic, copy) NSString *name;
@property (nonatomic, strong) Team *team;     // ← подозрительно
@end

@interface Team : NSObject
@property (nonatomic, strong) NSMutableArray<Player *> *players;
@end
```

**Подумай сам.** Кто кого держит и где замыкается кольцо?

**Разбор.** Считаем сильные ссылки. `Team.players` сильно держит каждого
`Player` — это правильно, команда владеет составом. Но `Player.team`
объявлен `strong` — игрок тоже сильно держит команду. Получается кольцо:
команда → игрок → команда. Когда снаружи на оба объекта ссылок не
останется, их счётчики не дойдут до нуля, `dealloc` не сработает —
классическая утечка (глава 13).

Чинить надо ту ссылку, которая **не владеет по смыслу**. Команда владеет
игроком — `Team.players` оставляем `strong`. Игрок командой не владеет,
лишь смотрит «вверх» — значит `Player.team` должно быть **`weak`**. Меняем
один атрибут, и кольцо разорвано:

```objc
@property (nonatomic, weak) Team *team;   // вверх не владеем
```

Это та же тройка случаев, что и в главе 13: `parent ↔ child`,
`объект ↔ блок`, `объект ↔ delegate`. Лечение всегда одно — одну из двух
ссылок сделать слабой, и слабой делает ту, что «вверх» или «вбок», а не
«вниз к собственности».

**Решение:** `code/middle-01-retain-cycle.m` (уже с починкой — `weak`).

```text
Асет играет за Кайрат
выходим из блока — ждём три dealloc...
dealloc Team (Кайрат)
dealloc Player (Асет)
dealloc Player (Болат)
блок закрыт — dealloc были выше, утечки нет
```

Три `dealloc` на месте — утечки нет. Верни `Player.team` обратно в
`strong`, пересобери — и все три строки `dealloc` исчезнут. Вот так,
по пропавшему `dealloc`, утечку и ловят.

## Задача 4. Цикл удержания объект ↔ блок: что выведет `dealloc`

**Условие.** Объект хранит блок в своём свойстве, а блок внутри обращается
к `self`. Два варианта метода — какой из них утечёт и почему? Сработает ли
`dealloc`?

```objc
@interface Worker : NSObject
@property (nonatomic, copy) void (^job)(void);
@property (nonatomic, copy) NSString *name;
@end

- (void)setupBad {
    self.job = ^{ NSLog(@"%@", self.name); };          // A
}
- (void)setupGood {
    __weak typeof(self) weakSelf = self;
    self.job = ^{ NSLog(@"%@", weakSelf.name); };      // B
}
```

**Подумай сам.** Что захватывает блок, когда упоминает `self.name`?

**Разбор.** Блок захватывает объекты **сильно**. Стоит блоку упомянуть
`self.name`, как он захватывает сам `self` — сильно. А `self` сильно
держит блок в свойстве `job` (атрибут `copy`, для блоков это правильно).
Кольцо: `self → job → self`.

- В варианте A (`setupBad`) кольцо замкнуто. После того как внешний код
  отпустит `Worker`, его счётчик останется 1 (держит блок), `dealloc`
  **не сработает**. Кстати, clang это кольцо видит и предупреждает:
  `capturing 'self' strongly in this block is likely to lead to a retain
  cycle [-Warc-retain-cycles]`. Глушить предупреждение нельзя — это и есть
  баг.
- В варианте B (`setupGood`) блок захватывает не `self`, а `weakSelf` —
  слабую копию ссылки. Сильно `self` блок больше не держит, кольца нет.
  Когда внешний код отпустит `Worker`, тот спокойно уничтожится, и
  `dealloc` **сработает**.

Полный рабочий пример с обоими вариантами и живыми `dealloc`-логами уже
разобран в главе 12 (`code/12-retain-cycle.m`): для `bad` строки `dealloc`
нет, для `good` — есть. Идиома `__weak typeof(self) weakSelf = self;` —
твой главный инструмент против цикла «объект ↔ блок». Если внутри блока
`self` нужен несколько раз и важно, чтобы он не исчез посреди работы,
делают ещё `__strong typeof(weakSelf) strongSelf = weakSelf;` в начале
блока — это «weak-strong dance», но базовый ответ на собеседовании —
`weakSelf`.

## Задача 5. Зачем `@autoreleasepool` внутри длинного цикла

**Условие.** Тебе говорят: «оберни тело тяжёлого цикла в
`@autoreleasepool`». Объясни, что это даёт. Покажи на примере, что объект,
которого держит только пул, живёт ровно до слива пула.

**Подумай сам.** Кто освобождает временные объекты, у которых нет явного
владельца, и **когда**?

**Разбор.** Многие объекты живут «в долг»: их никто не держит сильно, и в
живых их удерживает только **пул автоосвобождения** (глава 13). Пул
сливается (drain) на своей закрывающей скобке и шлёт всем накопленным
объектам отложенный `release`. Если ты в длинном цикле плодишь тысячи
таких временных объектов, они копятся в пуле до самого его слива — память
пухнет, хотя на каждом шаге тебе нужен лишь один. Свой `@autoreleasepool`
внутри тела цикла сливается на каждой итерации и держит пик памяти низким.

Важная честная оговорка про **современный ARC с `-O2`**. По нашим
экспериментам компилятор агрессивно оптимизирует возвращаемые временные
объекты (return-value optimization) и часто освобождает их сразу на конце
выражения, вообще не пропуская через пул. Поэтому простой цикл с
`[NSString stringWithFormat:]` на оптимизированной сборке память почти не
растит — ARC справляется и без тебя. Но как только объект реально попадает
в пул (его держит только пул), правило снова работает: он живёт до слива.
Чтобы показать это наглядно, в примере мы кладём объект в пул явно через
`CFAutorelease(CFBridgingRetain(t))` — эти функции в обход
ARC-оптимизации отдают объект пулу.

**Решение:** `code/middle-04-autoreleasepool.m`.

```text
=== объект живёт ровно до слива пула ===
внутри пула: Temp(1) ещё жив (dealloc не было)
  dealloc Temp(1)
после слива: Temp(1) уже мёртв (dealloc был выше)
=== тяжёлый цикл: пул на каждой итерации ===
итерация 0: объект создан
  dealloc Temp(100)
итерация 1: объект создан
  dealloc Temp(101)
итерация 2: объект создан
  dealloc Temp(102)
цикл закончен — пул не дал памяти расти
```

`dealloc Temp(1)` встал точно между «внутри пула» и «после слива» — объект
дожил до закрывающей скобки пула и умер на ней. В цикле каждый `Temp`
умирает на сливе своей итерации, а не копится до конца.

## Задача 6. Поверхностная копия коллекции

**Условие.** Есть массив, внутри которого лежит **мутабельный** вложенный
массив. Делаем `mutableCopy` и потом меняем вложенный массив. Что увидим в
обеих коллекциях?

```objc
NSMutableArray *inner = [NSMutableArray arrayWithObjects:@"a", @"b", nil];
NSArray *original = @[inner, @"hello"];
NSMutableArray *shallow = [original mutableCopy];
[inner addObject:@"c"];
// original[0] = ?   shallow[0] = ?
```

**Подумай сам.** Что именно копирует `mutableCopy` — контейнер, его
содержимое или и то и другое?

**Разбор.** `copy` и `mutableCopy` у коллекций делают **поверхностную
копию** (shallow copy): создаётся новый контейнер, но в него кладутся **те
же самые** объекты, что были в оригинале, — по ссылке, без копирования.
Контейнеры теперь разные (`original != shallow`), а вот вложенный массив
`inner` — **общий** на обе коллекции (`original[0] == shallow[0]`).

Поэтому `[inner addObject:@"c"]` меняет один объект, видимый из обеих
коллекций: и `original[0]`, и `shallow[0]` покажут `(a, b, c)`. Копия
защитила тебя только от изменений **верхнего** уровня (добавь элемент в
`shallow` — `original` не дрогнет), но не от изменений вложенных
мутабельных объектов.

Когда нужна полная независимость, делают **глубокую копию** (deep copy).
Простой способ — прогнать структуру через архиватор:
`NSKeyedArchiver` → `NSKeyedUnarchiver`. После такой копии вложенные
массивы тоже становятся отдельными.

**Решение:** `code/middle-05-shallow-copy.m`.

```text
разные контейнеры? да
общий вложенный массив? да
original[0] = (
    a,
    b,
    c
)
shallow[0]  = (
    a,
    b,
    c
)
после deep-копии inner += d:
original[0] = (
    a,
    b,
    c,
    d
)
deep[0]     = (
    a,
    b,
    c
)
```

После `mutableCopy` оба массива видят `c`. После глубокой копии добавленный
`d` ушёл только в `original` — `deep` его не заметил, потому что у него
свой, отдельный вложенный массив.

## Задача 7. `copy`-семантика у `NSString`-свойства

**Условие.** Свойство объявлено `strong`, а присваивают ему
`NSMutableString`. Потом исходную строку меняют. Что станет со значением
свойства? Сравни со свойством `copy`.

```objc
@property (nonatomic, strong) NSString *strongName;
@property (nonatomic, copy)   NSString *safeName;

NSMutableString *src = [NSMutableString stringWithString:@"Айгуль"];
p.strongName = src;
p.safeName   = src;
[src appendString:@" Сергеевна"];   // меняем ИСХОДНУЮ строку
```

**Подумай сам.** Что хранит свойство `strong` — снимок строки или ссылку
на ту же `src`?

**Разбор.** `NSMutableString` — наследник `NSString`, поэтому его можно
присвоить свойству типа `NSString *`. Но дальше всё зависит от атрибута:

- `strong` сохраняет **ту же ссылку** на `src`. Изменили `src` — и
  `strongName` «поехал» вслед, ведь это один и тот же объект. После
  `appendString:` он покажет `Айгуль Сергеевна`. Объект мутирует за спиной
  владельца — источник коварных багов.
- `copy` в сеттере вызывает `[src copy]` и сохраняет **неизменяемый
  снимок**. Дальнейшие изменения `src` его не трогают: `safeName` так и
  останется `Айгуль`.

Отсюда правило, которое на собеседовании ждут почти всегда: **строковые
свойства (`NSString`, `NSArray`, `NSDictionary` и любые типы с мутабельным
наследником) объявляй `copy`.** Тогда снаружи никто не подсунет тебе
мутабельный объект и не изменит его потом за твоей спиной. У `copy` для
неизменяемой строки накладных расходов почти нет — `[immutableString copy]`
часто возвращает тот же объект с поднятым счётчиком, а не настоящую копию.

**Решение:** `code/middle-08-string-copy.m`.

```text
до мутации:
  strongName = Айгуль
  safeName   = Айгуль
после мутации src:
  strongName = Айгуль Сергеевна
  safeName   = Айгуль
```

Одно и то же присваивание, разные атрибуты — и `strong` «протёк»
изменением исходной строки, а `copy` устоял.

## Задача 8. Простой кэш на `NSMutableDictionary` и copy-ключи

**Условие.** Напиши простой кэш «ключ-значение» поверх
`NSMutableDictionary`. Объясни, что произойдёт, если в качестве ключа
передать `NSMutableString`, а потом изменить эту строку. Останется ли
значение доступным?

**Подумай сам.** `NSDictionary` хранит ссылку на твой ключ или его копию?

**Разбор.** `NSDictionary` хранит **копию** ключа — поэтому ключ обязан
поддерживать `NSCopying`, а при вставке словарь сам вызывает у ключа
`copy`. Это сделано именно ради защиты: если бы словарь держал ссылку на
твой мутабельный ключ, ты бы изменил строку — изменился бы и её `hash`, и
словарь больше не нашёл бы значение по «тому же» ключу. Снимок-копия
замораживает ключ в момент вставки.

Значит, наш кэш над `NSMutableDictionary` уже корректен: `setObject:forKey:`
сам копирует ключ. Передали `NSMutableString @"user:1"`, потом дописали к
ней `-changed` — в словаре всё равно лежит замороженная копия `user:1`.
Значение достаётся по литералу `@"user:1"`, а по изменённой строке — уже
нет (другой ключ).

Когда кэш должен ещё и сбрасываться под нехватку памяти, вместо
`NSMutableDictionary` берут **`NSCache`**: тот сам выкидывает элементы при
давлении на память и потокобезопасен. Но семантику ключей `NSCache` не
копирует (ключ просто `retain`), поэтому для строковых ключей либо
копируй их сам, либо используй неизменяемые.

**Решение:** `code/middle-13-cache.m`.

```text
по 'user:1':         Асет
по изменённому ключу: (null)
объектов в кэше: 1
```

Значение нашлось по оригинальному ключу и не нашлось по изменённой строке —
доказательство того, что словарь сохранил копию ключа, а не ссылку на твою
мутабельную строку.

## Задача 9. Спроектируй делегат с необязательными методами

**Условие.** Спроектируй протокол делегата для загрузчика: один метод
обязательный («завершилось»), один необязательный («прогресс»). Покажи,
как загрузчик зовёт необязательный метод безопасно, и объясни, почему
свойство `delegate` обычно `weak`.

**Подумай сам.** Что будет, если позвать `@optional`-метод у делегата,
который его не реализует?

**Разбор.** Протокол делит методы директивами `@required` (по умолчанию) и
`@optional`. Обязательный метод протокол гарантирует — его можно звать без
проверки. А необязательный делегат может и не реализовать; если позвать
несуществующий метод напрямую — `unrecognized selector`, падение. Поэтому
перед вызовом `@optional`-метода спрашивают
**`respondsToSelector:`** — реализует ли делегат этот селектор:

```objc
if ([self.delegate respondsToSelector:@selector(downloaderDidProgress:)]) {
    [self.delegate downloaderDidProgress:0.5];
}
```

Свойство-делегат объявляют **`weak`** по той же причине, что в задаче 3:
почти всегда владелец держит объект, а тот через `delegate` смотрит назад
на владельца. Сделай `delegate` сильным — получишь цикл удержания
`владелец → объект → delegate → владелец`. Слабая ссылка рвёт кольцо и
заодно сама обнуляется в `nil`, если делегат умер раньше, — тогда вызовы к
`self.delegate` просто молча уходят в `nil`.

Тип свойства — `id<DownloaderDelegate>`: «любой объект, лишь бы соответствовал
протоколу». Протокол наследует `<NSObject>`, чтобы у делегата гарантированно
был `respondsToSelector:`.

**Решение:** `code/middle-06-delegate.m`.

```text
--- minimal (без optional) ---
Minimal: готово, DATA
--- full (с optional) ---
Full: прогресс 50%
Full: готово, DATA
```

Первый делегат реализует только обязательный метод — прогресс пропущен без
падения. Второй реализует оба — прогресс вызван. Один и тот же загрузчик,
поведение задаёт делегат.

## Задача 10. Две категории с одинаковым методом — что вызовется

**Условие.** В двух разных категориях одного класса объявлен метод с
**одинаковым** именем, но разной реализацией. Какая из них победит при
вызове?

```objc
@interface NSString (A)
- (NSString *)tagline;
@end
@implementation NSString (A)
- (NSString *)tagline { return @"из A"; }
@end

@interface NSString (B)
- (NSString *)tagline;
@end
@implementation NSString (B)
- (NSString *)tagline { return @"из B"; }
@end
```

**Подумай сам.** Гарантирует ли язык, какая реализация окажется в таблице
методов?

**Разбор.** Это **неопределённое поведение**, и так на собеседовании и
отвечают. Когда две категории одного класса определяют метод с одним
именем, какая из них «ляжет» в таблицу методов класса последней — **не
специфицировано**. Обычно побеждает категория, чей объектный файл runtime
загрузил позже (зависит от порядка линковки), но опираться на это нельзя.

Хуже того — категория, переопределяющая метод **самого класса** (не другой
категории, а, скажем, родной метод `NSString`), молча затирает оригинал, и
вызвать прежнюю реализацию через `super` уже не получится. Поэтому правила
такие:

- **Не переопределяй существующие методы через категорию.** Категория —
  чтобы **добавлять** методы, а не подменять. Хочешь изменить поведение —
  делай подкласс.
- Имена методов в категориях **префиксируй** (`xyz_tagline`), чтобы не
  столкнуться ни с будущими методами Apple, ни с чужой категорией. Особенно
  это важно для категорий на классах Foundation.

Запускать такой код как «эксперимент» бессмысленно: результат у тебя может
оказаться `из A`, у коллеги — `из B`, а после обновления компилятора —
снова другой. Правильный ответ — «поведение не определено, так делать
нельзя».

## Задача 11. Категория не может добавить ivar — как обойти

**Условие.** Тебе нужно «прицепить» дополнительное поле к чужому классу
(скажем, `NSString`) через категорию. Но категория не умеет добавлять
ivar. Как сохранить данные на объекте?

**Подумай сам.** Где хранить значение, если места под ivar в объекте нет?

**Разбор.** Категория добавляет **методы**, но не **переменные экземпляра**:
размер объекта фиксируется при компиляции класса, и категория его менять не
может. Объявить в категории `@property` можно, но автоматического ivar под
него не появится — будут только объявления геттера и сеттера, которые ты
обязан написать сам. А хранить значение — через **связанные объекты**
(associated objects) из runtime:

```objc
#import <objc/runtime.h>
static const char kTagKey;   // адрес переменной = уникальный ключ

- (void)setTag:(NSString *)tag {
    objc_setAssociatedObject(self, &kTagKey, tag,
                             OBJC_ASSOCIATION_COPY_NONATOMIC);
}
- (NSString *)tag {
    return objc_getAssociatedObject(self, &kTagKey);
}
```

`objc_setAssociatedObject` привязывает значение к объекту по **ключу** —
им служит адрес статической переменной (`&kTagKey`), он гарантированно
уникален. Политика `OBJC_ASSOCIATION_COPY_NONATOMIC` означает «храни
копию, без атомарности» — это аналог атрибута `copy` у свойства. Runtime
сам снимет связанные объекты, когда носитель умрёт, — следить за их
освобождением не нужно.

Это ровно тот механизм, на котором, например, держат «обёрнутый» делегат
или флаг на ячейке таблицы, не плодя подкласс.

**Решение:** `code/middle-07-associated.m`.

```text
до: tag = (null)
после: tag = важный
```

До присваивания связанного значения нет — геттер возвращает `nil`. После —
строка достаётся обратно с того же объекта.

## Задача 12. KVC: доступ по строке, keyPath и операторы

**Условие.** Что напечатает этот код? Объясни `valueForKey:`,
`valueForKeyPath:` и операторы `@sum`/`@avg`/`@max`.

```objc
[e setValue:@350000 forKey:@"salary"];
[e valueForKeyPath:@"address.city"];
[team valueForKeyPath:@"@sum.salary"];
[team valueForKeyPath:@"@avg.salary"];
```

**Подумай сам.** Как KVC превращает строку `@"salary"` в вызов сеттера, и
что делает `@` перед именем оператора?

**Разбор.** KVC (Key-Value Coding, глава 20) даёт доступ к свойствам по
**строковому имени**, известному только во время выполнения:

- `setValue:forKey:` ищет сеттер `setSalary:` и зовёт его. Свойство —
  примитив `NSInteger`, поэтому KVC сам **распаковывает** переданный
  `NSNumber` (`@350000`) в `NSInteger`. Обратно, `valueForKey:` для
  примитива сам **упаковывает** значение в `NSNumber`.
- `valueForKeyPath:@"address.city"` идёт по точке сквозь вложенный объект:
  сначала `address`, у него — `city`. Это **keyPath**, цепочка ключей.
- Применённый к **массиву**, `valueForKey:@"name"` собирает значения ключа
  из всех элементов в новый массив.
- `@sum`, `@avg`, `@max`, `@count` — **коллекционные операторы**. `@` перед
  именем оператора отличает его от обычного ключа. `@"@sum.salary"`
  означает «просуммируй `salary` по всем элементам массива». Результат —
  `NSNumber`.

**Решение:** `code/middle-09-kvc.m`.

```text
valueForKey name = Асет
после setValue salary = 350000
keyPath city = Алматы
все имена: (
    "\U0410\U0441\U0435\U0442",
    "\U0411\U043e\U043b\U0430\U0442",
    "\U0414\U0430\U043d\U0430"
)
@sum.salary = 1200000
@avg.salary = 400000
@max.salary = 500000
@count       = 3
```

Кириллица в массиве показана escape-кодами вида `\U0410` — так `NSArray`
печатает строки в `description`, это нормально. Сумма трёх зарплат —
1 200 000, среднее — 400 000, максимум — 500 000.

## Задача 13. KVO: что приходит в `observeValueForKeyPath:` и почему ivar молчит

**Условие.** Подписались на свойство `balance` через KVO. Меняем его то
через сеттер, то напрямую через ivar. Когда придёт уведомление, а когда
нет? Что лежит в словаре `change`? Что обязательно сделать в конце?

**Подумай сам.** На чём именно стоит KVO — на присваивании ivar или на
вызове сеттера?

**Разбор.** KVO (Key-Value Observing, глава 20) уведомляет наблюдателя об
изменении свойства. Подписка — `addObserver:forKeyPath:options:context:`.
Уведомление приходит в `observeValueForKeyPath:ofObject:change:context:`, и
в словаре `change` лежат старое и новое значения под ключами
`NSKeyValueChangeOldKey` и `NSKeyValueChangeNewKey` (если при подписке
запросил опции `Old` и `New`).

Ключевой момент: **KVO перехватывает сеттер, а не присваивание ivar**. Под
капотом runtime подменяет класс объекта на сгенерированный подкласс, чей
сеттер `setBalance:` шлёт уведомления вокруг настоящего присваивания.
Поэтому:

- `acc.balance = 100` идёт через сеттер — **уведомление придёт**.
- `acc->_rawBalance = 999` пишет прямо в ivar, минуя сеттер, — **никакого
  уведомления**. KVO про такое изменение не знает.

И обязательное: перед смертью наблюдаемого объекта (или наблюдателя) надо
снять подписку — **`removeObserver:forKeyPath:`**. Забудешь — при следующем
уведомлении KVO попробует достучаться до уже мёртвого наблюдателя и уронит
программу, либо рантайм выдаст «was deallocated while key value observers
were still registered».

**Решение:** `code/middle-10-kvo.m`.

```text
--- через сеттер (KVC-совместимо) ---
изменилось 'balance': 0 -> 100
изменилось 'balance': 100 -> 250
--- прямое изменение ivar (в обход сеттера) ---
_rawBalance стал 999, но observe не вызвался
наблюдатель снят
```

Два изменения через сеттер дали два уведомления со старым и новым
значением. Прямая запись в ivar прошла молча. В конце — `removeObserver:`.

## Задача 14. Реализуй `NSCopying`

**Условие.** Сделай свой класс копируемым: реализуй `copyWithZone:` так,
чтобы `[obj copy]` возвращал **независимую** копию (меняем копию —
оригинал не дрогнул).

**Подумай сам.** Что должен вернуть `copyWithZone:` и как перенести в копию
все поля, включая строковое?

**Разбор.** Чтобы объект отвечал на `copy`, класс объявляет протокол
`<NSCopying>` и реализует единственный его метод — `copyWithZone:`. Сам
`copy` без аргументов — это удобная обёртка из `NSObject`, которая зовёт
`copyWithZone:nil`. Реализация создаёт новый объект и переносит в него
состояние:

```objc
- (id)copyWithZone:(NSZone *)zone {
    Vec2 *copy = [[[self class] allocWithZone:zone] init];
    copy.x = self.x;
    copy.y = self.y;
    copy.label = self.label;   // свойство copy само снимет снимок строки
    return copy;
}
```

Тонкости, которые проверяют на собеседовании:

- `[[self class] allocWithZone:zone]`, а не `[[Vec2 alloc] ...]` — чтобы у
  **подкласса** копия получалась правильного класса.
- Строковое поле `label` объявлено свойством `copy`, поэтому присваивание
  `copy.label = self.label` само сделает снимок — глубоко копировать строку
  вручную не нужно.
- Числа `x`, `y` — значения, копируются присваиванием.

**Решение:** `code/middle-11-nscopying.m`.

```text
оригинал: (1, 2) A
копия:    (100, 2) B
разные объекты? да
```

Изменили копии `x` и `label` — оригинал остался `(1, 2) A`. Объекты разные:
`copy` вернул новый экземпляр, а не ту же ссылку.

## Задача 15. Реализуй `isEqual:` и `hash` вместе

**Условие.** Реализуй сравнение объектов по значению: два «денежных»
объекта равны, если равны их суммы. Что будет, если переопределить
`isEqual:`, но **забыть** `hash`? Проверь поведение в `NSSet`.

**Подумай сам.** Зачем коллекциям-множествам нужен `hash`, если есть
`isEqual:`?

**Разбор.** Контракт `NSObject` жёсткий: **если два объекта равны по
`isEqual:`, у них обязан совпадать `hash`.** `NSSet` и `NSDictionary`
сначала раскладывают объекты по «корзинам» по их `hash` и только внутри
корзины сравнивают через `isEqual:`. Если переопределить `isEqual:`, но не
`hash`, два «равных» объекта унаследуют дефолтный `hash` от `NSObject`
(он основан на адресе) — у каждого свой. Они попадут в **разные корзины**, и
множество их сравнивать не станет: оба окажутся внутри, а поиск по
«равному» объекту провалится.

Поэтому переопределяют **обе** вещи согласованно:

```objc
- (BOOL)isEqual:(id)other {
    if (self == other) return YES;
    if (![other isKindOfClass:[Money class]]) return NO;
    return self.amount == ((Money *)other).amount;
}
- (NSUInteger)hash { return (NSUInteger)self.amount; }
```

`hash` должен зависеть **ровно от тех полей**, что участвуют в `isEqual:`.
Для нескольких полей их хэши обычно комбинируют через XOR (`a ^ b`).

**Решение:** `code/middle-12-isequal-hash.m`.

```text
=== сломанный (hash не согласован) ===
в множестве объектов: 2 (ждали 1)
containsObject(100)? НЕТ
=== правильный (isEqual + hash) ===
в множестве объектов: 1 (ждали 1)
containsObject(100)? да
```

Без согласованного `hash` множество приняло два «равных» объекта как
разные (`count = 2`) и не нашло объект по значению. С правильным `hash` —
дубликат отброшен (`count = 1`), поиск работает.

## Задача 16. `isEqual:` против `isEqualToString:`

**Условие.** В чём разница между `[a isEqual:b]` и `[a isEqualToString:b]`
для двух `NSString`? Что быстрее и что безопаснее?

**Подумай сам.** Какой из методов знает заранее, что оба аргумента —
строки?

**Разбор.** Оба сравнивают строки по содержимому (не по адресу — для адреса
был бы `==`, и для строк он почти всегда неверен). Разница в типе и цене:

- `isEqual:` — общий метод `NSObject`. Он принимает `id` (любой объект),
  поэтому сначала **проверяет класс** аргумента: а строка ли это вообще?
  Только потом сравнивает содержимое. Универсален, чуть медленнее,
  безопасен к чужим типам — `[str isEqual:someArray]` спокойно вернёт `NO`.
- `isEqualToString:` — специализированный метод `NSString`. Он уже
  **предполагает**, что аргумент — строка, пропускает проверку класса и
  сравнивает содержимое напрямую. Быстрее на горячем пути.

Ловушка `isEqualToString:`: если передать в него **не строку** (например,
`nil` пройдёт молча и вернёт `NO`, а вот объект другого класса в некоторых
случаях — неопределённое поведение), гарантий меньше. Практическое
правило: когда **точно знаешь**, что оба — `NSString`, бери
`isEqualToString:` (читаемее и быстрее). Когда тип под вопросом или
сравниваешь разнородные объекты — `isEqual:`. И никогда не сравнивай
строки через `==`: он сверяет указатели, а не текст, и «совпадёт» лишь
случайно (например, на интернированных литералах).

## Задача 17. Быстрый разбор: сработает ли `dealloc`?

**Условие.** Для каждого мини-сценария скажи, сработает ли `dealloc`
объекта `A` к концу блока. Все свойства — под ARC.

1. `A` создан локально, в конце блока локальная ссылка выходит из области.
2. `A` сильно держит `B`, `B` сильно держит `A`.
3. `A` сильно держит `B`, `B` держит `A` через `weak`-свойство.
4. `A` хранит в свойстве `copy`-блок, блок упоминает `self.name`.
5. `A` хранит блок, блок упоминает `weakSelf.name`.

**Подумай сам.** В каждом случае посчитай, остаётся ли на `A` хоть одна
сильная ссылка после выхода из блока.

**Разбор.**

1. **Сработает.** Единственная сильная ссылка вышла из области — счётчик 0,
   `dealloc`.
2. **Не сработает.** Классический цикл: каждый держит другого сильно,
   счётчики застряли на 1. Утечка.
3. **Сработает у обоих.** `weak` не считается за владение: когда исчезли
   локальные ссылки, `A` обнулился, за ним `B`.
4. **Не сработает.** Блок захватил `self` сильно, `self` держит блок —
   цикл «объект ↔ блок».
5. **Сработает.** Блок захватил `weakSelf`, сильного кольца нет.

Это сжатый смотр всего, что было выше: единственный вопрос на собеседовании
по памяти — «остаётся ли на объект сильная ссылка». Если да и она по кругу
ведёт к самому объекту — это цикл, `dealloc` молчит, и одну ссылку в кольце
надо сделать `weak`.

## Задача 18. Code review: найди и почини утечку в блоке

**Условие.** Тебе прислали на ревью этот метод. Объект `Timer`
устанавливает повторяющийся обработчик, который пишет в свой `log`. Найди
проблему и предложи правку.

```objc
@interface Timer : NSObject
@property (nonatomic, copy) void (^onTick)(void);
@property (nonatomic, strong) NSMutableArray *log;
@end

@implementation Timer
- (void)start {
    self.onTick = ^{
        [self.log addObject:@"tick"];   // ← что не так?
    };
}
- (void)dealloc { NSLog(@"dealloc Timer"); }
@end
```

**Подумай сам.** Что захватывает блок в строке `[self.log addObject:...]`?

**Разбор.** Блок упоминает `self.log` — а значит захватывает **`self`
сильно**. Свойство `onTick` объявлено `copy` и сильно держит блок. Кольцо
`self → onTick → self` замкнулось: `Timer` никогда не вызовет `dealloc`,
сообщение «dealloc Timer» не появится. Это утечка, и компилятор честно
предупредит про `-Warc-retain-cycles`.

Правка — слабая копия `self`:

```objc
- (void)start {
    __weak typeof(self) weakSelf = self;
    self.onTick = ^{
        [weakSelf.log addObject:@"tick"];
    };
}
```

Теперь блок захватывает `weakSelf`, сильного кольца нет, и когда внешний
код отпустит `Timer`, тот спокойно уничтожится — `dealloc Timer`
напечатается. Если внутри блока к `self` обращаются несколько раз и важно,
чтобы он не исчез посреди работы блока, в начале блока берут сильную копию
на время вызова:

```objc
self.onTick = ^{
    __strong typeof(weakSelf) strongSelf = weakSelf;
    if (strongSelf == nil) { return; }   // объект уже умер — выходим
    [strongSelf.log addObject:@"tick"];
};
```

Это «weak-strong dance»: слабая ссылка рвёт цикл, а локальная сильная на
время выполнения блока гарантирует, что объект не исчезнет между двумя
строками. На собеседовании достаточно назвать причину (захват `self`) и
базовую правку (`weakSelf`); упоминание `strongSelf` — плюс к ответу.

---

## Что проверяет этот раздел

Middle-уровень — это уже не «знаю синтаксис», а «понимаю модель». Сведём
ключевое в одну картину:

- **Память.** Сильная ссылка владеет, слабая наблюдает и сама становится
  `nil`, `unsafe_unretained` повисает. Цикл удержания — два владельца по
  кругу; лечится одним `weak`. ARC циклы не ловит — это на тебе.
- **Блоки.** Захват — копия значения в момент создания; `__block` — общая
  ячейка; упоминание `self` в блоке свойства — цикл, режется `weakSelf`.
- **Копирование.** `copy`/`mutableCopy` поверхностны; строковые свойства —
  `copy`; свой класс делаешь копируемым через `NSCopying`.
- **Контракты.** Равенство — это `isEqual:` плюс согласованный `hash`;
  словарь копирует ключи; делегат — `weak` и `respondsToSelector:` для
  `@optional`.
- **Runtime-приёмы.** Категория добавляет методы, но не ivar (выручают
  связанные объекты); две категории с одним методом — неопределённость;
  KVC даёт доступ по строке, KVO стоит на сеттере и требует
  `removeObserver:`.

Если на собеседовании ты на каждый такой вопрос отвечаешь не «по памяти»,
а выводом из модели владения и контрактов классов — это и есть Middle.
