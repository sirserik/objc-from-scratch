# Глава 12. Блоки

До сих пор мы передавали друг другу *данные*: числа, строки, объекты. В
этой главе научимся передавать *действие* — кусок кода, упакованный в
переменную. В Objective-C такая упаковка называется **блок** (block).
Блок можно положить в переменную, отдать в метод, сохранить на потом и
вызвать когда угодно. А ещё блок умеет то, чего обычная функция не умеет:
он запоминает переменные из того места, где был написан. Это делает его
**замыканием** (closure) — и именно ради этого блоки и придуманы.

Мы построим всё по нарастающей: простейший блок в переменной → блок,
который захватывает окружение → изменяемый захват через `__block` →
блок как «обработчик завершения» у собственного метода → и, наконец,
самая частая ловушка блоков — цикл удержания (retain cycle) и его
починка. Каждый шаг компилируем и смотрим на живой вывод.

## Что мы сделаем

- Разберём, что такое блок и зачем он нужен.
- Научимся читать и писать тип блока `void (^name)(int)` и литерал
  `^(int x){ ... }`.
- Дадим типам блоков короткие имена через `typedef`.
- Поймём, как блок захватывает переменные окружения и почему по
  умолчанию их нельзя менять внутри.
- Введём `__block` для изменяемого захвата.
- Передадим блок в метод — паттерн completion handler.
- Встретим retain cycle вживую (через `dealloc`) и починим его
  слабой ссылкой `weakSelf`.

## Сначала — указатель на функцию в Си

Чтобы оценить блок, посмотрим, что было до него. В Си действие тоже
можно положить в переменную — через **указатель на функцию**. Звучит
страшно, на деле просто адрес: переменная хранит адрес кода функции, и
через эту переменную функцию можно вызвать.

Объявляется так:

```c
int (*f)(int);
```

Читается изнутри наружу: `f` — это указатель (`*`) на функцию, которая
принимает `int` и возвращает `int`. Скобки вокруг `*f` обязательны: без
них `int *f(int)` означало бы совсем другое — функцию, возвращающую
`int *`.

Присваиваем и зовём:

```c
int doubleC(int x) { return x * 2; }

int (*f)(int) = doubleC;   // f показывает на код doubleC
int r = f(21);             // вызов через указатель: r == 42
```

Указатель на функцию умеет одно: показать на код. Он **не помнит**
ничего о месте, где его создали. Запомни это — через минуту блок сделает
ровно то, чего здесь не хватает.

## Что такое блок

Блок — это **объект-замыкание**: кусок кода вместе с переменными, которые
он «утащил» из окружения. В отличие от функции, блок можно написать прямо
посреди другого кода, без отдельного имени, и тут же положить в
переменную.

Сравним два синтаксиса бок о бок:

```objc
// Си: указатель на функцию
int (*f)(int) = doubleC;

// Objective-C: переменная-блок
int (^doubleB)(int) = ^(int x) {
    return x * 2;
};
```

Разница в одном символе: вместо звёздочки `*` у блока стоит **домик `^`**
(caret). Где у указателя на функцию `(*f)`, у блока `(^doubleB)`. Всё
остальное в типе читается одинаково: `int (^doubleB)(int)` — это блок,
принимающий `int` и возвращающий `int`.

Справа от `=` стоит **литерал блока**:

```objc
^(int x) {
    return x * 2;
}
```

Он начинается с того же домика `^`, дальше — список параметров `(int x)`
как у функции, затем тело в фигурных скобках. Имени у этого кода нет:
блок безымянный, он живёт в переменной `doubleB`.

Вызывают блок так же, как функцию — имя и круглые скобки с аргументами:

```objc
doubleB(21);   // вернёт 42
```

> **Отличие от Си.** Указатель на функцию `int (*f)(int)` умеет только
> показать на готовый код — он ничего не знает об окружении. Блок
> `int (^b)(int)` тоже хранит код, но вдобавок **захватывает** переменные
> того места, где написан. Это и делает его замыканием: код плюс
> прихваченное окружение. У си-функции окружения нет вовсе.

### Блоки разной формы

Не у каждого блока есть аргументы и возвращаемое значение. Самый частый
блок — «сделай что-нибудь», без входа и выхода:

```objc
void (^hello)(void) = ^{
    NSLog(@"привет из блока");
};
hello();
```

Тип `void (^hello)(void)` читается так: блок, который ничего не принимает
(`void` в скобках) и ничего не возвращает (`void` слева). Обрати
внимание: если у блока нет параметров, список `(void)` в литерале можно
опустить — пишем просто `^{ ... }`. Этот короткий вид `^{ }` ты уже
мельком видел в главе 11; теперь понятно, что это блок без аргументов.

## Захват окружения

Вот что блок умеет, а функция — нет. Напиши блок рядом с локальной
переменной, упомяни её внутри — и блок **захватит** (capture) её
значение.

```objc
int factor = 3;

int (^multiply)(int) = ^(int x) {
    return x * factor;   // factor взят из окружения
};

NSLog(@"3 * 5 = %d", multiply(5));   // 15
```

Переменной `factor` нет среди параметров блока. Блок «дотянулся» до неё
наружу, в тело `main`. В момент создания блока он снял **копию** значения
`factor` — то есть число `3` — и положил внутрь себя.

Слово «копию» здесь ключевое. Поменяем `factor` после создания блока:

```objc
factor = 100;
NSLog(@"блок помнит 3 * 5 = %d", multiply(5));   // всё ещё 15
```

Блок по-прежнему считает с тройкой. Он захватил *значение* `3`, а не саму
переменную `factor`. Дальнейшие изменения `factor` его не трогают.

Отсюда и правило: **захваченные значения внутри блока менять нельзя**.
Если написать в теле `factor = 7;` или `factor++`, компилятор откажется:

```text
error: variable is not assignable (missing __block type specifier)
```

Для блока это чужая константа, копия только для чтения. Так сделано
специально — чтобы не было путаницы, чьё значение меняется, внешнее или
внутреннее. Через минуту мы снимем это ограничение через `__block`, но
сперва запомним поведение по умолчанию: **захват — это копия только для
чтения**.

> **Отличие от Си.** Указатель на функцию не способен «увидеть» локальную
> `factor` — функция знает только свои параметры. Чтобы передать ей
> `factor`, в Си его пришлось бы явно отдать аргументом: `multiply(5,
> factor)`. Блок прихватывает `factor` сам, молча, в момент написания.
> Это и есть замыкание.

### typedef: короткое имя длинному типу

Тип блока громоздкий. Когда он встречается часто (в свойстве, в
параметре метода), его удобно спрятать за коротким именем через
`typedef`:

```objc
typedef void (^Greeter)(NSString *);
```

Читается так: `Greeter` — это имя для типа «блок, принимающий
`NSString *` и ничего не возвращающий». Имя блока в `typedef` (`Greeter`)
встаёт ровно туда, где в объявлении переменной стояло бы `(^имя)`.
Теперь вместо длинного типа пишем коротко:

```objc
NSString *prefix = @"Привет";
Greeter greet = ^(NSString *name) {
    NSLog(@"%@, %@!", prefix, name);   // prefix захвачен
};
greet(@"Мир");
```

Блок заодно захватил и `prefix` — объект захватывается так же, как
число. Без `typedef` то же объявление выглядело бы как
`void (^greet)(NSString *) = ^(NSString *name){ ... };` — глазам тяжелее.
`typedef` особенно выручает, когда тип блока — это тип параметра метода:
в сигнатуре метода длинная конструкция в скобках читается совсем плохо.
Скоро увидим это на completion handler.

## Изменяемый захват: `__block`

Иногда блок должен не просто читать внешнюю переменную, а **менять** её —
например, считать, сколько раз его вызвали. Обычный захват это запрещает.
Решение — пометить переменную ключевым словом `__block` (два
подчёркивания в начале):

```objc
__block int count = 0;

void (^tick)(void) = ^{
    count++;   // теперь можно: count — общая ячейка
};

tick();
tick();
tick();
NSLog(@"%d", count);   // 3
```

`__block` меняет саму природу захвата. Без него блок брал копию значения.
С ним переменная `count` превращается в **общую ячейку**: и внешний код,
и блок смотрят на одну и ту же `count`. Блок инкрементирует её —
изменение видно снаружи. Внешний код меняет её — изменение видно блоку.

> **Отличие от Си.** Чтобы функция в Си смогла изменить чужую переменную,
> ей передают **указатель** на эту переменную: `void tick(int *count) {
> (*count)++; }`, а зовут `tick(&count)`. Функция пишет по адресу — и
> снаружи видно. `__block` делает то же самое, но скрытно: компилятор сам
> заворачивает `count` в общую ячейку и сам организует доступ по ссылке.
> Тебе не нужно ни `&`, ни `*` — пишешь `count++`, как с обычной
> переменной.

### Программа с `__block`

Оба блока собраны в файл `code/12-block-var.m`: первый (`tick`) считает
вызовы, второй (`add`) накапливает сумму. Запуск и вывод:

```text

2026-06-28 ... сумма = 100
```

Второй блок `add` накапливает сумму в `__block`-переменной `sum`,

накопитель, `__block`-переменная — копилка.

## Блок как аргумент метода: completion handler

Главное применение блоков — отдать кусок кода *другому коду*, чтобы тот
вызвал его в нужный момент. Самый частый случай: метод делает работу, а в
конце зовёт переданный ему блок с результатом. Такой блок называют
**completion handler** — обработчик завершения.

Заведём класс `Downloader` с методом, который «качает» имя и по
завершении зовёт блок. Сначала через `typedef` опишем тип блока — иначе
сигнатура метода будет нечитаемой:

```objc
typedef void (^DownloadHandler)(NSString *result);

@interface Downloader : NSObject
- (void)downloadName:(NSString *)name
          completion:(DownloadHandler)completion;
@end
```

Метод `downloadName:completion:` берёт два аргумента: имя и блок-обработчик.
Реализация делает «работу» и в конце вызывает блок, отдавая ему
результат:

```objc
@implementation Downloader
- (void)downloadName:(NSString *)name
          completion:(DownloadHandler)completion {
    NSLog(@"качаю %@ ...", name);
    NSString *result = [name uppercaseString];
    completion(result);   // зовём переданный блок
}
@end
```

`completion(result)` — обычный вызов блока: имя параметра и круглые скобки
с аргументом. Метод не знает и не хочет знать, *что* за код внутри блока;
его дело — позвать его с результатом.

А вызывающий код передаёт блок прямо на месте, последним аргументом:

```objc
Downloader *d = [[Downloader alloc] init];
[d downloadName:@"file.txt" completion:^(NSString *result) {
    NSLog(@"готово, получил: %@", result);
}];
```

Литерал блока встал на место аргумента `completion:`. Он сработает не
сразу, а тогда, когда метод дойдёт до `completion(result)`.

> **Отличие от Си.** В Си «обратный вызов» (callback) делают через
> указатель на функцию: метод принимает `void (*cb)(const char *)`, а
> вызывающий передаёт имя заранее объявленной функции. Но функция-callback
> не видит локальных переменных места вызова — нужные данные ей
> пропихивают через дополнительный аргумент `void *context`. Блок носит
> своё окружение с собой, поэтому completion handler в Objective-C пишут
> прямо по месту, и он сразу видит все окрестные переменные.

### Программа с completion handler

Интерфейс, реализация и два вызова с разными обработчиками собраны в файл

## Блоки в Foundation

Многие методы Foundation принимают блок и зовут его для каждого элемента
или для сравнения. Два частых примера.

**`enumerateObjectsUsingBlock:`** — обойти массив, вызвав блок на каждом
элементе. Блок получает сам объект, его индекс и указатель `BOOL *stop`,
через который можно досрочно прервать обход:

```objc
NSArray *fruits = @[@"яблоко", @"груша", @"слива"];
[fruits enumerateObjectsUsingBlock:^(NSString *item,
                                     NSUInteger idx,
                                     BOOL *stop) {
    NSLog(@"%lu: %@", (unsigned long)idx, item);
    if (idx == 1) { *stop = YES; }   // остановиться после второго
}];
```

`*stop` — это запись по указателю: метод проверит ячейку после каждого
шага и, увидев `YES`, остановится. Вывод этого куска будет чуть ниже,
вместе с сортировкой — обе программы у нас в одном файле.

**`sortedArrayUsingComparator:`** — отсортировать массив, сравнивая пары
элементов блоком-компаратором. Блок возвращает `NSComparisonResult`:
«меньше», «равно» или «больше». Отсортируем слова по длине:

```objc
NSArray *words = @[@"кит", @"муравей", @"слон", @"ёж"];
NSArray *sorted = [words sortedArrayUsingComparator:
    ^NSComparisonResult(NSString *a, NSString *b) {
        return [@(a.length) compare:@(b.length)];
    }];
NSLog(@"по длине: %@", sorted);
```

Здесь `^NSComparisonResult(...)` — блок с явно указанным типом
возвращаемого значения сразу после `^`. Внутри `@(a.length)` заворачивает
длину в `NSNumber`, а `compare:` сравнивает два числа и сам выдаёт нужный
`NSComparisonResult`.

Обе программы лежат в `code/12-foundation-blocks.m`. Запусти — и увидишь
неожиданное:

```text
2026-06-28 ... 0: яблоко
2026-06-28 ... 1: груша
2026-06-28 ... по длине: (
    "\U0451\U0436",
    "\U043a\U0438\U0442",
    "\U0441\U043b\U043e\U043d",
    "\U043c\U0443\U0440\U0430\U0432\U0435\U0439"
)
2026-06-28 ... по длине через componentsJoinedByString: ёж, кит,
слон, муравей
```

(Последняя строка в терминале идёт одной строкой, здесь она перенесена,
чтобы влезть в страницу.)

Обход прервался после «груши», как мы и просили, — до «сливы» дело не
дошло. А вот сортировка напечаталась абракадаброй, хотя отработала
правильно. Дело не в блоке и не в кодировке файла: так печатает себя сам
`NSArray`. Его метод `description` (тот, что зовёт `%@`) экранирует
все не-ASCII символы в вид `\U0451`. `\U0451` — это код буквы «ё»,
`\U0436` — «ж», то есть первый элемент это «ёж».

Расшифровывать такое глазами невозможно, поэтому запомни приём из
последней строки: если надо посмотреть на массив строк по-человечески,
склей его в одну строку методом `componentsJoinedByString:`. У `NSString`
никакого экранирования нет, и кириллица печатается как есть. Порядок,
кстати, верный: «ёж» (2), «кит» (3), «слон» (4), «муравей» (7).

## Ловушка блоков: цикл удержания

Теперь — самое важное про блоки и память. Блок **захватывает объекты
сильно** (strong): пока жив блок, жив и захваченный объект, потому что
блок держит на него крепкую ссылку. Обычно это удобно. Но иногда
оборачивается бедой.

Сначала — два слова про «сильно» и «слабо», подробности будут в главе 13
про ARC. Под ARC каждый объект живёт, пока на него есть хотя бы одна
**сильная ссылка** (strong reference). Не осталось сильных ссылок —
объект уничтожается, срабатывает его `dealloc`. **Слабая ссылка** (weak
reference) на объект указывает, но «не считается»: она не удерживает
объект в живых.

Проблема возникает, когда два объекта держат друг друга сильно. Тогда
ни один из них никогда не дойдёт до нуля сильных ссылок — оба зависнут в
памяти навсегда. Это и есть **цикл удержания** (retain cycle).

Самый частый цикл — объект хранит блок в своём свойстве, а блок внутри
себя обращается к `self`:

```objc
@interface Worker : NSObject
@property (nonatomic, copy) void (^job)(void);
@property (nonatomic, copy) NSString *name;
@end
```

Свойство `job` объявлено `copy` — для блоков это правильный атрибут
(почему `copy`, разберём ниже в разделе про память). Теперь напишем
метод, который кладёт блок в `job`, а блок упоминает `self.name`:

```objc
- (void)setupBad {
    self.job = ^{
        NSLog(@"работаю как %@", self.name);   // захват self!
    };
}
```

Стоит блоку упомянуть `self.name`, как он захватывает **сам `self`** —
сильно. Получается кольцо:

```text
   self (Worker)  ──strong──►  job (блок)
        ▲                          │
        └──────── strong ──────────┘
   блок захватил self
```

`self` держит `job`, `job` держит `self`. Кольцо замкнулось — никто не
отпустит другого, `dealloc` не сработает. Утечка памяти.

Кстати, clang это кольцо **видит** и предупреждает. Если собрать `setupBad`
как есть, компилятор скажет:

```text
warning: capturing 'self' strongly in this block is likely to lead
to a retain cycle [-Warc-retain-cycles]
```

В нашем учебном файле мы это предупреждение намеренно глушим прагмой,
чтобы показать сам эффект утечки. В рабочем коде предупреждение надо не
глушить, а чинить.

### Чиним: `weakSelf`

Лекарство — захватить не сам `self`, а **слабую ссылку** на него. Тогда
блок на `self` смотрит, но в живых его не держит, и кольцо рвётся:

```objc
- (void)setupGood {
    __weak typeof(self) weakSelf = self;
    self.job = ^{
        NSLog(@"работаю как %@", weakSelf.name);
    };
}
```

Разберём первую строку по частям:

- `__weak` — слабая ссылка: указывает на объект, но не удерживает его.
- `typeof(self)` — «тип, как у `self`», то есть `Worker *`. Можно было
  написать и `Worker *` прямо, но `typeof(self)` не привязан к имени
  класса и переживёт переименования — это устойчивая идиома.
- `weakSelf = self` — заводим слабую копию ссылки на текущий объект.

Внутри блока обращаемся к `weakSelf`, а не к `self`. Блок захватывает
`weakSelf` (слабую ссылку), `self` блок больше сильно не держит — кольца
нет. Когда внешний код отпустит `Worker`, тот спокойно уничтожится.

> **Отличие от Си.** В Си такой проблемы нет, потому что нет ни ARC, ни
> сильных ссылок: память ты освобождаешь руками через `free`, и кольцевых
> зависимостей подсчёта ссылок просто не существует. Цикл удержания —
> плата за подсчёт ссылок: объект живёт, пока его кто-то держит. `__weak`
> подсказывает ARC: «эту ссылку при подсчёте не учитывай».

### Видим утечку вживую

Чтобы цикл удержания не остался теорией, поймаем его через `dealloc`.
Добавим в `Worker` метод `dealloc` с печатью — он сработает только если
объект реально уничтожен. Полный файл — `code/12-retain-cycle.m`. К
классу `Worker` (с показанными выше `setupBad` и `setupGood`) добавлен
`dealloc`, а в `setupBad` стоит та самая прагма, глушащая
`-Warc-retain-cycles`:

```objc
- (void)dealloc {
    NSLog(@"dealloc: Worker %@ уничтожен", self.name);
}
```

Главная функция создаёт два объекта в отдельных вложенных пулах — «плохой»
и «хороший» — и смотрит, для кого сработает `dealloc`:

```objc
int main(void) {
    @autoreleasepool {
        NSLog(@"--- цикл удержания (setupBad) ---");
        @autoreleasepool {
            Worker *w = [[Worker alloc] init];
            w.name = @"bad";
            [w setupBad];
        }   /* w вышел из области, но dealloc НЕ сработает: цикл */
        NSLog(@"(dealloc для bad так и не вызвался)");

        NSLog(@"--- починка (setupGood) ---");
        @autoreleasepool {
            Worker *w = [[Worker alloc] init];
            w.name = @"good";
            [w setupGood];
        }   /* здесь dealloc сработает — цикла нет */
        NSLog(@"(объект good освобождён выше)");
    }
    return 0;
}
```

Запуск:

```text
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/12-retain-cycle.m -o /tmp/t && /tmp/t
```

Вывод:

```text
2026-06-28 ... --- цикл удержания (setupBad) ---
2026-06-28 ... (dealloc для bad так и не вызвался)
2026-06-28 ... --- починка (setupGood) ---
2026-06-28 ... dealloc: Worker good уничтожен
2026-06-28 ... (объект good освобождён выше)
```

Вот доказательство. Для объекта `bad` строки `dealloc: Worker bad
уничтожен` **нет** — он завис в памяти, цикл не дал ему умереть. А для
`good` строка `dealloc: Worker good уничтожен` появилась ровно там, где
объект вышел из своего пула: слабая ссылка разорвала кольцо, и ARC
освободил объект. Один и тот же класс, одна разница — `self` против
`weakSelf`.

## Блоки и память: стек и куча

Когда ты пишешь литерал `^{ ... }`, захватывающий переменные, блок
сначала рождается **на стеке** — в кадре текущей функции — и исчезает,
как только функция вернётся.
Сохранить такой блок «на потом» (в свойство, в массив) нельзя: после
выхода из функции там мусор. Поэтому блок при необходимости **копируют в
кучу** — операцией `Block_copy` (парная ей `Block_release`); копия в куче
живёт, пока на неё есть ссылки, как обычный объект. (Блок, который
ничего не захватывает, компилятор кладёт в постоянную память программы:
ему нечего терять при выходе из функции.)

Под ARC это происходит **прозрачно**: присваиваешь блок сильной
переменной или свойству, возвращаешь из метода — ARC сам копирует его в
кучу и сам
следит за временем жизни, руками `Block_copy`/`Block_release` писать не
нужно. Поэтому блочное свойство объявляют с атрибутом `copy`
(`@property (nonatomic, copy) void (^job)(void);`) — он подчёркивает «храни
в куче». `strong` сработал бы так же, но `copy` остаётся принятым стилем.

## Полная программа

Итоговых файлов в главе шесть, каждый — самостоятельная программа:

- `code/12-basic.m` — блок в переменной, рядом с указателем на функцию.

Каждый файл собирается и запускается одной командой (подставь имя):

## Частые ошибки

- **Перепутал `^` и `*`.** Тип блока — `void (^name)(int)` с домиком, а
  не `void (*name)(int)` со звёздочкой (это указатель на функцию).
  Перепутаешь — компилятор будет ругаться на несовместимость типов.
- **Меняешь захваченную переменную без `__block`.** Тело блока считает
  обычный захват константой: `count++` внутри не скомпилируется, пока не
  пометишь `count` как `__block`.
- **Думаешь, что блок видит свежее значение.** Захват снимает копию в
  момент *создания* блока. Поменял переменную потом — блок этого не
  заметит (если только она не `__block`).
- **Цикл удержания через `self`.** Блок в свойстве объекта, упоминающий
  `self` (в том числе скрыто, через ivar или `self.property`), создаёт
  кольцо. Лекарство — `__weak typeof(self) weakSelf = self;` и обращение
  к `weakSelf`. Не глуши `-Warc-retain-cycles` — чини причину.
- **Забыл, что блок может не вызваться.** Completion handler вызывает
  *чужой* код. Если он по какой-то ветке забудет позвать твой блок, твой
  «финальный» код не выполнится. Проектируя метод с блоком, вызывай его
  на всех путях.
- **Возвращаешь стековый блок без ARC.** Под ARC безопасно; в ручном
  режиме (глава 13) вернуть захватывающий блок из функции без
  `Block_copy` — обращение к мусору после выхода из функции. Прямое
  `return ^{ ... x ... };` clang поймает сам (`returning block that lives
  on the local stack`), а вот через промежуточную переменную — уже нет.

## Упражнения

1. Напиши блок `int (^maxB)(int, int)`, возвращающий большее из двух
   чисел. Вызови его с разными парами и выведи результат.
2. Заведи `typedef double (^MathOp)(double, double)` и три переменные
   этого типа: сложение, вычитание, умножение. Положи их в `NSArray`
   и пройди циклом, применяя каждую к паре `10` и `3`.
3. Сделай блок-счётчик с `__block`: каждый вызов увеличивает счётчик и
   печатает его. Вызови пять раз.
4. Добавь классу `Downloader` метод
   `processNames:(NSArray *)names
   completion:(void (^)(NSInteger))completion`,
   который «обрабатывает» все имена и в конце зовёт `completion` с их
   количеством.
5. Возьми массив строк и отсортируй его `sortedArrayUsingComparator:`
   по убыванию длины (поменяй порядок аргументов в `compare:`).
6. Сломай `setupGood`: верни внутри блока `self` вместо `weakSelf`,
   собери и убедись, что `dealloc` перестал срабатывать. Потом верни
   `weakSelf` обратно.

## Что мы получили

Теперь ты умеешь упаковывать действие в переменную. Разобрали тип блока
`void (^name)(int)` и литерал `^(int x){ ... }`, домик `^` против
звёздочки указателя на функцию, захват окружения (копия только для
чтения) и изменяемый захват через `__block`, `typedef` для читаемых типов,
блок как аргумент метода (completion handler) и методы Foundation с
блоками. И главное — встретили цикл удержания вживую через `dealloc` и
починили его слабой ссылкой `weakSelf`.

Блоки вплотную подвели нас к теме памяти: сильные и слабые ссылки, кто
кого удерживает, когда срабатывает `dealloc`. Ровно об этом — следующая
глава 13 про ARC, где «сильно/слабо», `strong`/`weak`, `copy` и весь
подсчёт ссылок разбираются с самого начала и до конца.
