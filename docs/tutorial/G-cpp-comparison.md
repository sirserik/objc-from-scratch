# Приложение G. Objective-C глазами C++-разработчика

Остальная книга писалась для того, кто видит указатель впервые. Это
приложение — для тебя, если ты пришёл из C++. Премиса простая: ты уже
знаешь, что такое vtable, RAII, шаблоны, умные указатели и RTTI. Я не
буду объяснять их заново. Я покажу, **как Objective-C решает те же
задачи иначе** — где-то слабее, где-то неожиданно мощнее, — и где между
языками проходят настоящие границы.

Формат — сравнения бок о бок. Для каждой темы: короткий тезис, блок
«как в C++», блок «как в Objective-C», и разбор того, в чём именно
разница. Листинги в тексте — выжимки; полные программы, которые
компилируются и запускаются, лежат в `code/` с префиксом `g-`, команды
сборки — в конце.

## 1. Камертон: статика против динамики

Оба языка — надстройки над Си, оба компилируются в нативный код, оба
дают доступ к указателям и ручной памяти. На этом сходство кончается.

C++ — язык **компиляции**. Его идеал — zero-overhead abstraction: всё,
что можно решить до запуска, решается до запуска. Типы, перегрузки,
специализации шаблонов, devirtualization, инлайнинг — работа компилятора.
В готовом бинарнике от системы типов не остаётся почти ничего; вызов
функции — это переход по адресу, который выбрал компоновщик.

Objective-C — язык **рантайма**. Рядом с твоей программой живёт
библиотека `libobjc`, и она работает всё время выполнения: хранит классы
как объекты, ищет методы по имени, пересылает сообщения, добавляет методы
на лету. Центральная операция — не «вызвать функцию по адресу», а
«послать объекту сообщение, и пусть он сам в рантайме решит, какой код
выполнить». Это медленнее прямого вызова, но из этой динамики растёт
половина возможностей Cocoa: KVO, target-action, пересылка, категории,
NSCoding, апповый цикл.

Держи этот контраст в голове всё приложение. Почти каждое различие ниже —
его следствие.

## 2. Класс и файлы

И там, и там объявление отделяют от реализации. Но в C++ это твой выбор
(можно всё в заголовке), а в Objective-C — жёсткое разделение на два
ключевых слова.

```cpp
// Greeter.hpp
class Greeter {
public:
    Greeter(std::string name);   // объявление
    std::string hello() const;
    int times = 0;               // поле прямо в классе
private:
    std::string name_;
};

// Greeter.cpp
Greeter::Greeter(std::string name) : name_(std::move(name)) {}
std::string Greeter::hello() const { return "Привет, " + name_; }
```

```objc
// Greeter.h
@interface Greeter : NSObject
@property (nonatomic, copy) NSString *name;   // объявление свойства
@property (nonatomic) NSInteger times;
- (instancetype)initWithName:(NSString *)name;
- (NSString *)hello;
@end

// Greeter.m
@implementation Greeter
- (instancetype)initWithName:(NSString *)name {
    self = [super init];
    if (self) { _name = [name copy]; }
    return self;
}
- (NSString *)hello {
    return [NSString stringWithFormat:@"Привет, %@", _name];
}
@end
```

В чём разница:

- В C++ `class` — одно ключевое слово, заголовок и `.cpp` — твоё
  соглашение. В Objective-C интерфейс (`@interface … @end`) и реализация
  (`@implementation … @end`) — это синтаксис языка. Интерфейс кладут в
  `.h`, реализацию в `.m`.
- В Objective-C **нет инлайна тела метода в заголовке**. Нельзя написать
  `- (int)x { return 5; }` в `@interface`. Тело всегда в
  `@implementation`. Заголовочного `inline`-метода как в C++ просто не
  существует — диспетчеризация всё равно динамическая, инлайнить нечего.
- Базовый класс указывают через двоеточие — `: NSObject`. Почти всё в
  Foundation растёт из `NSObject` (см. приложение A); своя иерархия без
  него — редкость.
- Шаблона нет: один заголовок — один конкретный класс, не специализация.

## 3. Вызов метода против отправки сообщения

Это главное различие, и у него есть драматическое практическое следствие.

```cpp
Greeter *g = getGreeter();      // может вернуть nullptr
// g->hello() при g == nullptr — undefined behavior (разыменование).
// Защищаться надо РУЧНОЙ проверкой:
if (g != nullptr) {
    std::cout << g->hello();
}
```

```objc
Greeter *g = getGreeter();      // может вернуть nil
// [g hello] при g == nil — БЕЗОПАСНО. Вернётся nil, ничего не падает.
NSString *s = [g hello];        // если g == nil, s == nil — и всё
```

В C++ `g->hello()` для невиртуального метода компилятор превращает в
прямой `call` по известному адресу (для виртуального — в косвенный через
vtable). В обоих случаях получатель обязан существовать: вызов у
`nullptr` — UB. На практике виртуальный вызов почти наверняка упадёт, а
невиртуальный, не трогающий полей, может и «сработать» — что ещё хуже:
баг прячется до поры.

В Objective-C `[g hello]` компилятор превращает в
`objc_msgSend(g, @selector(hello))` (см. главу 14). Эта функция **первым
делом проверяет получателя на `nil`** и, если он `nil`, тихо возвращает
ноль нужного размера — `nil`, `0`, `NO`, `0.0` (см. главу 5). Программа
не падает. Это сознательное решение языка, а не случайность.

Проверяется это парой `code/g-nil-vs-null.cpp` и `code/g-nil-vs-null.m`.
C++ при `nullptr` обязан уклониться от вызова, иначе UB:

```text
g == nullptr, метод НЕ вызван (иначе UB/краш)
length = 5, upper = HELLO
```

Objective-C спокойно шлёт сообщения `nil` и получает нули:

```text
length        = 0
uppercaseStr  = (null)
hasPrefix     = 0
real length   = 5
real upper    = HELLO
```

Плюс: код Cocoa почти не обвешан проверками `if (x != nil)` — отправка
`nil` безвредна. Минус: если объект случайно стал `nil`, ошибка не
выстрелит сразу, а «размажется» нулями по логике, и баг всплывёт позже.
C++-привычка «получил указатель — проверь» в Objective-C превращается в
«получил неожиданный 0/nil — ищи, где по дороге был `nil`-получатель».

> **Отличие от C++.** `obj->method()` — диспетчеризация на этапе
> компиляции (прямой вызов) или через vtable (virtual). `[obj method]` —
> поиск метода по имени в рантайме, начиная с защиты от `nil`. Та же
> операция «позвать поведение объекта», но в разных временах: у C++ —
> почти всегда compile-time, у Objective-C — всегда run-time.

## 4. Типы и полиморфизм

В C++ полиморфизм надо *включить*: общий базовый класс плюс `virtual`. В
Objective-C он включён всегда, и общего предка не требует.

```cpp
struct Animal {
    virtual ~Animal() = default;
    virtual std::string speak() const = 0;   // без virtual — статика
};
struct Dog : Animal { std::string speak() const override { return "гав"; } };

std::unique_ptr<Animal> a = std::make_unique<Dog>();
a->speak();          // динамически — потому что virtual + общий базовый
```

```objc
@interface Dog : NSObject @end       // общего предка со speak у них нет
@interface Duck : NSObject @end

id animal = someAnimal();
if ([animal respondsToSelector:@selector(speak)]) {
    [animal speak];          // динамически ВСЕГДА, общий предок не нужен
}
```

В чём разница:

- **Методы Objective-C «виртуальные» по умолчанию.** Нет ключевого слова
  `virtual`, нет `override`. Каждое сообщение идёт через `objc_msgSend`, то
  есть реализация выбирается в рантайме. Аналог «невиртуального вызова ради
  скорости» появился в Clang лишь недавно и как расширение: атрибут
  `__attribute__((objc_direct))` превращает метод в прямой вызов Си-функции
  — зато такой метод пропадает из рантайма (его не найти по селектору, не
  переопределить, не подменить). В обычном коде им почти не пользуются.
- Поэтому **полиморфизм не требует общей базы**. В C++ положить `Dog` и
  `Duck` в один контейнер и звать `speak()` через виртуальный вызов можно,
  только если у них общий полиморфный предок (обходные пути вроде
  `std::variant` + `std::visit` требуют заранее знать весь список типов). В Objective-C достаточно, чтобы оба отвечали на
  селектор `speak` — это duck typing в буквальном смысле (см.
  `code/g-poly.m`).
- Тип **`id`** — это «любой объект», стираемый указатель без статических
  гарантий. Под `id` компилятор пропускает любое объявленное где угодно
  сообщение. Это твой аналог `void*` + «доверься рантайму», но безопаснее:
  непонятое сообщение не UB, а контролируемое исключение (глава 14).

Запусти обе программы. C++ через vtable:

```text
гав (это Dog)
мяу
```

Objective-C через сообщения к неродственным классам:

```text
Dog -> гав
   (это Dog)
Duck -> кря
```

Нюанс про «нет override»: переопределение метода в подклассе работает,
просто пишется без ключевого слова — ты объявляешь метод с тем же
селектором, и он перекрывает родительский. Защиты от опечатки в имени
(как `override` в C++) язык не даёт; ошибёшься в селекторе — получишь
новый метод вместо переопределения, молча.

## 5. Шаблоны против lightweight generics

Здесь Objective-C проигрывает вчистую, и это надо понимать сразу.

```cpp
template <typename T>
T max_of(T a, T b) { return a > b ? a : b; }

std::vector<int> v;        // настоящее инстанцирование под int
max_of(3, 7);              // инстанцируется max_of<int>
```

```objc
// Lightweight generics: ТОЛЬКО подсказка компилятору.
NSArray<NSString *> *names = @[@"Серик"];
NSString *first = names.firstObject;   // компилятор знает тип -> без каста

// В рантайме параметр типа стёрт: это обычный NSArray из id.
```

В чём разница:

- C++-шаблоны — это **мономорфизация**: компилятор генерирует отдельный
  машинный код под каждый набор типов. `std::vector<int>` и
  `std::vector<double>` — разные типы с разным кодом. На шаблонах же
  стоят метапрограммирование, трейты, SFINAE и (с C++20) концепты.
- ObjC lightweight generics (`NSArray<NSString *> *`) — это **только
  аннотация для компилятора**, чтобы он проверял типы на этапе сборки и
  избавлял от лишних кастов. В рантайме параметр **стирается** (type
  erasure): остаётся обычный `NSArray`, хранящий `id`. Никакого
  специализированного кода не генерируется.
- Аналога шаблонного метапрограммирования в Objective-C **нет вообще**.
  Generic-обобщения по типу делают через `id` и динамику, а не через
  генерацию кода. Если тебе нужна compile-time-генерация — это территория
  C++ (и .mm-файлов, тема 17).

## 6. Наследование

```cpp
// C++: множественное наследование + абстрактные классы.
struct Drawable { virtual void draw() const = 0; };
struct Serializable { virtual std::string encode() const = 0; };
class Widget : public Drawable, public Serializable { /* … */ };
```

```objc
// Objective-C: одиночное наследование классов + НЕСКОЛЬКО протоколов.
@protocol Drawable      <NSObject> - (void)draw; @end
@protocol Serializable  <NSObject> - (NSString *)encode; @end

@interface Widget : NSObject <Drawable, Serializable>
@end
```

В чём разница:

- Класс в Objective-C наследует **ровно один** суперкласс. Множественного
  наследования классов нет.
- Роль «множественности» играют **протоколы** (`@protocol`). Протокол ≈
  чисто абстрактный класс / интерфейс из C++: набор объявлений методов
  (и свойств) без реализации. Класс может принять сколько угодно
  протоколов — отсюда «много интерфейсов, один базовый класс».
- Ключевое отличие протокола от абстрактного класса C++: **у протокола
  нет состояния**. Он не несёт полей (ivars) и не даёт реализации по
  умолчанию. То есть это интерфейс в чистом виде, без «миксина с данными».
  Diamond-проблемы наследования данных просто не возникает — наследовать
  данные не от кого.
- В протоколе методы бывают `@required` (по умолчанию) и `@optional`.
  Опциональных методов в абстрактном классе C++ нет — там либо чисто
  виртуальный, либо нет. Перед вызовом опционального метода спрашивают
  `respondsToSelector:`.

Если нужна общая реализация для нескольких классов без общего предка — в
C++ ты бы взял CRTP или миксин-наследование. В Objective-C категории на
протокол нет (это возможность Swift, protocol extension): общую реализацию
кладут в категорию на общий базовый класс (хоть на `NSObject`) или в
свободную функцию; см. следующую тему.

## 7. Расширение классов: категории

Это приём, аналога которому в C++ нет, и он часто удивляет сильнее всего.

```cpp
// C++: дописать метод в std::string НЕЛЬЗЯ.
// Только свободная функция или свой наследник.
std::string shout(const std::string &s) {
    std::string r = s;
    for (char &c : r)
        c = static_cast<char>(std::toupper(static_cast<unsigned char>(c)));
    return r + "!";
}
shout(name);     // вызов «снаружи», не name.shout()
```

```objc
// Objective-C: КАТЕГОРИЯ добавляет метод прямо в чужой класс — NSString.
@interface NSString (Shout)
- (NSString *)shout;
@end
@implementation NSString (Shout)
- (NSString *)shout {
    return [[self uppercaseString] stringByAppendingString:@"!"];
}
@end

[@"привет" shout];     // теперь ЛЮБАЯ строка умеет shout как родной метод
```

В чём разница:

- В C++ изменить готовый класс (тем более чужой/системный) невозможно:
  можно унаследоваться или написать свободную функцию. Метод появляется
  «снаружи», синтаксис вызова другой.
- Категория Objective-C добавляет метод **в сам класс** во время загрузки
  образа. После этого `shout` есть у любого `NSString` в программе, как
  встроенный, и зовётся обычным сообщением `[s shout]`. Подкласс не
  создаётся (см. главу 11).
- Цена гибкости: категория **не может добавить хранимое поле** (ivar) —
  только методы. Если нужно «прицепить» данные к чужому классу,
  используют associated objects из рантайма. Для своих новых полей есть
  расширения класса (class extension, безымянная категория в `.m`).
- Ещё цена — глобальность: категория меняет класс для **всей** программы.
  Два конфликтующих метода с одним селектором в разных категориях — и кто
  победит, не определено. Дисциплина та же, что со swizzling.

Запуск `code/g-category.m` показывает, что метод доступен и литералам, и
строкам из недр Foundation:

```text
ПРИВЕТ!
T!
A!
BB!
CCC!
```

## 8. Память: ARC против RAII

Обе модели детерминированные (не трассирующий GC). Прямой аналог ARC в
C++ — не RAII вообще, а `std::shared_ptr`: оба считают ссылки. Но устроены
они по-разному.

```cpp
{
    auto obj   = std::make_shared<Node>();   // сильная ссылка, refcount=1
    auto alias = obj;                        // refcount=2
    std::weak_ptr<Node> w = obj;             // слабая, не держит
}   // здесь Node разрушается ДЕТЕРМИНИРОВАННО, на закрывающей скобке
```

```objc
{
    Node *obj = [[Node alloc] init];   // strong по умолчанию, retain=1
    Node *alias = obj;                 // retain=2 (ARC вставит retain)
    __weak Node *w = obj;              // слабая, не держит, занулится сама
}   // ARC вставит release; объект освободится, когда retain дойдёт до 0
```

Сопоставление почти один в один:

| C++ | Objective-C (ARC) |
| --- | --- |
| `std::shared_ptr<T>` | `strong`-ссылка |
| `std::weak_ptr<T>` | `weak`-ссылка |
| цикл `shared_ptr ⇄ shared_ptr` (утечка) | retain cycle |
| разрыв цикла через `weak_ptr` | разрыв через `weak` |
| деструктор `~T()` | `-dealloc` |

Где аналогия ломается — и это важно для C++-головы:

- **В Objective-C объекты всегда в куче и всегда по указателю.** Нет
  value-объектов на стеке, нет `Node n;` с автоматическим хранением. Любой
  объект — это `Node *`, рождённый `alloc`/`init`. Отсюда нет copy-ctor,
  move-ctor, RVO — этих понятий просто негде применить к объектам.
- **Нет деструкторов, привязанных к области видимости.** `-dealloc`
  детерминирован по счётчику ссылок: он приходит, когда счётчик дошёл до
  нуля. Локальную strong-переменную ARC отпускает не позже `}`, но
  спецификация Clang разрешает ему сделать это **раньше** — сразу после
  последнего использования (если не пометить переменную
  `__attribute__((objc_precise_lifetime))`). Деструктор C++ гарантированно
  зовётся ровно на `}`. Поэтому RAII-идиома «ресурс жив ровно до конца
  scope» (`lock_guard`, scope guard) на объектах Objective-C ненадёжна:
  ты управляешь не scope, а тем, кто держит strong-ссылку. Ресурс,
  который надо закрыть в точный момент, закрывают явным вызовом
  (`close`, `invalidate`).
- **`weak` сам зануляется.** Когда объект умирает, все `__weak`-указатели
  на него автоматически становятся `nil` (zeroing weak references). У
  `std::weak_ptr` иначе: сам объект `weak_ptr` не «обнуляется», ты узнаёшь
  о смерти только через `.lock()`/`.expired()`. В Objective-C можно прямо
  проверить `if (w != nil)`. Но в многопоточном коде объект может умереть
  сразу после проверки, поэтому идиома та же, что с `.lock()`: прочитать
  `weak` один раз в сильную локальную и работать с ней.
- ARC — это не библиотека, а **работа компилятора**: он вставляет
  `retain`/`release`/`autorelease` за тебя по правилам владения (глава
  13). Это ближе к «компилятор расставил `shared_ptr`-операции», чем к
  отдельному типу умного указателя.

## 9. Свойства

```cpp
class Person {
public:
    const std::string &name() const { return name_; }   // геттер вручную
    void setName(std::string n) { name_ = std::move(n); }
    int age = 0;                                         // или публичное поле
private:
    std::string name_;
};
// KVO/наблюдения за изменением поля — нет в языке.
```

```objc
@interface Person : NSObject
@property (nonatomic, copy)   NSString *name;   // геттер+сеттер генерятся
@property (nonatomic, assign) NSInteger age;
@end
// person.name = @"…";  ->  [person setName:@"…"]  (это сообщение)
// person.name          ->  [person name]
```

В чём разница:

- `@property` — это не поле, а **декларация пары сообщений** геттер/сеттер
  плюс (обычно) скрытый ivar `_name`. Компилятор синтезирует и аксессоры,
  и хранилище. Точечный синтаксис `person.name` — синтаксический сахар над
  отправкой сообщения, а не доступ к памяти, как `obj.field` в C++.
- Атрибуты в скобках задают семантику владения и потокобезопасность:
  `copy`/`strong`/`weak`/`assign`, `nonatomic`/`atomic`, `readonly`. В
  C++ это ты пишешь руками в сеттере. `copy` у `NSString`-свойства —
  важная идиома (immutable-копия на входе), прямого аналога у `std::string`
  нет, потому что там присваивание и так копирует значение.
- Главный бонус, которого в C++ нет в языке: свойства автоматически
  участвуют в **KVC** (доступ по строковому ключу: `[obj valueForKey:@"name"]`)
  и **KVO** (наблюдение за изменением, глава 20). Это рантайм-магия поверх
  сеттеров-сообщений; в C++ такого встроенного механизма наблюдения нет —
  его собирают руками (сигналы/слоты, observer-паттерн).

## 10. Перегрузка: её нет

```cpp
// C++: перегрузка функций и операторов — норма.
double area(double s)        { return s * s; }
double area(double w, double h) { return w * h; }  // то же имя, иные параметры
Vec2 operator+(Vec2 a, Vec2 b);                      // operator overloading
```

```objc
// Objective-C: НЕТ ни перегрузки функций/методов, ни перегрузки операторов.
// Каждый селектор уникален. «Разные сигнатуры» = разные ИМЕНА.
- (instancetype)initWithName:(NSString *)name;
- (instancetype)initWithName:(NSString *)name age:(NSInteger)age;
```

В чём разница:

- Имя метода Objective-C — это **селектор целиком**, со всеми двоеточиями
  (глава 5). `initWithName:` и `initWithName:age:` — два разных имени, а не
  одна перегруженная функция. Поэтому методы называют длинно и описательно:
  имя обязано быть уникальным и заодно объясняет каждый аргумент прямо в
  точке вызова.
- Перегрузки **функций/методов по типам аргументов нет**: нельзя завести
  два метода `setValue:` с разными типами — это один селектор. Если нужны
  варианты, придумывают разные имена (`setIntValue:`, `setStringValue:`).
- Перегрузки **операторов нет**: `+` и `==` для своих классов не
  переопределяются (`==` у объектов всегда сравнивает указатели).
  Сравнение по содержимому — это сообщение (`isEqual:`/
  `isEqualToString:`), сложение — метод (`arrayByAddingObject:`).
  Единственное исключение — сабскрипты: `obj[i]` и `obj[key]` компилятор
  превращает в сообщения `objectAtIndexedSubscript:`/
  `objectForKeyedSubscript:` (и парные `set…`), так что своему классу
  «`[]`» можно дать, просто реализовав эти методы. Но это соглашение об
  именах, а не настоящий `operator[]`.

Проверка C++-стороны — `code/g-overload.cpp`:

```text
9
10
площадь фигуры X
(4, 6)
```

В Objective-C каждую из этих «перегрузок» пришлось бы назвать отдельным
селектором.

## 11. Пространства имён: их тоже нет

```cpp
namespace net { class Socket {}; }
namespace ui  { class Socket {}; }   // ок, разные пространства
net::Socket s;
```

```objc
// Objective-C: namespace НЕТ. Уникальность — через ПРЕФИКСЫ в имени класса.
@interface NSString : NSObject @end   // NS  = NeXTSTEP / Foundation
// CFArrayRef                         // CF  = Core Foundation (Си-тип)
@interface SRKSocket : NSObject @end   // свой трёхбуквенный префикс
```

В чём разница:

- В Objective-C **плоское глобальное пространство имён классов**: имя
  класса должно быть уникально на всю программу, включая все слинкованные
  фреймворки. `namespace`, вложенности, `using` — ничего этого нет.
- Поэтому коллизии разводят **префиксами**: `NS` (Foundation/AppKit
  исторически от NeXTSTEP), `CF` (Core Foundation), `UI` (UIKit), `CA`
  (Core Animation). Двухбуквенные префиксы Apple оставляет себе, поэтому
  свои классы префиксуют **тремя** буквами и больше — чтобы не
  столкнуться с будущими системными именами.
- Это касается и `@protocol`, и категорий, и даже Си-функций C-уровня
  рантайма. Дисциплина именования заменяет языковой механизм.

## 12. Интроспекция против RTTI

Здесь Objective-C берёт убедительный реванш за шаблоны.

```cpp
// C++ RTTI: скромный набор, требует полиморфного типа (есть virtual).
Animal *a = get();
if (Dog *d = dynamic_cast<Dog *>(a)) { /* это Dog */ }
const std::type_info &t = typeid(*a);
std::cout << t.name();      // искажённое имя, без списка методов/полей
```

```objc
// Objective-C runtime: объект знает о себе почти всё (глава 14).
if ([obj isKindOfClass:[Dog class]]) { /* это Dog или его потомок */ }
if ([obj respondsToSelector:@selector(speak)]) { [obj speak]; }

unsigned int n;
Method *m = class_copyMethodList([obj class], &n);   // СПИСОК методов
// + class_copyIvarList, class_getSuperclass, swizzling,
//   добавление методов на лету
free(m);
```

В чём разница:

- C++ RTTI — это `typeid` и `dynamic_cast`; динамический ответ они дают
  лишь для полиморфных типов. Ты можешь спросить «этот ли тип» и привести вниз по иерархии.
  Перечислить методы или поля класса в рантайме нельзя — после компиляции
  их структуры в программе нет.
- Objective-C-объект **носит знание о себе с собой** через поле `isa` и
  живой объект класса. В рантайме доступны: имя класса, цепочка
  суперклассов, полный список методов и ivar'ов, проверки
  `isKindOfClass:`/`respondsToSelector:`/`conformsToProtocol:`, добавление
  методов (`class_addMethod`), подмена реализаций (swizzling), пересылка
  сообщений. На этом построены KVO, сериализация, DI-фреймворки и половина
  отладочного инструментария (глава 14).
- Практически: где C++ требует знать тип статически или городить
  visitor-паттерн, Objective-C спрашивает объект напрямую во время работы.
  Цена — та самая динамика и чуть меньшая скорость.

## 13. Строки и контейнеры: семантика копирования

Тонкое место, на котором C++-разработчик спотыкается чаще всего.

```cpp
std::vector<std::string> a{"apple", "banana"};
std::vector<std::string> b = a;   // ГЛУБОКАЯ КОПИЯ: b независим от a
b.push_back("cherry");
b[0] = "APPLE";
// a по-прежнему {apple, banana}; &a[0] != &b[0]
```

```objc
NSMutableArray *a = [@[@"apple", @"banana"] mutableCopy];
NSMutableArray *b = a;            // копируется только УКАЗАТЕЛЬ: один объект
[b addObject:@"cherry"];
b[0] = @"APPLE";
// a ТОЖЕ изменился: a и b — это один и тот же массив в куче
```

В чём разница:

- `std::string`/`std::vector` — **value-типы**. Сам объект живёт на стеке
  или инлайн внутри владельца (буфер элементов — в куче, но им владеет
  только он), присваивание = глубокая копия, передача в функцию по
  значению копирует, по `const&` — нет. Семантика значения, как у `int`.
- `NSString`/`NSArray` — **объекты в куче по ссылке**. Переменная — это
  указатель; присваивание копирует **указатель**, а не содержимое. Два
  имени смотрят на один объект, и правка через одно видна через другое.
  Это reference-семантика, как у `shared_ptr<vector>`, а не у `vector`.
- Чтобы получить независимую копию, её **просят явно**: `[obj copy]`
  (immutable-копия) или `[obj mutableCopy]`. Это контракт протоколов
  `NSCopying`/`NSMutableCopying` (приложение A).
- Отсюда же пары immutable/mutable: `NSString`/`NSMutableString`,
  `NSArray`/`NSMutableArray`. В C++ изменяемость регулирует `const`, и тип
  один; в Objective-C это **два разных класса**, причём mutable —
  наследник immutable.

Сравни вывод. C++ (`code/g-copy-semantics.cpp`) — два независимых вектора:

```text
a.size() = 2, a[0] = apple
b.size() = 3, b[0] = APPLE
&a[0] == &b[0]? no
```

Objective-C (`code/g-copy-semantics.m`) — один объект на два имени, пока
не попросили `mutableCopy`:

```text
a.count = 3, a[0] = APPLE
b.count = 3, b[0] = APPLE
a == b (один объект)? да
после mutableCopy: a.count = 3, c.count = 4
```

> **Отличие от C++.** `=` у `std::vector` — это копирование значения; у
> `NSArray *` — копирование указателя. Если в C++-голове сидит «присвоил —
> значит скопировал», в Objective-C это источник коварных багов: ты
> поменял `b`, а сломался `a`.

## 14. Исключения

Идиома обработки ошибок различается принципиально, и это не вкусовщина.

```cpp
// C++: исключения — ШТАТНЫЙ механизм ошибок, дружат с RAII.
try {
    auto data = readFile(path);     // бросит при ошибке
    process(data);                  // деструкторы раскрутят ресурсы
} catch (const std::runtime_error &e) {
    log(e.what());
}
```

```objc
// Objective-C: recoverable-ошибки — через NSError **, а НЕ исключения.
NSError *error = nil;
NSData *data = [NSData dataWithContentsOfFile:path
                                     options:0
                                       error:&error];
if (!data) {                         // вернул nil -> смотрим error
    NSLog(@"%@", error.localizedDescription);
    return;
}
// @try/@catch существует, но он для ПРОГРАММЕРСКИХ ошибок (баг в коде):
@try { [arr objectAtIndex:999]; }
@catch (NSException *e) { NSLog(@"баг: %@", e.reason); }
```

В чём разница:

- В C++ исключения — нормальный путь сообщения об ошибке, и они работают в
  связке с RAII: при раскрутке стека деструкторы автоматически
  освобождают ресурсы. `throw`/`catch` — повседневный инструмент.
- В Objective-C исключения (`@throw`/`@try`/`@catch`/`NSException`)
  зарезервированы под **ошибки программиста** — выход за границы массива,
  unrecognized selector, нарушение контракта. Их **не** ловят, чтобы
  «продолжить работу»; они сигнализируют о баге, который надо чинить.
- Ожидаемые, восстановимые ошибки (файла нет, сеть упала, JSON битый)
  передают через **`NSError **`** — выходной параметр-указатель: метод
  возвращает `nil`/`NO` при неудаче и заполняет `error` (глава 18). Это
  ближе к C++ `std::expected` (C++23)/кодам возврата, чем к исключениям.
- Практическое следствие для C++-головы: код Objective-C не рассчитан на
  раскрутку исключением. Под ARC в `.m` по умолчанию даже сильные локальные
  переменные при `@throw` не отпускаются (нужен флаг
  `-fobjc-arc-exceptions`; в `.mm` он включён по умолчанию), а Cocoa-код
  между `@throw` и `@catch` может остаться в полусломанном состоянии.
  Поэтому исключениями не «рулят» потоком.

## 15. Блоки против лямбд

Близкие родственники, но с разным синтаксисом захвата.

```cpp
int base = 10;
auto byValue = [base](int x) { return base + x; };   // [=]-стиль: копия
auto byRef   = [&base](int x) { return base + x; };  // [&]: по ссылке
auto counter = [n = 0]() mutable { return ++n; };    // изменяемое состояние
std::function<void(const std::string&)> f = [](auto s){ /*…*/ };  // тип
```

```objc
int base = 10;
int (^byCopy)(int) = ^(int x) { return base + x; };  // копия, как [=]
__block int counter = 0;                // __block: по ссылке + mutable
void (^tick)(void) = ^{ counter++; };
typedef int (^IntTransform)(int);       // тип блока через typedef
```

Сопоставление:

- `^{ … }` — это блок, замыкание Objective-C. По умолчанию он **копирует**
  захваченные переменные (как `[=]` в C++). Захваченное только читается;
  присвоить ему внутри нельзя.
- Чтобы менять захваченную переменную, её помечают **`__block`**. Это
  совмещает в себе и захват «по ссылке» (`[&]`), и право на мутацию
  (`mutable`) из C++ — одно ключевое слово вместо двух механизмов.
- Тип блока пишут как `returnType (^name)(args)` и обычно прячут за
  `typedef` — это твой аналог `std::function<…>`/`auto`. Блок, в отличие
  от не-захватывающей C++-лямбды, не конвертируется в указатель на функцию.
  (Обратное есть: в `.mm` под ARC C++-лямбду можно присвоить переменной
  блочного типа.)
- Память: блоки участвуют в ARC. Захват `self` сильной ссылкой в
  долгоживущем блоке — классический retain cycle (аналог двух
  `shared_ptr` друг на друга); лечится `__weak`-копией `self`, как
  `weak_ptr` в C++.

Вывод совпадает по смыслу. C++ (`code/g-blocks.cpp`):

```text
byValue(5) = 15
byRef(5)   = 105
counter: 123
Привет, C++!
sum = 10
```

Objective-C (`code/g-blocks.m`):

```text
addByCopy(5) = 15
counter = 3
sum = 10
```

## 16. const, ссылки и параметры

```cpp
void greet(const std::string &name);   // ссылка, без копии, const-correct
int &ref = x;                           // ссылки как полноценный тип
const Widget &w = makeWidget();         // const-correctness пронизывает API
```

```objc
- (void)greet:(NSString *)name;   // объект ВСЕГДА указатель, ссылок нет
// NSString * const ptr — const на сам указатель, не на «глубину»
```

В чём разница:

- В Objective-C (в `.m`) **нет ссылок** (`&`). Объекты передаются и
  хранятся только как указатели. «Ссылочный» параметр-выход делают через
  указатель на указатель: `NSError **`, `id *` (тема 14).
- **`const`-correctness ограничен.** `const` применим к Си-типам и к
  самому указателю (`NSString * const p`), но «глубокой» константности
  объекта, как `const Widget&`, в системе типов нет. Неизменяемость
  объекта выражают не `const`, а **отдельным классом** (`NSString` vs
  `NSMutableString`) — см. тему 13.
- Поэтому привычные C++-приёмы «передал по `const&`, чтобы без копии и без
  правки» в Objective-C не нужны и невыразимы: объект и так передаётся
  указателем (без копии), а защита от правки — это выбор immutable-класса.

(Ссылки `&` и `const Widget&` снова станут доступны в `.mm`-файлах — там
работает полноценный C++, тема 17.)

## 17. Objective-C++ (.mm): главное практическое

Вот ради чего C++-разработчику вообще стоит читать про Objective-C: их
можно **смешивать в одном файле**. Файл с расширением `.mm` компилируется
как Objective-C++ (`clang++ -ObjC++`), и в нём доступны оба языка
целиком: `std::string` и `NSString`, шаблоны и сообщения, RAII и ARC.

Можно держать C++-объект полем ObjC-класса и звать C++ из методов:

```objc
// .mm — C++-объекты как ivar, C++ вызывается из метода Objective-C.
@implementation Sample {
    Stats       _stats;    // обычный C++-класс с std::vector внутри
    std::string _label;    // std::string как ivar
}
- (void)addValue:(double)v { _stats.add(v); }   // зовём C++ из ObjC-метода
- (double)mean             { return _stats.mean(); }
@end
```

И наоборот — звать Objective-C из обычной C++-функции:

```objc
// .mm — Foundation внутри чистой C++-функции.
static std::string normalize(const std::string &input) {
    @autoreleasepool {
        NSString *s = [NSString stringWithUTF8String:input.c_str()];
        NSString *up = [[s stringByTrimmingCharactersInSet:
            [NSCharacterSet whitespaceCharacterSet]] uppercaseString];
        return std::string([up UTF8String]);   // NSString -> std::string
    }
}
```

Запусти оба файла. `code/g-interop.mm` — C++-контейнеры внутри ObjC-класса:

```text
mean = 3.70
sample: mean=3.70, sorted=[1.0 1.5 3.0 4.0 9.0 ]
```

`code/g-interop-call.mm` — Objective-C из C++-функции:

```text
'  привет  ' -> 'ПРИВЕТ' (len=6)
'Objective-C++' -> 'OBJECTIVE-C++' (len=13)
'  mix  ' -> 'MIX' (len=3)
```

Грабли, о которых надо знать заранее:

- **Деструкторы C++-полей.** Для класса с C++-ivar'ами компилятор
  генерирует скрытый метод `.cxx_destruct`, и runtime зовёт его, когда
  объект уничтожается (после `-dealloc`), — это тот самый метод, что мы
  видели в дампе методов в главе 14. Он есть и без ARC. То есть `std::vector`/
  `std::string` как ivar честно разрушаются, без ручного кода. Симметрично
  есть `.cxx_construct` для их конструирования.
- **C++-ivar должен быть default-constructible.** Компилятор
  инициализирует ivar'ы при создании объекта, поэтому C++-поле обязано
  иметь конструктор по умолчанию. Тип без него (например, требующий
  аргумент) напрямую в ivar не положить — заворачивай в указатель,
  `std::optional` или `std::unique_ptr`.
- **Ссылку (`&`) в ivar положить нельзя.** Ссылка не имеет «пустого»
  состояния и не переназначается, а ivar'ы создаются до твоего `init`.
  Нужна косвенность — храни указатель.
- **Кодировка при `%s`.** `%s` в `NSString`/`NSLog` трактует
  Си-строку в системной кодировке, а не обязательно UTF-8 — кириллица из
  `std::string` через `%s` может исказиться. Конвертируй явно через
  `[NSString stringWithUTF8String:…]` и печатай `%@`.
- **Один `.mm` тянет за собой C++-рантайм.** Смешивать дёшево в плане
  кода, но `.mm` компилируется дольше и подключает libc++. Чисто
  ObjC-файлы оставляй `.m`, переводи в `.mm` только те, где реально нужен
  C++.

Именно так в экосистеме Apple живут кроссплатформенные C++-ядра под
нативным UI: бизнес-логика и алгоритмы на C++ (общие с Android/Windows),
а тонкий слой UI и интеграции с Cocoa — на Objective-C, и стыкуются они в
`.mm`.

## 18. Когда что — и сводка

Грубое, но рабочее правило выбора:

- **C++** — когда нужен перформанс «к металлу», zero-overhead абстракции,
  value-семантика, шаблонное обобщение, кроссплатформенность, контроль над
  каждым байтом и каждым тактом.
- **Objective-C** — когда работаешь с Cocoa/Foundation, нужна динамика
  рантайма (KVO, target-action, пересылка, категории, сериализация),
  гибкость «спросить объект в рантайме» важнее последней наносекунды.
- **Вместе** — в экосистеме Apple их мешают через `.mm`: C++-ядро плюс
  ObjC-обвязка к системным фреймворкам.

Сводная таблица «C++ → аналог в Objective-C»:

| C++ | Objective-C |
| --- | --- |
| vtable / virtual call | `objc_msgSend` (всегда динамически) |
| `template<T>` (мономорфизация) | lightweight generics (стираются в рантайме) |
| `std::shared_ptr` | `strong`-ссылка (ARC) |
| `std::weak_ptr` | `weak`-ссылка (само-зануляющаяся) |
| `~T()` по выходу из scope | `-dealloc` по обнулению счётчика |
| `dynamic_cast` / `typeid` | `isKindOfClass:` / `respondsToSelector:` + runtime |
| абстрактный класс / интерфейс | `@protocol` (без состояния) |
| множественное наследование | один суперкласс + несколько протоколов |
| свободная функция над чужим типом | категория (`@interface NSString (X)`) |
| `namespace` | префиксы имён (`NS`, `CF`, свой) |
| лямбда `[](){}` | блок `^{ }` |
| `[&]` / `mutable` захват | `__block` |
| `std::function<…>` | `typedef`-тип блока |
| `std::string` (value) | `NSString *` (heap, по ссылке) |
| `std::vector` (value, копия при `=`) | `NSArray *` (по ссылке, `copy` явно) |
| `const` / immutable через `const` | отдельный immutable-класс |
| RAII | ARC |
| исключения как штатные ошибки | `NSError **` (исключения — для багов) |
| перегрузка функций/операторов | нет — уникальные селекторы |

## Проверяем

Все файлы приложения лежат в `code/` с префиксом `g-`. Команды сборки по
языкам:

```text
# Objective-C (.m)
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/g-ИМЯ.m  -o /tmp/t && /tmp/t

# C++ (.cpp)
clang++ -std=c++17 -Wall -Wextra -O2 \
    code/g-ИМЯ.cpp -o /tmp/t && /tmp/t

# Objective-C++ (.mm)
clang++ -ObjC++ -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/g-ИМЯ.mm -o /tmp/t && /tmp/t
```

Файлы и что показывают:

- `g-nil-vs-null.cpp` / `g-nil-vs-null.m` — UB при вызове у `nullptr`
  против безопасного сообщения к `nil`.
- `g-copy-semantics.cpp` / `g-copy-semantics.m` — глубокая копия
  `std::vector` против копирования указателя у `NSMutableArray`.
- `g-blocks.cpp` / `g-blocks.m` — лямбды и захват против блоков и
  `__block`.
- `g-poly.cpp` / `g-poly.m` — виртуальная диспетчеризация против duck
  typing на `id` + `respondsToSelector:`.
- `g-overload.cpp` — перегрузка функций и операторов (в Objective-C её
  нет).
- `g-category.m` — категория добавляет метод прямо в `NSString`.
- `g-interop.mm` — C++-объекты (`Stats`, `std::string`) как ivar
  ObjC-класса; C++ зовётся из ObjC-методов.
- `g-interop-call.mm` — Objective-C/Foundation внутри чистой
  C++-функции.

Все двенадцать собираются под `-Wall -Wextra` **без единого
предупреждения**. Дата, время и числа в скобках у строк `NSLog` будут
твои.
