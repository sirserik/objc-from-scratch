# Приложение F. Задачи собеседования: Senior

Junior проверял механику, Middle — модель владения и контракты классов. На
Senior спрашивают про то, что крутится **под капотом**: как устроены `isa`
и метаклассы, как `objc_msgSend` ищет метод, три шанса пересылки, swizzling,
связанные объекты, KVO изнутри, и отдельно — многопоточность: гонки,
синглтоны, барьеры, дедлоки, пулы автоосвобождения в фоне. Здесь почти нет
ответов в одну строку: за каждым вопросом стоит runtime или модель потоков.

Формат прежний. Сначала **условие**. Если задача про «что выведет» —
остановись на **подумай сам** и ответь, прежде чем читать **разбор**. Где
есть рабочий код, он лежит в `code/senior-NN-имя.m`, собран и запущен, и
весь показанный вывод — настоящий. Дату, имя программы и число в скобках,
которые `NSLog` печатает в начале строки, здесь убрали — у тебя они будут
свои.

Собрать и запустить любой файл:

```text
clang -fobjc-arc -framework Foundation -Wall -Wextra -O2 \
    code/senior-01-metaclass.m -o /tmp/t && /tmp/t
```

Часть задач — концептуальные, без файла в `code/`: они или уронили бы
программу (дедлок, сломанный swizzling), или их результат не определён
(две категории), или это разбор словами (исключения, пулы в фоне). Такие
помечены прямо в тексте.

Идём от runtime к потокам и краевым случаям, от сложного к очень сложному.

## Задача 1. Куда указывает `isa` класса и где живут методы класса

**Условие.** Есть класс `Tool` с методом экземпляра `-use` и методом
класса `+build`. Ответь, не запуская:

- куда указывает `isa` самого класса `Tool`;
- в чьей таблице методов лежит `-use`, а в чьей `+build`;
- куда в итоге приходит цепочка `isa`, если идти `объект → класс →
  метакласс → …`.

**Подумай сам.** Если объект знает свой класс через `isa`, то что знает
через свой `isa` сам класс?

**Разбор.** Объект — это структура, чьё первое поле `isa` указывает на
класс (глава 14). Но **класс — тоже объект**, и у него тоже есть `isa`.
Указывает он на **метакласс** (metaclass) — «класс класса».

Зачем метакласс вообще нужен. Методы экземпляра (с минусом, `-use`) лежат
в таблице методов **класса**: шлёшь сообщение объекту — runtime идёт по его
`isa` в класс и ищет там. А методы класса (с плюсом, `+build`) надо где-то
держать по той же схеме. Их кладут в **метакласс**. Когда шлёшь сообщение
классу (`[Tool build]`), runtime идёт по `isa` класса в метакласс и ищет
`+build` там. Одна и та же машина поиска работает на двух уровнях.

Поэтому:

- `-use` лежит в таблице **класса** `Tool`, в метаклассе его нет;
- `+build` лежит в таблице **метакласса** `Tool`, в самом классе его нет.

Цепочка `isa` из примера: объект `t` → класс `Tool` → метакласс `Tool` →
**корневой метакласс** (метакласс `NSObject`), а его `isa` указывает сам на
себя — цепочка замыкается. Заметь: `isa` любого метакласса ведёт **сразу**
в корневой метакласс, минуя метаклассы родителей. По родителям вверх идёт
другой указатель — `superclass` (метакласс `Tool` → метакласс `NSObject` →
класс `NSObject`). В выводе последняя строка — как раз этот прыжок: `isa`
метакласса `Tool` ведёт в метакласс `NSObject`, чьё имя — `NSObject`.

Решение — `code/senior-01-metaclass.m`:

```text
isa класса Tool указывает на: Tool (метакласс? да)
-use   в классе Tool?     да
-use   в метаклассе Tool? нет
+build в классе Tool?     нет
+build в метаклассе Tool? да
цепочка isa:
  объект t        isa -> Tool
  класс Tool      isa -> Tool
  метакласс Tool  isa -> NSObject
```

Заметь тонкость вывода: у метакласса **то же имя**, что у класса, — `Tool`.
`class_getName` для метакласса возвращает имя класса. Отличить их можно
только через `class_isMetaClass` (в первой строке — «метакласс? да»).
А `-use` нашёлся только в классе, `+build` — только в метаклассе: ровно
там, где runtime их и держит.

> **Отличие от Си.** В Си у типа нет «класса своего типа» — после
> компиляции от `struct Tool` не остаётся ничего, спрашивать не у кого.
> Здесь же у класса есть свой класс (метакласс), а у того — свой (корневой
> метакласс): целая живая лесенка `isa` там, где в Си пустота.

## Задача 2. `objc_msgSend`, `SEL`, `IMP`, `Method` — кто есть кто

**Условие.** У класса `Calc` есть метод `-(int)addTo:(int)x`, который
возвращает `x + 100`. Объясни, во что компилятор превращает `[c addTo:5]`,
и что напечатают три вызова — обычная отправка, вызов через `IMP` напрямую
и вызов через `objc_msgSend`, приведённый к точной сигнатуре.

```objc
int viaMessage = [c addTo:5];                         // (1)
int (*impFn)(id, SEL, int) = (void *)impFromMethod;
int viaImp = impFn(c, sel, 5);                        // (2)
int (*send)(id, SEL, int) = (void *)objc_msgSend;
int viaSend = send(c, sel, 5);                        // (3)
```

**Подумай сам.** Чем `SEL` отличается от `IMP`, а `Method` — от них обоих?

**Разбор.** Разложи отправку сообщения на детали (глава 14):

- **`SEL` (селектор)** — уникализированное имя сообщения. Не строка, а её
  зарегистрированный в runtime «номерок»: для `"addTo:"` во всей программе
  существует ровно один `SEL`, поэтому селекторы сравнивают через `==`.
- **`IMP` (implementation)** — указатель на си-функцию, которая и есть тело
  метода. Её первые два скрытых аргумента — `self` и `_cmd` (селектор),
  дальше параметры.
- **`Method`** — пара (`SEL`, `IMP`) плюс кодировка типов. Класс хранит
  таблицу таких пар.
- **`objc_msgSend(receiver, sel, …)`** — функция, которая по `isa`
  получателя находит нужную `IMP` и передаёт ей управление.

`[c addTo:5]` компилятор превращает в `objc_msgSend(c, @selector(addTo:),
5)`. Все три пути в задаче ведут к одной и той же `IMP` и дают один и тот
же результат — `105`. Разница лишь в том, **на каком уровне** ты входишь:
скобки прячут `objc_msgSend`; `impFn` зовёт реализацию напрямую, минуя
поиск; `send` — это сам `objc_msgSend`, приведённый к сигнатуре метода. Без
приведения её не вызвать вообще: в современном SDK она объявлена как
`void objc_msgSend(void)`, и вызов с аргументами — ошибка компиляции, а не
предупреждение.

Кодировка типов `i20@0:8i16` (вывод с x86_64/arm64) читается так: возвращает `int` (`i`); дальше
аргументы — `@` (self), `:` (_cmd), `i` (наш `int x`); числа — смещения и
размеры, их можно игнорировать. Аргументов «3» — это `self`, `_cmd` и `x`:
два всегда скрытые.

Решение — `code/senior-02-msgsend.m`:

```text
SEL как строка: addTo:
Method найден: да
кодировка типов метода: i20@0:8i16
число аргументов (с учётом self и _cmd): 3
IMP из Method и из класса совпали? да
[c addTo:5]        = 105
через IMP          = 105
через objc_msgSend = 105
```

`IMP из Method` (через `method_getImplementation`) и `IMP из класса` (через
`class_getMethodImplementation`) совпали — это буквально один адрес кода.
Все три вызова дали `105`: квадратные скобки — лишь удобный синтаксис над
`objc_msgSend`.

> **Отличие от Си.** В Си `addTo(c, 5)` — переход по **фиксированному
> адресу**, выбранному компоновщиком на этапе сборки. В Objective-C тот же
> вызов — это поиск `IMP` по `SEL` **во время выполнения**, от `isa`
> получателя вверх. Один и тот же `[obj addTo:5]` может выполнить разный код
> в зависимости от того, какой объект сейчас в `obj`.

## Задача 3. Динамическое разрешение метода: сколько раз позовётся `resolve`

**Условие.** Класс `Ghost` не реализует ни `shout`, ни `twice:`. Их выдаёт
`+resolveInstanceMethod:` через `class_addMethod` при первом обращении.
Сколько раз вызовется `+resolveInstanceMethod:`, если послать `shout`
дважды и `twice:` один раз?

**Подумай сам.** Когда метод уже доращён в класс, нужен ли `resolve` при
следующем таком же сообщении?

**Разбор.** Когда `objc_msgSend` не находит метод обычным поиском (по
классу и вверх по `superclass`), он даёт классу первый шанс — зовёт
`+resolveInstanceMethod:(SEL)sel`: «может, доопределишь?» Если ты внутри
вызвал `class_addMethod` и вернул `YES`, runtime повторяет поиск — теперь
метод на месте.

Ключевое: `class_addMethod` встраивает метод **в класс навсегда**. Поэтому
`resolve` срабатывает **ровно один раз на селектор** — при самом первом
сообщении. Второй `shout` идёт уже по готовой таблице, минуя разрешение.

Считаем вызовы `+resolveInstanceMethod:`:

- первый `shout` → метода нет → `resolve` (раз), доращиваем, выполняем;
- второй `shout` → метод уже есть → `resolve` **не** зовётся;
- `twice:` → метода нет → `resolve` (два), доращиваем, выполняем.

Итого — **2 раза**. Кодировки типов в `class_addMethod`: `"@@:"` —
вернёт объект (`@`), принимает self (`@`) и _cmd (`:`); `"@@:@"` — то же
плюс ещё один объектный аргумент.

Решение — `code/senior-03-resolve.m`:

```text
первый вызов shout:
  [resolve] доопределили shout
  Ghost кричит! (селектор был shout)
второй вызов shout (resolve уже не нужен):
  Ghost кричит! (селектор был shout)
вызов twice:21 ->
  [resolve] доопределили twice:
  42
resolveInstanceMethod: позвался 2 раз(а)
```

`[resolve]` напечаталось дважды — по разу на каждый новый селектор. Между
двумя `shout` его нет: класс буквально вырос на метод и больше в разрешении
не нуждается.

## Задача 4. Логирующий прокси на `forwardingTargetForSelector:`

**Условие.** Сделай прокси, который сам не реализует `name` и `compute:`,
а пересылает их «настоящему» объекту `Service` и попутно считает каждую
пересылку. Какой из трёх шансов пересылки тут самый дешёвый и почему?

**Подумай сам.** Что должен вернуть `forwardingTargetForSelector:`, чтобы
runtime просто повторил сообщение другому объекту?

**Разбор.** Когда первый шанс (`resolveInstanceMethod:`) не сработал,
runtime даёт **второй**: `-forwardingTargetForSelector:(SEL)sel`. Ты
возвращаешь **другой объект**, и runtime повторяет отправку уже ему —
буквально как `objc_msgSend(другойОбъект, sel, …)`. Это самый дешёвый шанс:
ни копирования аргументов, ни построения `NSInvocation`, сообщение просто
едет к новому получателю. Тип возврата и аргументы сохраняются бесплатно.

На этом строят прокси: объект-обёртка хранит `_target` и в
`forwardingTargetForSelector:` возвращает его, если тот умеет селектор.
Заодно можно посчитать и залогировать каждую пересылку — то, ради чего
обёртку часто и заводят (аналитика, трассировка).

Тонкость: `[proxy respondsToSelector:@selector(name)]` вернул бы **нет** —
прокси и правда не реализует `name`, он его пересылает. Пересылка работает
уровнем ниже, уже после того как обычный поиск метода провалился.

Решение — `code/senior-05-logging-proxy.m`:

```text
  [proxy] переслано: name (всего 1)
name    = Service
  [proxy] переслано: compute: (всего 2)
compute = 81
  [proxy] переслано: compute: (всего 3)
compute = 16
итого переслано сообщений: 3
```

Снаружи `proxy` ведёт себя как `Service`: вернул имя и посчитал квадраты
(9² = 81, 4² = 16). Внутри — три залогированные пересылки. Один объект
прозрачно подменил другой, добавив к нему лог.

## Задача 5. Рассылающий прокси: почему тут нужен `forwardInvocation:`

**Условие.** Нужен прокси, который **одно** сообщение `event:` доставляет
**сразу нескольким** адресатам. Почему `forwardingTargetForSelector:` тут
не годится и какой шанс пересылки придётся взять?

**Подумай сам.** Сколько объектов умеет вернуть `forwardingTargetForSelector:`?

**Разбор.** `forwardingTargetForSelector:` умеет вернуть **ровно одного**
получателя — runtime повторит сообщение ему, и на этом всё. Доставить одно
сообщение нескольким он не может в принципе.

Здесь нужен **третий шанс** — самый мощный и самый дорогой:

1. `-methodSignatureForSelector:` — runtime просит описание сигнатуры
   метода, чтобы понять, как упаковать аргументы. Берём сигнатуру у первого
   адресата, который знает селектор.
2. `-forwardInvocation:(NSInvocation *)inv` — runtime упаковывает всё
   сообщение целиком в объект `NSInvocation`: получатель, селектор, все
   аргументы. С ним можно делать что угодно. Мы в цикле зовём
   `[inv invokeWithTarget:t]` для **каждого** адресата — сообщение
   выполняется на всех по очереди.

`NSInvocation` строить дороже, чем просто повторить отправку, но только он
даёт полный контроль: переслать многим, изменить аргументы, отложить,
залогировать. Тип переменной — `id<Listener>`: компилятор разрешает слать
`event:`, хотя `Broadcaster` его не реализует (динамика главы 5).

Решение — `code/senior-04-broadcast-proxy.m`:

```text
шлём ОДНО сообщение прокси:
  Анна получает событие: пожарная тревога
  Борис получает событие: пожарная тревога
  Вера получает событие: пожарная тревога
```

Одно `[group event:@"пожарная тревога"]` превратилось в три доставки.
`forwardingTargetForSelector:` так не смог бы — он вернул бы лишь одного
слушателя.

## Задача 6. Ленивый прокси на `NSProxy`: зачем отдельный корень

**Условие.** «Тяжёлый» объект `Heavy` дорого создавать, и мы хотим отложить
его создание до первого реального обращения. Сделай прокси-заместитель.
Почему для этого берут `NSProxy`, а не `NSObject`?

**Подумай сам.** Если унаследовать прокси от `NSObject`, какие сообщения он
обработает **сам**, не переслав их `Heavy`?

**Разбор.** В Objective-C два корня иерархии (глава 14). Основной —
**`NSObject`**: он тащит гору готового поведения (`description`, `hash`,
`isEqual:`, `respondsToSelector:`, десятки `NSObject`-методов). Второй,
отдельный — **`NSProxy`**: тонкий абстрактный класс специально для
заместителей. Он почти ничего не реализует сам и заставляет наследника
определить пересылку (`methodSignatureForSelector:` + `forwardInvocation:`).

В этом и причина выбора. Прокси должен пересылать `Heavy` **всё**. Унаследуй
он `NSObject` — сотни сообщений из `NSObject` и его категорий
(`isKindOfClass:`, `respondsToSelector:`, `conformsToProtocol:`,
`valueForKey:`, `performSelector:`…) прокси обработал бы **сам**, своим
унаследованным кодом, и ответил бы про себя, а не про `Heavy`. У `NSProxy`
своих ответов — горстка: по нашему эксперименту сам он отвечает на
`class`, `description`, `hash`, `isEqual:` (плюс управление памятью), а
`isKindOfClass:` и `respondsToSelector:` уже уходят в пересылку и честно
отвечают за `Heavy`. Мимо пересылки проходит минимум.

Механика: `LazyProxy` хранит `_real` (поначалу `nil`). Метод `real`
создаёт `Heavy` при первом обращении (лениво). `forwardInvocation:` зовёт
`[inv invokeWithTarget:[self real]]` — и именно тут, на первом реальном
сообщении, `Heavy` наконец рождается. Создаётся прокси через `[LazyProxy
alloc]` без `init`: у `NSProxy` своя схема.

Решение — `code/senior-13-nsproxy.m`:

```text
создаём прокси (Heavy ещё НЕ создан):
прокси готов, Heavy всё ещё не создан
первое реальное обращение -> report:
  Heavy: дорогой объект СОЗДАН
  ответ: тяжёлый отчёт готов
```

Прокси создан, а «Heavy СОЗДАН» появилось **только** на `report` — создание
отложилось ровно до первого дела. Будь прокси на `NSObject`, часть служебных
сообщений он перехватил бы сам, и прозрачной замены не вышло бы.

## Задача 7. Method swizzling правильно: `+load`, `dispatch_once`, `class_addMethod`

**Условие.** Нужно подменить метод `-tap` класса `Button` так, чтобы перед
оригиналом срабатывала аналитика. Где безопасно делать подмену, зачем тут
`dispatch_once`, и почему «правильный» swizzle сначала пробует
`class_addMethod`, а не сразу `method_exchangeImplementations`?

**Подумай сам.** Что будет, если метод `tap` достался классу **по
наследству**, а ты обменяешь его реализацию через `exchange`?

**Разбор.** Swizzling — обмен реализациями двух методов (глава 14). Делать
его надо аккуратно, иначе словишь трудноуловимый баг. Три правила из
рабочего решения:

1. **Где.** Подмену кладут в `+load` категории. `+load` runtime зовёт
   один раз при загрузке образа, ещё до `main`, и потокобезопасно. Это
   надёжный момент: класс уже есть, но программа ещё не работает.
2. **`dispatch_once`.** Дополнительный пояс поверх подтяжек: гарантирует,
   что подмена выполнится строго один раз, даже если код как-то позовут
   повторно. Двойной swizzle вернул бы метод в исходное состояние —
   `dispatch_once` это исключает.
3. **Сначала `class_addMethod`.** Если `tap` достался `Button` **по
   наследству** (определён в родителе), голый `method_exchangeImplementations`
   полез бы менять реализацию **в родителе** — а это сломает поведение для
   всех остальных потомков. Поэтому сперва пробуем `class_addMethod`: она
   добавит метод **в наш класс** и вернёт `YES`, если метода тут ещё не
   было. Тогда обмен делаем уже внутри своего класса. И только если метод
   определён прямо в `Button` (`class_addMethod` вернула `NO`) — честный
   `exchange`.

Тело `analytics_tap` после обмена в конце зовёт `[self analytics_tap]` —
на вид рекурсия, но это не она: после обмена имя `analytics_tap` указывает
на **старый** код `tap`. Классический приём «обёртки».

Решение — `code/senior-06-swizzle.m`:

```text
нажимаем кнопку:
  [analytics] зафиксировали нажатие
  Button: обычное нажатие
```

`[b tap]` теперь сначала логирует, потом выполняет исходное нажатие — мы
обернули чужой метод, не трогая его исходник. Подмена глобальна: касается
всех экземпляров `Button` в программе.

## Задача 8. Найди тонкий баг: swizzling, который ломает KVO

**(Концептуальная, без файла: сценарий из условия роняет программу. Мы
воспроизвели его экспериментом.)**

**Условие.** В проекте есть помощник, который вешает логирование на сеттер
`setName:`. Чтобы «попасть в настоящий класс объекта», он берёт класс через
`object_getClass(obj)` и свиззлит его по схеме задачи 7 при первом вызове.
Работало месяцами. Потом в одном экране на тот же `Person` повесили KVO —
раньше, чем сработал помощник. Теперь первое же `p.name = …` роняет
программу с `EXC_BAD_ACCESS` где-то внутри Foundation. Где баг?

**Подумай сам.** Что вернёт `object_getClass(obj)` для объекта, на который
уже подписан KVO, — и чей сеттер тогда окажется в обмене?

**Разбор.** Вспомни, как устроен KVO (глава 20, задача 10 ниже). В момент
`addObserver:` Foundation создаёт **динамический подкласс**
(`NSKVONotifying_Person`), кладёт в него свой `setName:` и **подменяет
`isa`** объекта на этот подкласс. `-class` при этом врёт, что это
по-прежнему `Person`, а `object_getClass` говорит правду.

Теперь пройди по шагам помощника:

1. `object_getClass(p)` вернул **не** `Person`, а `NSKVONotifying_Person`.
   Свиззлим чужой, сгенерированный Foundation класс.
2. `class_addMethod(…, @selector(setName:), …)` вернул `NO`: в KVO-подклассе
   `setName:` уже есть. Значит, идём в `method_exchangeImplementations`.
3. А `log_setName:` в KVO-подклассе **нет** — `class_getInstanceMethod`
   нашёл его у родителя `Person`. Обмен переписал метод **родителя**:
   теперь у всех `Person` под именем `log_setName:` сидит KVO-сеттер. Это
   ровно та ошибка, от которой защищает `class_addMethod` в задаче 7, только
   с другой стороны.
4. KVO-сеттер — общая функция на все свойства. Какой ключ менять и чью
   реализацию звать дальше, он, судя по поведению, выводит из селектора
   `_cmd`. После обмена его
   зовут под чужим именем `log_setName:` — и его логика рушится. В нашем
   эксперименте это падение с `EXC_BAD_ACCESS` внутри
   `-[NSObject(NSKeyValueObservingPrivate) _changeValueForKeys:…]`.

Отдельно — «плавающий» хвост. Пока KVO не подписан, `object_getClass`
возвращает `Person`, и помощник подменяет сеттер у `Person`. Подписали
KVO после этого — всё работает: KVO-сеттер в момент вызова зовёт
`setName:` родителя и попадает в подмену (лог и уведомление — оба есть,
мы проверили). Поэтому баг зависит от порядка: кто успел первым — KVO или
помощник.

Как чинить:

- Свиззли **только свой класс, взятый статически** (`[Person class]` или
  `self` в `+load` категории), а не класс конкретного экземпляра. Под
  `object_getClass(obj)` может оказаться что угодно: KVO-подкласс,
  класс-кластер, прокси.
- Делай это **один раз в `+load`** с `dispatch_once` (задача 7) — до того,
  как кто-либо успеет подписаться на KVO.
- Не свиззли сеттеры, за которыми наблюдают через KVO, без крайней нужды.
  Хочешь лог изменений — подпишись на тот же KVO.

Короткий ответ на собеседовании: **`object_getClass` у наблюдаемого
объекта — это `NSKVONotifying_…`; свиззлинг его сеттера подсовывает
KVO-функции чужой `_cmd` и заодно портит метод родителя. Свиззли только
свой класс, статически, в `+load`, один раз.**

## Задача 9. Связанный объект: хранимое свойство в категории

**Условие.** `View` — будто бы чужой класс из фреймворка: исходник
недоступен, ivar в него не добавить. Нужно прицепить к нему счётчик
`badgeCount`. Категория хранить поля не умеет. Как сохранить значение
**на объекте**, и почему у двух разных `View` оно своё?

**Подумай сам.** Если в объекте нет места под новый ivar, где runtime
держит привязанное к нему значение?

**Разбор.** Категория добавляет **методы**, но не **ivar**: размер объекта
фиксируется при компиляции класса. Объявить в категории `@property` можно,
но автоматического ivar под него не будет — только обещание геттера и
сеттера, которые ты обязан написать сам. А значение хранят через **связанные
объекты** (associated objects) из runtime:

```objc
static const void *kBadgeKey = &kBadgeKey;   // адрес = уникальный ключ

- (void)setBadgeCount:(NSNumber *)v {
    objc_setAssociatedObject(self, kBadgeKey, v,
                             OBJC_ASSOCIATION_RETAIN_NONATOMIC);
}
- (NSNumber *)badgeCount {
    return objc_getAssociatedObject(self, kBadgeKey);
}
```

`objc_setAssociatedObject` привязывает значение **к конкретному объекту**
по ключу. Ключом служит адрес статической переменной (`&kBadgeKey`) — он
гарантированно уникален во всей программе. Привязка живёт у каждого
экземпляра своя: runtime держит её в отдельной таблице, индексированной по
объекту, а не в самом объекте. Поэтому `a.badgeCount` и `b.badgeCount`
независимы. И следить за освобождением не нужно: связанные объекты runtime
снимает сам, когда носитель умирает.

Политика `OBJC_ASSOCIATION_RETAIN_NONATOMIC` означает «держи сильно, без
атомарности» — аналог `strong, nonatomic` у свойства (для строк взяли бы
`COPY_NONATOMIC`).

Решение — `code/senior-07-associated.m`:

```text
до:  Почта badge=(null), Чаты badge=(null)
после: Почта badge=7, Чаты badge=0
у каждого объекта своё значение? да
```

До присваивания связанного значения нет — геттер возвращает `nil`
(`(null)`). После — у «Почты» 7, у «Чатов» 0: значение у каждого объекта
своё, хотя ivar мы не добавляли и класс не трогали.

> **Отличие от Си.** В Си, чтобы прицепить данные к чужой структуре, пришлось
> бы менять её определение и пересобирать всех, кто её использует. Здесь
> runtime хранит привязку в стороне, по адресу объекта, — чужой класс можно
> «дорастить» данными, не имея его исходника.

## Задача 10. KVO под капотом: подмена `isa` и `NSKVONotifying_`

**Условие.** Подписались через KVO на свойство `balance` объекта `Account`.
Что произойдёт с **классом** объекта? Что покажет `-class`, а что — реальный
`isa` (через `object_getClass`) до подписки, после неё и после отписки?

**Подумай сам.** Как одно лишь `addObserver:` заставляет обычный сеттер
рассылать уведомления, не трогая исходный код `Account`?

**Разбор.** KVO стоит **на сеттере**, и реализован он через подмену `isa`
(глава 20). В момент `addObserver:forKeyPath:` runtime:

1. генерирует **динамический подкласс** `NSKVONotifying_Account`;
2. переопределяет в нём `setBalance:` так, чтобы вокруг настоящего
   присваивания слались `willChangeValueForKey:` / `didChangeValueForKey:`;
3. **подменяет `isa`** объекта `acc` на этот новый подкласс.

С этого момента `acc` физически — экземпляр `NSKVONotifying_Account`, и его
сеттер уведомляет наблюдателей. Но `-class` специально **врёт**, что это
по-прежнему `Account`: KVO маскирует подмену, чтобы не пугать твой код. А
настоящий `isa`, прочитанный напрямую через `object_getClass`, выдаёт
правду — `NSKVONotifying_Account`. После `removeObserver:` runtime возвращает
`isa` на место — снова `Account`.

Отсюда два важных факта (оба видны в выводе):

- Уведомление приходит только при изменении **через сеттер** (или через
  KVC `setValue:forKey:`, который его зовёт) — потому что перехвачен именно
  сеттер. Прямая запись в ivar минует его, и KVO молчит.
- В конце обязателен `removeObserver:`: `addObserver:` не удерживает
  наблюдателя, и если тот умрёт раньше, следующее уведомление уйдёт по
  висячему указателю и уронит программу.

Решение — `code/senior-08-kvo-isa.m`:

```text
до подписки:   -class=Account  настоящий isa=Account
после подписки: -class=Account  настоящий isa=NSKVONotifying_Account
меняем баланс через сеттер:
  [наблюдатель] balance: 0 -> 100
  [наблюдатель] balance: 100 -> 250
после отписки:  настоящий isa=Account
```

Вот доказательство «isa-swizzling»: `-class` всё время говорит `Account`, а
настоящий `isa` после подписки стал `NSKVONotifying_Account` и вернулся
обратно после отписки. Два изменения через сеттер дали два уведомления со
старым и новым значением. Это та же машинерия, что в задаче 8, — вот почему
swizzling наблюдаемых сеттеров и опасен.

## Задача 11. Две категории с одинаковым методом — какая победит

**(Концептуальная, без файла — результат не определён, запускать
бессмысленно.)**

**Условие.** На один класс навесили две категории, и в обеих объявлен
метод `tagline` с **разной** реализацией. Какая из них вызовется?

```objc
@implementation NSString (A)
- (NSString *)tagline { return @"из A"; }
@end
@implementation NSString (B)
- (NSString *)tagline { return @"из B"; }
@end
```

**Подумай сам.** Гарантирует ли язык, какая реализация ляжет в таблицу
методов класса?

**Разбор.** Это **неопределённое поведение**. Когда две категории одного
класса определяют метод с одним именем, какая из них «победит» — **не
специфицировано**.

Почему так, на уровне runtime. При загрузке образа runtime берёт методы
категорий и **дописывает** их в таблицу методов класса. Методы категории
кладутся так, что при поиске находятся **раньше** родных методов класса, —
поэтому категория и «перебивает» оригинал. А вот порядок между **двумя
категориями** определяется порядком, в котором runtime их подгрузил, то
есть порядком линковки объектных файлов. По нашим наблюдениям обычно
«побеждает» категория, загруженная **последней** (её метод оказывается в
начале списка и находится первым), — но опираться на это нельзя: поменяется
порядок файлов в сборке, версия компилятора или тулчейна — и результат
сменится. Поэтому «эксперимент» тут ничего не доказывает: у тебя выйдет
`из A`, а у коллеги с другим порядком файлов в проекте — `из B`.

Хуже того — категория, переопределяющая **родной** метод класса (не другой
категории, а сам метод `NSString`), молча затирает оригинал, и вызвать
прежнюю реализацию через `super` уже нельзя: у категории нет «родителя» с
этим методом.

Правила, которые ждут в ответе:

- **Категория — чтобы добавлять методы, а не подменять.** Хочешь изменить
  поведение — делай подкласс или swizzling (осознанно, см. задачи 7–8).
- **Префиксируй имена методов в категориях** (`abc_tagline`), особенно на
  классах Foundation, — чтобы не столкнуться ни с будущим методом Apple, ни
  с чужой категорией.
- Правильный ответ на «какая победит» — **«поведение не определено, так
  делать нельзя»**, а не угадывание порядка линковки.

## Задача 12. Гонка данных: `atomic` не делает коллекцию потокобезопасной

**Условие.** Свойство `value` объявлено `atomic`. Два потока параллельно по
100 000 раз делают `value = value + 1`. Ожидаем 200 000. Что получим — и
почему `atomic` тут не спас?

**Подумай сам.** `atomic` делает неделимым **что** — отдельный `get`/`set`
или всю операцию `value = value + 1`?

**Разбор.** `atomic` гарантирует, что **каждый отдельный** геттер и сеттер
выполнится целиком, без того чтобы другой поток увидел свойство
«наполовину записанным». Это всё, что он обещает.

А `value = value + 1` — это **две** раздельные операции:

1. `get` — прочитать текущее `value`;
2. `set` — записать `value + 1`.

Между ними другой поток успевает вклиниться: оба читают, скажем, 1000, оба
пишут 1001 — один инкремент потерян. `atomic` сделал неделимыми **шаги**,
но не **связку** read-modify-write. Это и есть гонка данных (race
condition): часть инкрементов теряется, итог меньше ожидаемого.

Чинить надо так, чтобы **вся** связка read-modify-write была неделимой.
В решении это последовательная (`SERIAL`) очередь: `dispatch_sync(guard,
^{ good++; })` — два потока физически не пересекутся внутри, очередь
пропускает по одному. Альтернативы — мьютекс (`@synchronized`,
`os_unfair_lock`) или атомарный счётчик из `<stdatomic.h>`.

Решение — `code/senior-09-atomic-race.m`:

```text
atomic-свойство: ожидали 200000, получили 175216  (часть потеряна)
serial-очередь:  ожидали 200000, получили 200000
```

Точное число у тебя будет своё (гонка недетерминирована), но оно будет
**меньше** 200 000 — инкременты теряются. Через последовательную очередь —
ровно 200 000.

Вывод, который ждут на собеседовании: **`atomic` защищает доступ к одному
свойству, а не последовательность операций и тем более не содержимое
коллекции.** `atomic`-свойство типа `NSMutableArray` тоже не делает сам
массив потокобезопасным — атомарна лишь подмена указателя на массив, а не
`addObject:`. Для составных операций нужна явная синхронизация.

## Задача 13. `dispatch_sync` на текущей последовательной очереди — дедлок

**(Концептуальная, без файла — пример роняет программу.)**

**Условие.** Что произойдёт с этим кодом, если он выполняется **на главном
потоке**?

```objc
dispatch_sync(dispatch_get_main_queue(), ^{
    NSLog(@"привет");
});
```

А с этим — если он уже выполняется внутри блока на последовательной очереди
`q`?

```objc
dispatch_sync(q, ^{                 // мы уже внутри блока на q
    dispatch_sync(q, ^{ ... });     // и снова синхронно на ту же q
});
```

**Подумай сам.** Что делает `dispatch_sync` с **текущим** потоком, пока
блок не выполнится, — и кто на последовательной очереди должен этот блок
выполнить?

**Разбор.** Оба случая — **дедлок** (взаимная блокировка): поток ждёт сам
себя. На старых системах программа просто зависала навсегда. Современный
libdispatch такую ситуацию распознаёт и роняет процесс: по нашему запуску
на macOS оба примера падают с `EXC_BAD_INSTRUCTION` в функции
`__DISPATCH_WAIT_FOR_QUEUE__` (в crash-логе будет строка «dispatch_sync
called on queue already owned by current thread»). Это диагностика, а не
спасение: код всё равно сломан.

Разбери `dispatch_sync` по словам: «поставь блок в очередь и **заблокируй
текущий поток**, пока этот блок не выполнится до конца». Теперь наложи это
на **последовательную** очередь — она выполняет блоки строго по одному, не
начиная следующий, пока не закончит текущий.

Первый случай. Главная очередь последовательна, и обслуживает её главный
поток. Ты на главном потоке зовёшь `dispatch_sync(main)`. Главный поток
**блокируется** и ждёт, пока блок выполнится. Но выполнить блок может только
главный поток — а он сейчас стоит и ждёт сам себя. Никто не сдвинется:
зависание.

Второй случай — та же ловушка в общем виде. Ты **внутри** блока на очереди
`q` синхронно ставишь на `q` ещё один блок и ждёшь его. Но `q` не начнёт
второй блок, пока не доделает первый, — а первый стоит и ждёт второго.
Круг замкнулся.

Ключевая формула: **`dispatch_sync` на ту очередь, на которой ты сейчас
выполняешься (если она последовательная), — это всегда дедлок.** Сюда же
частый прод-баг: код на главном потоке вызывает «удобную» обёртку, а та
внутри делает `dispatch_sync(main)` «чтобы наверняка на главном» — и всё
виснет, как только её случайно позвали уже с главного потока.

Как правильно:

- Если ты, возможно, **уже** на нужной очереди и нужен синхронный результат
  — не делай безусловный `dispatch_sync`; проверь, та ли это очередь, или
  выполни блок напрямую.
- Не нужен результат прямо сейчас — бери `dispatch_async`: он не блокирует
  текущий поток и дедлока не даёт.
- `dispatch_sync` на **другую** очередь (не текущую) — нормально; опасна
  именно отправка на самого себя.

В `code/` этот пример не кладём намеренно: он либо падает, либо виснет —
смотря по системе.

## Задача 14. Потокобезопасный синглтон на `dispatch_once`

**Условие.** Шестнадцать потоков одновременно лезут за `[Database shared]`.
Напиши `+shared` так, чтобы объект создался **ровно один раз** и все потоки
получили один и тот же экземпляр. Почему именно `dispatch_once`, а не
`if (instance == nil)`?

**Подумай сам.** Что будет, если два потока одновременно пройдут проверку
`if (instance == nil)` раньше, чем хоть один успел присвоить `instance`?

**Разбор.** Наивный `if (instance == nil) { instance = [[self alloc]
init]; }` в многопотоке ломается: два потока могут **одновременно** увидеть
`nil`, оба создадут объект, и один экземпляр перезатрёт другой — синглтон
перестаёт быть единственным. Это та же гонка, что в задаче 12, только цена
выше: расходятся не числа, а сам объект.

`dispatch_once` решает это на корню. Он гарантирует, что блок выполнится
**один раз за всё время работы программы**, даже под шквалом потоков:
первый поток выполняет блок, остальные ждут его завершения и затем видят
готовый результат. Токен `dispatch_once_t` обязан быть `static` (одна
ячейка на всю программу) — по нему `dispatch_once` и помнит, что уже
отработал.

Деталь: внутри пишут `[[self alloc] init]`, а не `[[Database alloc] init]`.
`self` в методе класса — это сам класс, по которому метод позвали, поэтому
подкласс получит синглтон своего класса.

Решение — `code/senior-10-singleton.m`:

```text
   >>> Database создан (видно один раз)
a == b ? да, один объект
path: /var/db/main
```

Строка «Database создан» напечаталась **один раз**, хотя за синглтоном
ломились 16 потоков. `a == b` — один и тот же объект. `dispatch_once`
сделал создание атомарным и единственным.

## Задача 15. Потокобезопасный кэш: барьерная запись на concurrent-очереди

**Условие.** Нужен кэш «ключ-значение», в который пишут и из которого читают
**много потоков сразу**. Хочется, чтобы чтения шли параллельно, а записи —
эксклюзивно (никто не читает в момент записи). Как это устроить на GCD?

**Подумай сам.** Можно ли пускать читателей параллельно, но писателя — в
одиночку, на одной и той же очереди?

**Разбор.** Это классическая схема «много читателей — один писатель»
(readers-writer), и GCD даёт её почти даром через **барьер** на собственной
**concurrent**-очереди:

- **Чтение** — `dispatch_sync(_queue, ^{ … })` на concurrent-очереди:
  несколько чтений идут **параллельно**, не мешая друг другу, и `sync`
  возвращает прочитанное значение вызывающему.
- **Запись** — `dispatch_barrier_async(_queue, ^{ … })`. Барьер заставляет
  GCD дождаться завершения **всех текущих** операций на очереди, выполнить
  блок-писатель **в одиночку** (в этот момент на очереди больше ничего не
  идёт) и только потом пустить следующие. `async` — потому что писателю не
  нужно ждать результата, он лишь ставит барьер в очередь и сразу
  возвращается, не блокируя свой поток.

Важно: очередь должна быть **своя**, созданная `dispatch_queue_create(…,
DISPATCH_QUEUE_CONCURRENT)`. На глобальной concurrent-очереди барьер не
работает как барьер — она общая, и GCD не даёт на ней эксклюзивности.

Зачем `count` в конце читает через `dispatch_sync` на той же очереди: к
моменту, когда `sync`-чтение дойдёт до выполнения, все ранее поставленные
барьеры-записи на этой очереди уже отработают (очередь упорядочена) —
поэтому увидим ровно 100 элементов, а не «сколько успели».

Решение — `code/senior-11-barrier-cache.m`:

```text
в кэше 100 элементов (ожидали 100)
k7  = 49 (ожидали 49)
k12 = 144 (ожидали 144)
```

Сто параллельных писателей и пятьдесят параллельных читателей не подрались:
барьер развёл записи с чтениями, и кэш собрал все 100 пар (7² = 49,
12² = 144). Чтения при этом шли одновременно — барьер сдерживает только
запись.

## Задача 16. `weak` в многопоточности и пулы автоосвобождения в фоне

**(Концептуальная, без файла — разбираем словами.)**

**Условие.** Две части одного вопроса.

1. Безопасно ли читать `__weak`-ссылку из нескольких потоков? Что не так с
   таким кодом, если объект могут освободить в другом потоке?

   ```objc
   if (self.weakDelegate) {
       [self.weakDelegate doWork];   // между проверкой и вызовом?
   }
   ```

2. Ты запускаешь долгую работу на **своём** фоновом потоке (`NSThread`/
   `pthread`), внутри в цикле создаёшь временные объекты. Почему память
   может потечь и runtime ругается «autoreleased with no pool in place»?

**Подумай сам.** (1) Сколько раз этот код **читает** `weakDelegate` и что
может случиться между чтениями? (2) Кто на свежесозданном потоке отвечает
за слив пула автоосвобождения?

**Разбор, часть 1 — `weak` и потоки.** Само по себе чтение и запись
`__weak`-ссылки **потокобезопасны**: машинерия ARC под капотом
синхронизирована, и ты всегда получишь либо валидный, уже удержанный на
время чтения объект, либо честный `nil`, но **никогда** не висячий
указатель на освобождённую память. Это сильная гарантия.

Ловушка в другом — в **двойном чтении**. Код выше читает `weakDelegate`
**дважды**: один раз в `if`, второй раз при вызове. Между ними другой поток
может освободить объект. Тогда первое чтение даст живой объект (`if`
пройдёт), а второе — уже `nil`. Само сообщение к `nil` безопасно (тихий
no-op), но логика «проверил — значит есть» нарушена, и при более сложном
коде это даёт плавающие баги. Правильно — **прочитать один раз в сильную
локальную переменную**, она удержит объект на время работы:

```objc
__strong id strong = self.weakDelegate;   // одно чтение, объект удержан
if (strong) {
    [strong doWork];                       // он точно жив до конца блока
}
```

Это тот же «weak-strong dance», что и в блоках (приложение E): слабая
ссылка рвёт цикл, а локальная сильная гарантирует, что объект не исчезнет
**посреди** работы.

**Разбор, часть 2 — пулы в фоне.** Многие объекты Foundation возвращаются
**автоосвобождёнными**: их держит в живых только **пул автоосвобождения**
(autorelease pool), пока тот не сольётся (глава 13). Вопрос — кто этот пул
создаёт.

- На **главном** потоке пул есть всегда — его крутит run loop приложения,
  сливая на каждом витке.
- На очередях **GCD** система оборачивает выполнение блоков в свой пул и
  периодически его сливает — поэтому под `dispatch_async` обычно пул заводить
  не нужно (но для долгого цикла внутри блока — всё равно стоит).
- На **своём** потоке (`NSThread`, голый `pthread`) **явного пула нет** —
  его никто не создал. Современный runtime на этот случай молча заводит
  пул сам и сливает его, **только когда поток завершается**. По нашему
  эксперименту (`pthread`, три автоосвобождённых объекта) все три
  `dealloc` пришли уже после выхода из функции потока. Для короткого потока
  это терпимо. Для долгоживущего потока с циклом — нет: временные объекты
  копятся часами, память растёт, будто течёт.
- Сообщение `object … autoreleased with no pool in place - just leaking`
  из старых книг и форумов runtime печатает только при переменной окружения
  `OBJC_DEBUG_MISSING_POOLS=YES`. В этом режиме он пул не заводит, и
  объекты действительно текут — так удобно искать места без пула.

Лечение — обернуть тело потока (а в длинном цикле — тело итерации) в свой
`@autoreleasepool`:

```objc
- (void)threadMain {
    @autoreleasepool {                 // пул на весь поток
        while (working) {
            @autoreleasepool {     // и на каждую итерацию: пик памяти низкий
                ... временные объекты ...
            }
        }
    }
}
```

Короткий ответ на собеседовании: **`weak` потокобезопасен, но читай его
один раз в сильную локальную; у своего фонового потока нет явного пула —
runtime сольёт неявный только при выходе из потока, поэтому оборачивай
работу (и каждую итерацию долгого цикла) в `@autoreleasepool` сам.**

## Задача 17. Исключение через границу `@autoreleasepool` и в фоновом потоке

**(Концептуальная, без файла — разбираем словами.)**

**Условие.** Две ситуации.

1. Объект автоосвобождён **внутри** `@autoreleasepool { … }`, и прямо оттуда
   бросают `NSException`, который ловят **снаружи** пула. Что станет с этим
   объектом и можно ли вернуть его наружу?
2. На фоновой GCD-очереди бросают `NSException` и **нигде** не ловят. Что
   будет с программой — упадёт только поток или весь процесс?

**Подумай сам.** Что происходит с пулом, когда исключение «разматывает» стек
мимо его закрывающей скобки? И есть ли у фонового потока «верхний» ловец
исключений, как у главного run loop?

**Разбор, часть 1 — исключение через границу пула.** Интуиция говорит:
«при выходе из `{ }` пул сливается». Но спецификация ARC в Clang говорит
прямо обратное: если блок `@autoreleasepool` покинули **исключением**, пул
**не сливается**. Он остаётся в стеке пулов, и его объекты освобождает
первый **внешний** пул, который сольётся нормально: при его сливе runtime
заодно снимает и все забытые внутренние.

Мы проверили: объект автоосвобождён во внутреннем пуле, из него брошено
исключение, `@catch` снаружи его поймал — `dealloc` пришёл только в конце
внешнего `@autoreleasepool`, уже после `@catch`.

Практический вывод: **не опирайся на время жизни автоосвобождённого
объекта, который пересёк границу пула исключением.** Он не умрёт сразу, но
и сильной ссылки на него у тебя нет: исчезнет, когда сольётся какой-то
внешний пул, — а этот момент от тебя не зависит. Если объект нужен после
`@catch`, держи его в сильной переменной, объявленной **снаружи** `@try`.
Добавь сюда, что код под ARC по умолчанию не готов к исключениям (флаг
`-fobjc-arc-exceptions` выключен для `.m`): при разматывании ARC не
отпускает сильные локальные переменные, и они текут.

**Разбор, часть 2 — исключение в фоне.** В Objective-C `NSException` — это
сигнал о **программерской ошибке** (вышел за границу массива, послал
нераспознанный селектор), а **не** механизм управления потоком. Восстановимые
ошибки передают через `NSError`, а не бросают исключениями.

Что до фонового потока: **никакого «верхнего» ловца у него нет**. AppKit
на главном потоке по умолчанию ловит исключения из обработчиков событий и
пишет их в лог (UIKit так не делает — там приложение падает), но обычный
фоновый поток и блок GCD такой защиты не имеют. Непойманное
`NSException` доходит до самого верха стека потока, runtime зовёт
обработчик непойманных исключений и затем `abort()` — **падает весь
процесс**, а не «только поток». Поток в общей памяти процесса; уронив его
исключением, ты роняешь всё приложение.

Отсюда правила:

- `@try/@catch` — **не** инструмент повседневной обработки ошибок и тем
  более не «глушилка» багов. Поймать `NSException`, чтобы продолжить как ни
  в чём не бывало, опасно: после программерской ошибки состояние программы
  уже могло поехать (полусделанная мутация, повисший lock).
- Исключение, пересекающее `@autoreleasepool`, **не** сливает его: объекты
  доживут до слива внешнего пула, но владеть ими ты уже не можешь.
- В фоновом потоке/блоке GCD непойманное исключение валит **весь процесс**.
  Для ожидаемых сбоев возвращай `NSError`, а исключения оставь на
  невосстановимые ошибки программиста.

В `code/` это не кладём: пример с непойманным исключением сознательно
завершает процесс и сломал бы проверку.

## Задача 18. Tagged pointers: почему `==` для маленьких `NSNumber` иногда прав

**Условие.** Два одинаковых **маленьких** `NSNumber`, созданных в рантайме,
сравнивают через `==` (указатели). Потом — два одинаковых **больших**.
Где `==` даст «равны», а где «нет», и почему?

```objc
NSNumber *a = [NSNumber numberWithInteger:5];
NSNumber *b = [NSNumber numberWithInteger:5];                    // a == b ?
NSNumber *c = [NSNumber numberWithInteger:1234567890123456789LL];
NSNumber *d = [NSNumber numberWithInteger:1234567890123456789LL];  // c == d ?
```

**Подумай сам.** Всегда ли `NSNumber` — это объект в куче со своим адресом?

**Разбор.** На 64-битных системах маленькие `NSNumber` runtime хранит
**прямо внутри указателя** — это **tagged pointer** («помеченный
указатель»): само число закодировано в биты «адреса», отдельный объект в
куче **не создаётся**. Два одинаковых маленьких числа получают **один и тот
же** tagged-указатель — поэтому `==` для них случайно оказывается прав
(`да`).

Большое число (`1234567890123456789`) в биты указателя не влезает — runtime
создаёт **настоящий объект в куче**. Два таких равны по значению, но это
**два разных** объекта по разным адресам, и `==` честно даёт `нет`.

Любопытная деталь: `[a class]` для tagged-числа всё равно показывает
`__NSCFNumber` — снаружи это полноценный `NSNumber`, упаковка в указатель
скрыта. И адреса tagged-указателей **обфусцированы** (runtime подмешивает
случайную соль на каждый запуск), поэтому в выводе они выглядят как огромные
«случайные» числа и меняются от запуска к запуску: прочитать число прямо
из «адреса» не выйдет.

Решение — `code/senior-12-tagged.m`:

```text
маленькое 5:  a == b (указатели)? да   класс=__NSCFNumber
   a=0x5012cb0de9e1ded7  b=0x5012cb0de9e1ded7  (свой в каждом запуске)
большое число: c == d (указатели)? нет   класс=__NSCFNumber
   c=0x6000007556c0  d=0x6000007556e0  (обычные адреса в куче)
isEqual: всегда верно: маленькие равны, большие равны
```

Смотри: маленькие `5` дали одинаковый указатель (`==` → да), большие —
разные кучные адреса (`==` → нет). А `isEqual:` верен в **обоих** случаях.

Вывод, который и проверяют: **`==` для `NSNumber` (и для объектов вообще) —
лотерея**, зависит от значения, разрядности и сборки. Сравнивай значения
**только** через `isEqual:` / `isEqualToNumber:`. Tagged pointers — причина,
по которой `==` иногда «случайно работает» и тем коварнее: на маленьких
числах в тестах прошло, на больших в проде сломалось.

> **Отличие от Си.** В Си `int` — это всегда само число в памяти, и `==`
> сравнивает значения. Здесь `NSNumber` — объект, `==` сравнивает указатели,
> и runtime ради экономии прячет маленькие числа в сам указатель. Поэтому
> «сравнение чисел» через `==` ведёт себя то как сравнение значений, то как
> сравнение адресов — и доверять ему нельзя.

## Задача 19. Найди и почини утечку: цикл удержания через `NSTimer`

**Условие.** Объект `Ticker` заводит повторяющийся таймер на себя через
`scheduledTimerWithTimeInterval:target:selector:…`. Объект выходит из
области видимости, но `dealloc` не зовётся. Где цикл удержания и как починить?

```objc
- (void)startBad {
    self.timer = [NSTimer scheduledTimerWithTimeInterval:0.05
                                                  target:self
                                                selector:@selector(tick:)
                                                userInfo:nil
                                                 repeats:YES];
}
```

**Подумай сам.** Как `NSTimer` относится к своему `target` — слабо или
сильно? И кто держит сам таймер?

**Разбор.** `scheduledTimer…target:` **сильно удерживает** `target`, то
есть `self`. А `self` сильно держит таймер в свойстве `timer`. И вдобавок
запланированный таймер держит **run loop**. Кольцо:

```text
run loop ──> timer ──strong──> self ──strong──> timer
```

Пока таймер не остановлен (`invalidate`), его держит run loop, таймер держит
`self`, `self` держит таймер. Внешние ссылки на `Ticker` исчезли, а счётчик
не падает до нуля — `dealloc` не сработает **никогда**. Коварство в том, что
`weak` на свойстве `timer` тут не помог бы: сильную ссылку держит не оно, а
сам таймер на `target`.

Чинить надо **связь таймер → self**. В современном API берут **блочный**
таймер и захватывают `self` **слабо**:

```objc
- (void)startGood {
    __weak typeof(self) weakSelf = self;
    self.timer = [NSTimer scheduledTimerWithTimeInterval:0.05
                                                 repeats:YES
                                                   block:^(NSTimer *t) {
        Ticker *strong = weakSelf;
        if (!strong) { [t invalidate]; return; }   // self ушёл — гасим таймер
        [strong tick:t];
    }];
}
```

Теперь таймер держит блок, а блок ссылается на `self` **слабо**. Когда
внешний код отпускает `Ticker`, `weakSelf` становится `nil`, блок при
очередном тике это видит и сам гасит осиротевший таймер (`invalidate`) —
кольцо разорвано, `dealloc` срабатывает.

(Не путай: слабый захват освобождает `self`, но не сам таймер. Пока его не
погасили, run loop держит таймер, таймер держит блок, и блок продолжает
срабатывать впустую. Поэтому таймер всё равно гасят через `invalidate` —
в нашем решении это делает сам блок, заметив `weakSelf == nil`, а в
реальном коде обычно ещё и явно, когда таймер больше не нужен.)

Решение — `code/senior-14-timer-cycle.m`:

```text
--- ПЛОХО: target/selector-таймер ---
  (dealloc для «bad» НЕ вызван — утечка через таймер)
--- ХОРОШО: блочный таймер + weak ---
  dealloc: Ticker «good» освобождён
  (dealloc для «good» вызван выше — цикл разорван)
```

У «bad» строки `dealloc` нет — объект застрял в кольце с таймером. У «good»
`dealloc` напечатался: слабый захват `self` в блоке разорвал цикл, и
осиротевший таймер сам погасился при следующем тике. По пропавшему
`dealloc`, как обычно, утечку и ловят.

> **Отличие от Си.** В Си «таймер» был бы структурой с указателем на
> callback-функцию — никаких счётчиков ссылок, никаких циклов удержания,
> только риск забыть `free` или позвать функцию по висячему указателю. Здесь
> память считает ARC, и появляется новый класс ошибок: объект и таймер,
> сильно держащие друг друга. Лечится тем же `weak`, что и циклы с блоками
> и делегатами.

## Что повторить перед Senior-собеседованием

Если на любой пункт отвечаешь не из модели, а «по памяти» — вернись к задаче.

- **`isa` и метаклассы.** Объект → класс → метакласс → корневой метакласс
  (замкнут на себя). `-методы` живут в классе, `+методы` — в метаклассе
  (задача 1).
- **Отправка сообщения.** `[obj foo:5]` = `objc_msgSend(obj, sel, 5)`; `SEL`
  — имя, `IMP` — код, `Method` — их пара; сначала кэш класса, потом поиск
  от `isa` вверх по `superclass` (задача 2).
- **Три шанса пересылки.** `resolveInstanceMethod:` (доращиваем метод) →
  `forwardingTargetForSelector:` (один другой получатель, дёшево) →
  `methodSignatureForSelector:` + `forwardInvocation:` (`NSInvocation`,
  много получателей, дорого) → `doesNotRecognizeSelector:` и падение
  (задачи 3, 4, 5).
- **Два корня.** `NSObject` (почти всё) и `NSProxy` (тонкий, для прокси —
  ничего лишнего не перехватывает) (задача 6).
- **Swizzling.** Только в `+load`, `dispatch_once`, сначала `class_addMethod`
  (не ломать родителя); свиззлить свой класс статически, а не
  `object_getClass(obj)` — там может оказаться KVO-подкласс (задачи 7, 8).
- **Связанные объекты.** Категория добавляет методы, но не ivar — данные
  цепляем через `objc_setAssociatedObject` по адресу-ключу (задача 9).
- **KVO изнутри.** Подмена `isa` на `NSKVONotifying_…`, перехват сеттера,
  `-class` врёт; обязателен `removeObserver:` (задача 10).
- **Категории-дубли.** Два метода с одним именем — поведение не определено;
  категория добавляет, а не подменяет; префиксы (задача 11).
- **Потоки.** `atomic` ≠ потокобезопасная коллекция и ≠ атомарный
  read-modify-write; синглтон — `dispatch_once`; кэш — concurrent-очередь +
  `dispatch_barrier_async`; `dispatch_sync` на текущую serial-очередь —
  дедлок, который современный GCD превращает в падение (задачи 12–15).
- **`weak` и пулы.** `weak` потокобезопасен, но читай один раз в сильную
  локальную; у своего фонового потока нет явного пула, неявный сливается
  лишь при выходе из потока — оборачивай в `@autoreleasepool` (задача 16).
- **Исключения.** Программерская ошибка, не управление потоком; пересекая
  пул, **не** сливают его; непойманное в фоне валит весь процесс
  (задача 17).
- **Tagged pointers.** Маленькие `NSNumber` живут в самом указателе — `==`
  «случайно» прав; сравнивай через `isEqual:` (задача 18).
- **`NSTimer`.** Держит `target` сильно — цикл через run loop; лечится
  блочным таймером с `weakSelf` и `invalidate` (задача 19).
